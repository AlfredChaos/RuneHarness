Context Compact — 上下文压缩

「上下文总会满，要有办法腾地方」— 四层压缩策略，便宜的先跑，贵的后跑

Learn Claude Code · s08 记忆管理 · 414 LOC · 9 个工具 · Harness 层：压缩 — 干净的记忆，无限的会话

0问题：上下文一定会满 — Agent 跑着跑着就不动了

每条命令输出、每个文件内容都堆在 messages 列表里：读 1 个 1000 行文件 ≈ 4000 token， 读 30 个文件、跑 20 条命令后，窗口被占满，API 直接拒绝：prompt_too_long。 不压缩，Agent 没法在大项目里干活。

1总览：agent_loop 里的压缩管线 — 每轮 LLM 调用前先跑三层预处理器

保留 s07 的 hook / 技能加载 / 子 Agent 骨架。核心变动：每轮 LLM 调用前插入三层纯文本预处理器（0 次 API）； token 仍超阈值才触发 LLM 摘要（1 次 API）；API 报错时走应急裁剪。

L1 snip · 裁消息 L2 micro / 正常流程 L3 budget · 落盘 L4 LLM 摘要 应急 / 主动 compact

2各层详解：消息列表前后对比 — 颜色：user 青 · assistant 绿 · tool_result 紫

3关键设计决策 — 为什么是这个顺序、这些数字

顺序不能换

  • • 执行顺序：budget → snip → micro（编号 L3→L1→L2）
  • • micro 会把旧大结果替换成一行占位符
  • • 所以 budget 必须先跑，把完整内容落盘
  • • CC 源码同理：applyToolResultBudget 在最前（query.ts:379）

配对不可拆

  • • assistant(tool_use) ↔ user(tool_result) 必须成对
  • • snip 的 head_end / tail_start、reactive 的 tail_start
  •   都会向前微调，避开孤儿 tool_result
  • • 否则 API 直接报协议错误

便宜的先跑，贵的后跑

  • • L1/L2/L3：纯文本/结构操作，0 次 API，每轮都跑
  • • L4：1 次 LLM 调用，仅超阈值才触发
  • • reactive：只在 API 报错后兜底
  • • 摘要提示词首尾双重防呆：禁止调用工具

防死循环

  • • auto compact 熔断器：连续失败 3 次即停
  • • reactive 重试上限 1 次，超限 raise
  • • compact 工具调用后 break 本轮，干净重开
  • • 杜绝「压缩→仍失败→再压缩」无限烧 API
