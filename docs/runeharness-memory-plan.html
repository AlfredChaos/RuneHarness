RuneHarness 记忆模块方案

记忆统一进 SQLite。会话启动时把用户记忆注入第一条 user 消息。/dream 是唯一的提取入口：手动触发、定时触发、退出时收尾各一次。换人格 = 换 Profile。

依据 learn.shareai.run s09 + CC src/memdir、services/{extractMemories, autoDream} 衔接 docs/runeharness-compaction-plan.html v0.4 草案 · 2026-10-06 · 统一 DB + supersede 流水 + entities/related 关系列
怎么读：第 1 章给结论。第 2、3 章说明参照对象和现状约束。第 4 章定义两个抽象（Space / Profile）。第 5–8 章是存储、读、写、dream 四条机制，每条先给场景再讲设计。第 9 章给两个画像的完整定义。第 10–15 章是装配、边界、风险、阶段与未决项。

术语表：
记忆空间：一个隔离的记忆全集，等于 DB 里的一组行（(tenant, space) 主键前缀）。
索引：一段渲染文本，每行一条记忆的一句话描述，由 SQL 查询生成，不落盘。
正文：一条记忆的完整内容。
提取：dream 的第一阶段，从对话行里筛出该记的内容。
整理：dream 的第二阶段，合并、去重、淘汰已有记忆。
画像（Profile）：这套 agent 该记什么的全部配置。
视图：session.Fold 组装的发送形态。原始行：append-only 消息行。
未消化行：id 大于本空间记录的水位的原始行。
第 1 章 · 结论先行

一张表、一次启动注入、一个 /dream 命令

记忆 = memories 表 + 启动注入 + dream 循环。

记忆存在 ~/.rune/memory.db 里，按 (tenant, space, name) 隔离。云端换成同一个 memory.Store 接口的 Postgres 实现。

读：会话启动时，代码把索引和常驻正文拼进第一条 user 消息。这条消息落在 Fold 首部，整个会话都在视图里。dream 更新记忆后，下一条 user 消息重新注入一份新快照。

写：模型用 memory 工具直写；/dream 消化本空间所有未消化的会话行，产出 ops 更新记忆。dream 有三个触发器：手动命令、进程内定时器、正常退出时收尾。

换人格 = 换 Profile。画像决定记什么、记到哪、哪些类型常驻注入。机制不变。

四个取舍定形：

1
记忆统一进 DB，不落文件
记忆按行存进独立库文件 ~/.rune/memory.db。代码独占写口。云端多租户下进程盘既不隔离也不持久，DB 形态本地云端同构——本地是 SQLite，云端是 Postgres，换 memory.Store 实现即可。代价是用户不能像改文件一样改记忆，由 /memory 命令和 memory 工具补上读写口。见 §5。
2
注入挂第一条 user 消息，借 Fold 首部常驻
Fold 永远保留前 3 条真实 user 消息作首部。记忆块骑在第一条 user 消息上，就等于在视图里常驻——压缩甩不掉它，也不需要水印机制。代价是它是快照：dream 改了记忆后，下一条 user 消息附一份新索引，模型以最新份为准。见 §6。
3
写面由专用工具封死
RH 没有 write_file，写文件只能经 run_command 撞 Gate3 确认。 memory 工具直接调 Store，参数只有 name/type/description/body，模型给不了路径也给不了 tenant。见 §7.1。
4
提取只走 dream，消化范围是全部未消化行
不做每轮后台提取。dream 按会话水位读本空间所有未消化的原始行——不只当前会话。进程被 kill 不会丢记忆，下次 dream 自动补账。见 §8。
注意 · v1 不做四件事

不做 embedding 检索：单空间行数预期在百级，索引全文注入够用。不做每轮 side-query 选择：启动注入已覆盖常驻部分，其余正文用 memory 工具按需取。不做 session memory：RH 已有滚动摘要。不做多层空间（private + team）：留扩展缝。

第 4 章 · 核心抽象

Space 定"记在哪"，Profile 定"记什么"

灵活性需求只落在两个抽象上。Space 是隔离和寻址单元。Profile 是记忆的全部策略。

4.1 Space：一个空间 = DB 里一组行

场景 云端陪伴 agent 服务两个用户

一个陪伴 agent 实例部署在云端。租户 tenant-7 下的用户 u100 和用户 u200 先后与它对话。两人各自的画像和共同经历不应互相泄漏。

请求入口把 Scope{TenantID: "tenant-7", SubjectID: "u100"} 注进 ctx。代码按画像的 Space=subject 解析出空间键 subject/tenant-7/u100。所有 SQL 都带 WHERE tenant=? AND space=?。

两个空间在同一张表里是两组行。模型全程看不到这些键。模型要跨用户读记忆，参数层面没有能表达这个动作的字段。

结论：Space 由画像声明键型，由代码从 ctx 的 scope 解析。模型从始至终不知道键。

SpaceKind 键来源 适用人格 space 列的值
workspace scope.Workspace 清洗为 slug（worktree 归并到 git 根） coding agent ws/<slug>
subject scope.SubjectID（新增字段，云端入口注入） 陪伴 / 专家 agent subject/<subject>。SubjectID 为空时回落 local-user
tenant scope.TenantID 租户级共享知识（预留） shared（tenant 列已是边界）
注意 · 本方案对既有代码唯一的横切改动

subject 空间需要 Scope.SubjectID 字段。云端入口按 auth 身份注入。本地 CLI 恒为 local-user。其余实现全部收在新包 internal/memory 内。

4.2 Profile：记忆画像

场景 同一份代码，两种人格

用户在仓库 RuneHarness 里对 coding agent 说"集成测试别 mock 数据库"。同一份二进制，换一个 Profile，作为陪伴 agent 听老周说"以后叫我老周就行"。

两个请求走同一套读写机制。coding 画像把第一条存成 type: feedback。companion 画像把第二条存成 type: expression。类型辞典不同，机制相同。

结论：Profile 是一套完整策略。它声明空间键型、类型辞典、提取焦点、不存清单、常驻注入类型和 dream 节奏。它不进存储层。存储层只看到行。

type SpaceKind string // workspace | subject | tenant

// TypeDef 定义一类记忆：名字进 type 列，文案进 system 指令和 dream 提示。
type TypeDef struct {
    Name         string // type 值，如 "feedback"
    Desc         string // 这类记忆是什么
    Save         string // 何时存
    Use          string // 读到后怎么用
    Body         string // 正文结构约定，如 "**Why:** / **How to apply:**"
    Example      string // 对话示例
    AlwaysInject bool   // true = 启动注入时连正文一起带上（pinned）
}

type DreamCfg struct {
    MinRows      int // 未消化行数下限，不足不跑（默认 4）
    IntervalMin  int // 定时器间隔分钟（coding=60，companion=120）
    BodyBudget   int // dream 输入可携带的已有正文总字节（默认 24KB）
    BatchRows    int // 单次消化原始行上限，超出分批（默认 300）
}

type InjectCfg struct {
    MaxIndexBytes int // 索引文本上限（默认 8KB）
    MaxBodyBytes  int // 常驻正文合计上限（默认 16KB）
}

type Profile struct {
    Name      string
    Space     SpaceKind
    Types     []TypeDef
    DoNot     []string // 不存清单
    Focus     string   // 提取侧重点，dream 提示的第一段
    Dream     DreamCfg
    Inject    InjectCfg
    WriteTool bool     // 是否向模型暴露 memory 工具
}

画像有两个来源。内置 Go 常量提供 coding、companion、generic（§9）。文件 ~/.rune/profiles/<name>.md 提供自定义画像，frontmatter 写旋钮，正文写辞典和 Focus。选择顺序是 RUNE_MEMORY_PROFILE 环境变量、文件、内置。

第 5 章 · 存储

一个 DB 文件，两张表

记忆存 ~/.rune/memory.db。它与会话库 ~/.rune/sessions.db 是两个文件、两个连接——会话 schema 演进不影响记忆 schema。所有读写经 memory.Store 接口，云端换 Postgres 实现。

5.1 表结构

CREATE TABLE memories (
  tenant      TEXT NOT NULL,
  space       TEXT NOT NULL,   -- 'ws/<slug>' | 'subject/<id>' | 'shared'
  name        TEXT NOT NULL,   -- slug，模型给的 name 经清洗
  type        TEXT NOT NULL,   -- 画像辞典里的类型
  descr       TEXT NOT NULL,   -- 一句话描述，索引行用它
  body        TEXT NOT NULL,   -- Markdown 正文
  source_sess TEXT,            -- 产生它的会话
  entities    TEXT,            -- 逗号分隔的实体标签："孩子","领导","ingest-pipeline"
  related     TEXT,            -- 逗号分隔的 name，指向与本条有关联的记忆
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  PRIMARY KEY (tenant, space, name)
);

CREATE TABLE memory_log (      -- append-only 变更流水，可重放的来源
  seq       INTEGER PRIMARY KEY AUTOINCREMENT,
  tenant    TEXT NOT NULL,
  space     TEXT NOT NULL,
  name      TEXT NOT NULL,
  op        TEXT NOT NULL,       -- upsert | supersede | delete | merge
  old_body  TEXT,               -- supersede / delete 时的旧值
  new_body  TEXT,
  reason    TEXT,               -- 模型给的变更理由
  sess      TEXT,
  at        INTEGER NOT NULL
);

CREATE TABLE memory_meta (
  tenant  TEXT NOT NULL,
  space   TEXT NOT NULL,
  key     TEXT NOT NULL,    -- 'cursor:<sessID>' | 'last_dream' | 'dream_failures' | 'dream_lock'
  value   TEXT NOT NULL,
  PRIMARY KEY (tenant, space, key)
);
  • name 清洗规则与文件方案一致：转小写、非字母数字折成 -、拒绝 .. 和分隔符。保留名集合仍在（memory-index 等），虽然 DB 下没有路径逃逸，清洗是为了让 name 能安全进提示和日志。
  • memory_meta 存 dream 的运行状态：每会话水位、上次 dream 时间、熔断计数、锁行。
  • memory_log 兼任两份职责：变更审计（可重放，折叠流水得到任意时刻的信念集）和 tombstone——dream 输入携带近期 delete 清单，防止已删记忆从未消化行里复活（§8.4）。
  • entities 是"这条记忆关于谁"的标签列。实体归一在写入时由模型做，不在查询时做。 related 是记忆间的边，供按图找上下文。两者是轻量关系层，不是图数据库（§8.4）。
  • schema 版本走一行 meta key='schema_version'，与 session sqlite 的迁移方式一致。

5.2 Store 接口：本地云端同一个形状

type Store interface {
    // 空间从 ctx 的 scope + 画像解析。接口签名里没有租户参数，
    // 模型生成的参数无法指定读写目标（与 session.Store 同一套路）。
    List(ctx)             ([]Header, error)  -- name/type/descr/updated_at
    Get(ctx, name)        (Row, error)
    Upsert(ctx, r Row)    error              -- name 清洗在实现内
    Delete(ctx, name)     error
    Meta(ctx, key)        (string, error)    -- 水位/锁/熔断计数
    SetMeta(ctx, k, v)    error
    History(ctx, name)    ([]Change, error)  -- memory_log 回放一条记忆的变更史
    RecentDeletes(ctx)    ([]string, error)  -- tombstone 清单，dream 输入防复活
    Lock(ctx, ttl)        (unlock func() error, ok bool, err error)
}
  • 本地实现：SQLite + WAL。锁用 memory_meta 里的 dream_lock 行（lease + 过期时间，INSERT OR IGNORE 竞争）。
  • 云端实现：Postgres，同一组表。tenant 列天然是隔离边界；可再加行级安全策略兜底。

5.3 配额

位置 上限 超出后的行为
索引渲染 8KB（Inject.MaxIndexBytes），约 100 行 按 updated_at 降序截断，追加警告行写明哪条限命中
单条描述 150 字符 写入时截断

第 6 章 · 读路径

启动注入常驻位，其余按需自取

场景 新会话第一句："继续昨天的工作"

用户新开一个会话。工作区是同一个仓库，记忆空间里有昨天 dream 出的三条记忆。

user
继续昨天的工作

<memory-index updated="2026-10-06T18:23+08:00">
- [project] project-auth — auth 重写由合规驱动，截止 11-01
- [feedback] feedback-testing — 集成测试连真实库
- [user] user-role — 十年 Go，React 新手
</memory-index>
assistant
从 auth 重写接着来。昨天做到一半的是…… 需要细节时调 memory(op=read, name="project-auth")

这条 user 消息是本会话第一条真实 user 消息。Fold 的首部永远保留前 3 条 user 消息——记忆块骑在它上面，等于在整个会话的视图里常驻。压缩折叠中段，首部不动。

6.1 启动注入：一次，落在首部

装配规则：

  1. 代码在本进程内该会话的第一条 user 消息上，附加 <memory-index> 块。
  2. 索引由 SQL 查询渲染：本空间全部记忆按 type 分组、组内按 updated_at 降序，每行 - [type] name — descr。索引不落盘，它不是文件。
  3. 画像里 AlwaysInject=true 的类型，正文一并带上（每篇 ≤4KB，合计 ≤16KB）。
  4. dream 改动了记忆后，下一条 user 消息再附一份新索引，带 updated 时间戳。首部的旧快照不再更新——模型以最新一份为准（行为提示里写明这条）。
  5. 空间为空时不注入任何块。
为什么不每轮注入

注入内容随每条 user 消息进原始行。每轮重复注入一份 8KB 索引就是膨胀源。第一条 user 消息借 Fold 首部常驻，一次注入全程有效——这是 RH 折叠视图结构免费送出的长驻位，CC 的文件方案里没有对应物。

6.2 正文按需取：memory op=read

启动注入只带索引和常驻类型正文。任务中途需要某条记忆的细节时，模型调 memory(op=list) 看索引、 memory(op=read, name=…) 取正文、op=about 按实体聚合、op=history 看一条记忆的变更史。这取代了 CC 的每轮 side-query 选择——少一次每轮 LLM 调用，代价是模型要自己判断"该去翻了"（行为提示里写明何时去读）。

第 7 章 · 写路径

模型直写 + dream 提取，互不重叠

用户说"记住这个"时模型立即直写。用户没明说但表达了偏好时，dream 兜底。两条路径写同一张表。

7.1 memory 工具：模型可见的写口

场景 用户说"记住：集成测试连真实库"

用户在会话里显式要求记住一条工程约定。

没有专用工具（走 run_command）
# 模型凑一条 sqlite 命令插行
$ sqlite3 ~/.rune/memory.db "INSERT …"
# Gate3 弹窗：allow "sqlite3 …"？
# SQL 写错没人拦，tenant 写错没人发现
memory 工具
memory(op=save,
  name="feedback-testing",
  type="feedback",
  description="集成测试连真实库",
  body="…**Why:** 上季度被 mock 坑过")
→ saved: feedback-testing
# 无弹窗，写面封死在本空间
name: memory
description: Read and update the persistent memory store.
  ops: save (name, type, description, body, [entities], [related]) |
       forget (name) | list | read (name) | about (entity) | history (name).
  Memories persist across sessions — do not store ephemeral task state.
  • 工具注册进 SafeTools。写面被实现封死在本空间，等价于 CC 的 isAutoMemPath carve-out，但更强——模型连空间键都给不了。
  • op=read 返回正文，op=list 返回索引文本。op=save 返回 saved: <name>，不回填索引。
  • Profile.WriteTool=false 时不注册工具。陪伴场景可让"记得"完全来自 dream，模型不感知记忆存在。

7.2 dream 提取：见第 8 章

dream 是本方案唯一的提取入口。它消化本空间全部未消化行，产出 ops 更新 memories 表。触发器和流程在 §8。

8.1 触发器

结论：ticker 是心跳不是节奏。ticker 每 10–15 分钟只做一次 meta 读，空转几乎免费。真正的节奏由 §8.2 的门决定：物量门管"欠账够不够格"，间隔门管"记忆晚多久入库能接受"。coding 画像的记忆大头走工具直写，dream 只捞遗漏，冷却放到 60 分钟。companion 画像里 dream 是唯一写口，冷却定 120 分钟——退出收尾兜住"聊完就走"的场景，ticker 只管连续聊过 2 小时的长会话。记忆延迟的实际口径是"会话结束或 2 小时，先到为准"。

触发器 位置 门控
/dream 命令 suggest.go 的 slashCommands，TUI 发 DreamMsg 只过锁。手动触发不看间隔和物量
定时器 进程内 ticker，间隔 = Profile.Dream.IntervalMin。云端形态换成 cron 调 Dream() 过全部三道门
退出收尾 main.go 在 program.Run() 返回后调一次，超时 30 秒 过锁和物量门，不看间隔门

8.2 三道门

  1. 物量门：本空间全部会话的未消化行合计 ≥ Dream.MinRows。水位存在 memory_meta key='cursor:<sessID>'。
  2. 间隔门：距上次 dream ≥ IntervalMin 分钟。key='last_dream' 记录时间。
  3. 锁门：抢不到 dream_lock 租约就跳过。租约 10 分钟过期，抗进程崩溃。

8.3 dream 循环

1
代码收集欠账
列出本空间的会话水位。对每个有未消化行的会话，读 LoadRawHistory 里 id > 水位 的非控制行。读原始行而不是视图：视图的中段可能已被摘要，原始行不受压缩影响。渲染口径对齐 summary.go 的 renderEvent。
2
分批消化
未消化行超过 BatchRows 就分批。每批一次 side-query：输入是画像提取提示 + 已有清单（正文总量 ≤ BodyBudget 时连正文一起给，供模型判断更新还是新增）+ 本批渲染 + 近期删除清单（tombstone，§8.4）。输出 JSON ops：[{op: upsert|supersede|delete, name, type, description, body, entities, related, reason}]。 supersede 表示"旧信念被新事实更替"，应带 reason。
3
代码校验落盘
ops 逐条校验：type 应在辞典内，name 应过清洗，delete/supersede 应指向已存在行，supersede 应带 reason。通过后 Upsert/Delete 落库并写 memory_log，水位推进到本批末尾。失败计 dream_failures，连续 3 次熔断——与 compact 同一口径。
4
整理阶段（物量门再加一道）
提取跑完后，记忆行数 ≥30 或本轮改动 ≥10 条时追加一次整理调用：side-query 读全部记忆，输出 ops（upsert / delete / merge-into），代码执行。矛盾条目在此合并（场景见下）。
5
回报
触发 OnChange(n)，TUI 落一行 memory updated: N new, M merged。下一条 user 消息自动带新索引（§6.1 第 4 条）。
场景 整理阶段合并两条打架的记忆

空间里有 feedback-test-db（"集成测试连真实库"）和后来 dream 出的 feedback-test-mock（"CI 环境没有数据库，CI 里允许 mock"）。两条都对，字面冲突。

整理把它们合成一条 feedback-testing（"本地连真实库；CI 无数据库时允许 mock，在配置里注明环境判断"）。合并由 side-query 提议，由代码执行。

注意 · dream 与提取提示

提取提示三段式：Focus（画像的第一段，说清该捕捉什么）→ 类型辞典（逐类型的 save/use/structure）→ 不存清单 + ops 契约（没有新信息就返回 []；已有清单前置给模型去重）。写记忆的语言跟随对话语言。

8.4 变更、删除与边界场景

场景 昨天喜欢苹果，今天讨厌苹果

上次 dream 存了 persona-food（"喜欢苹果"）。这一轮用户说"我现在讨厌苹果，查出血糖高"。

dream 看到已有清单里的旧条目和新表述，输出 supersede：新正文写"现在讨厌苹果（2026-10 起因血糖偏高）；此前喜欢"，reason 写"用户改口"。代码把新正文落库，把旧正文连同 reason 写进 memory_log。

结果分两层：当前表是此刻的信念（讨厌苹果），流水是全部变更史（曾喜欢苹果）。决策用前者，回放用后者——"上周你为什么推荐我买苹果"有答案了。变化叙事留在正文里，因为"人变了"本身就是信号，陪伴场景尤其如此。

结论：版本不是表的维度，是一条 append-only 流水。memories 永远存当前信念， memory_log 记每次变更的旧值、新值、reason、会话和时间。可重放 = 折叠流水到任意时刻；审计 = 流水本身。

边界场景 例子 机制
矛盾陈述 昨天喜欢苹果，今天讨厌苹果 supersede op 带 reason。旧值进 memory_log，新正文可写变化叙事
删除后复活 说"忘掉苹果"时，含该信息的原始行还未消化 dream 输入带 RecentDeletes 清单，提取提示写明"被删条目不重建"。tombstone 由 memory_log 兼任
同一实体多条记忆 "孩子"出现在 5 条记忆里 entities 列聚合。memory op=about "孩子" 一次取全
事件链条 模考 → 志愿填报 → 中考 related 列互指 + bond 正文的事件结构（§9.2）
称呼变体 老周 / 周哥 / 周叔 提取时模型归一到同一 entity。整理阶段合并别名
过期事实 "孩子今年中考"在明年失效 提取时相对日期转绝对。整理阶段按时间淘汰或改写过时条目
不确定信息 "我可能要换工作" 正文标"未确认"。后续确认时 supersede
为什么不加图谱和双时态表

记忆的消费者是 LLM，不是查询引擎。模型读自然语言本来就能连"初三学生家长"和"模考失利"。 entities/related 两列解决的是"找得全"，不是"表达语义"——语义留在正文里，模型读得懂。同样，版本需求拆成"当前信念"（表）和"变更史"（流水）两层就够了，bi-temporal 的 valid_from/valid_to 查询在这个量级买不到东西。图谱和双时态都留作规模上来后的扩展（§15）。

第 10 章 · 装配

main.go 的五处接线

// internal/memory 单例。store 供 LoadRawHistory 取欠账，llm 供 dream side-query。
mem, err := memory.New(store, model, memory.Config{
    DBPath:  cfg.MemoryDB,      // RUNE_MEMORY_DB，空 → ~/.rune/memory.db。云端换 Store 实现
    Profile: prof,              // cfg.MemoryProfile → 内置表 / ~/.rune/profiles/
    Dream:   cfg.MemoryDream,   // RUNE_MEMORY_DREAM，默认开
})
// 写口：画像允许时注册工具。
toolSet = append(toolSet, mem.Tool())
permCfg.SafeTools = append(permCfg.SafeTools, memory.ToolName)
// 读：第一条 user 消息带索引 + 常驻正文；dream 后重注索引。
a.Hooks.OnUserPromptSubmit(mem.InjectOnce)
// dream：定时器 + 退出收尾；/dream 走 TUI 命令。
go mem.DreamTicker(ctx)          // 间隔 = Profile.Dream.IntervalMin
defer mem.DreamOnExit()          // program.Run() 返回后跑一次，30s 超时
// system：画像的稳定指令段进 Env。
env.MemoryGuide = mem.SystemGuide()  // 空串则省略该段
// TUI：dream 完成后落一行提示。
mem.OnChange = func(n int) { p.Send(tui.MemoryMsg{Saved: n}) }
环境变量 默认 作用
RUNE_MEMORY on 总开关。=0 时整个模块不装配
RUNE_MEMORY_PROFILE coding 内置名，或 ~/.rune/profiles/ 下的文件名
RUNE_MEMORY_DB ~/.rune/memory.db 本地记忆库文件
RUNE_MEMORY_DREAM on 定时器和退出收尾开关。关闭后仍可 /dream 手动触发和直写

TUI 增量有三处。/dream 命令手动触发一次 dream。/memory 命令显示空间键和索引文本。两条都注册进 suggest.go 的 slashCommands。 MemoryMsg 在对话区落一行 memory updated: 2 new, 1 merged。

第 11 章 · 边界

记忆和压缩各管一段，互不读写对方状态

压缩（internal/compact） 记忆（internal/memory）
管什么 本会话的发送形态：卸载、摘要、熔断 跨会话的知识：偏好、事实、指针
存哪 sessions.db：消息行、控制行、blob、session_state memory.db：memories + memory_meta
谁写 循环内 Maintain / Compact / Backfill 模型（memory 工具）+ dream
谁读 Fold 组装视图 第一条 user 消息的注入块
读对方吗 不读记忆。压缩只动消息行 不读压缩状态。dream 走 LoadRawHistory 原始行，天然越过折叠

三个交互点确认无害：

  • 首部注入与压缩共存。记忆块骑在第一条 user 消息上，属首部，压缩只动中段。视图里它永远在场。
  • dream 读原始行。视图折叠不影响 dream 输入。水位按原始行 id 记，压缩不产生行 id 之外的洞。
  • blob 指针只给预览。原始行里的 <persisted-output src="blob://…"> 以预览形态进 dream 输入。提取目标是偏好和事实，不依赖工具输出全文。提取提示允许模型放弃需要全文才能判断的线索。
第 12 章 · 安全与隐私

隔离靠 scope 不靠参数，写面只有工具

  • 写面：memory 工具和 dream 代码只能写 (tenant, space) 前缀下的行。name 经 slug 清洗。模型参数里没有租户和空间字段，跨租户读写在参数层不存在。
  • 读面：记忆在 DB 里，不在进程盘上。read_file 不限路径也够不到它——上一轮文件方案里最大的越界口，在 DB 形态下消失了。
  • 不存凭据，双层防线：软层是每个画像的 DoNot 固定含"密钥、凭据、token 一律不存"，dream 提示复述。硬层是代码侧——Upsert 前对 body/description 跑密钥模式扫描（ sk- 前缀、JWT、PEM 私钥头等），命中直接拒绝写入。提示词防的是"模型主动写"，扫描防的是"模型没认出来"。
  • 遗忘权：用户说"忘掉 X"时模型用 op=forget 立即删行。陪伴画像的提取提示还要求"用户标了别记的内容不进记忆"。
  • 索引不泄密：索引描述行进视图文本。提取提示要求 description 只写主题，不写敏感值。
注意 · DB 形态下残余的两个口子

一是 run_command：模型可以执行 sqlite3 ~/.rune/memory.db … 直接碰库文件。Gate3 会弹确认，但白名单一旦放行过 sqlite3 就不再有提示。云端形态下 run_command 应进每租户沙箱，主机上没有库文件可碰。二是 read_file 同理可读库文件字节流。两者都是既有工具面的云端化缺口，记忆落地以沙箱为前提（§15）。

警告 · 云端部署的画像串号风险

陪伴和专家场景的记忆是用户画像，属个人数据。dream 产物跨会话可见，SubjectID 注入错一次就是画像串号。防串号的结构保证是：空间解析只认 ctx 的 scope，dream goroutine 和退出收尾都继承装配时的 scope，不靠传参。前提是入口装配把 SubjectID 注对。上线前应把"dream 输入不跨 subject"写进审计清单。

第 13 章 · 风险

哪些地方可能翻车

风险 触发条件 后果 缓解
首部索引是快照，会旧 dream 改了记忆，首部仍是旧索引 模型可能引用旧条目 dream 后下一条 user 消息重注新索引带时间戳；行为提示写明"以最新一份为准"；before-recommending 段要求先验证再推荐

dream 质量靠模型自觉 JSON 解析失败、乱存、漏存 记忆噪声或缺失 ops 白名单校验 + 已有清单前置去重 + 连续 3 次失败熔断

过期记忆仍在被引用 事实变化后旧记忆未更新 模型按过期事实回答 照抄 CC 的 before-recommending 段：涉及文件、函数、旗标的记忆先验证再推荐；冲突时信当下并顺手改记忆

留给第二个真实用例的五件事

  • 按需选择器。v1 启动注入只带索引和常驻正文，其余靠模型 op=read 自取。若"该翻不翻"成为真实失败案例，加回每轮 side-query 选择（CC 的 findRelevantMemories 是现成参照），挂同一个 OnUserPromptSubmit 即可，不动存储。
  • 云端 Store 实现。Postgres 版 memory.Store + read_file/run_command 每租户沙箱。后者是独立于记忆的既有云端化工作，但记忆云端落地以它为前提（§12）。
  • journal 形态。长驻陪伴场景可考虑 append-only 日志行（CC KAIROS），dream 只蒸馏不进主题行。当前 dream 直写主题行已够用，先不加。
  • 多层空间。private + team 双层（CC TEAMMEM）有真实多用户需求时再加。届时 space 从单值变列表，索引渲染分段。
  • 关系图谱。entities/related 是轻量关系层，不做遍历查询。单空间记忆超过约 500 条、需要多跳查询（"我朋友的同事"）、实体归一要程序化时，再上真图谱（三元组表或图引擎）。写入路径不变，只是 related 从提示列变成查询结构。
  • session memory。CC 用每会话 memory 文件替代摘要调用省一次 LLM 请求。RH 已有滚动摘要，属独立增量。
