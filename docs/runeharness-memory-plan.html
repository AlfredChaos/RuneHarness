RuneHarness 记忆模块方案

一层不丢细节的存储：文件仓库 + 索引 + 按需召回 + 后台提取。同一份机制按 Profile 分形——coding agent 记工程经验，陪伴 agent 记人，专家 agent 记领域事实。

怎么读：第 1 章给结论与四个关键取舍；第 2 章对比教学版与 CC 实装、说明每条抄什么；第 3 章列 RH 现状里决定方案形态的六条约束；第 4 章定义两个核心抽象（Space / Profile）；第 5–8 章是存储、读、写、整理四条机制；第 9 章给两个内置 Profile 的完整定义；第 10–12 章是装配、边界与安全；第 13–14 章排阶段与未决项。
前置约定：下文"视图"指 session.Fold 组装出的发送形态，"原始行"指 LoadRawHistory 返回的 append-only 行；两者不是一回事，方案里反复用到这个区分。
第 1 章 · 结论先行

一个目录、一份索引、两条写路径、两条读路径

记忆 = 记忆空间（一个按 scope 派生的目录）里的 .md 文件集 + MEMORY.md 索引。读：索引随 user 消息按需注入，正文由一次 side-query 按查询选 ≤5 篇附加。写：模型经专用 memory 工具直写（索引由代码重建，模型不碰索引）+ Stop hook 触发后台提取（side-query 出 JSON ops，代码落盘）。整理：低频 Dream 合并去重。换 persona = 换一个 Profile 对象——类型辞典、提取焦点、空间键、读写节奏四个旋钮决定"记什么、往哪记、怎么取"。

方案由四个取舍定形：

1
记忆落文件，不落 DB——与压缩相反
压缩状态是机器中间态，所以进 session.Store；记忆是知识资产：用户要能读、能手改、能带走、能 grep。文件形态与 CC 一致，与 skill 的渐进披露一致。云端形态下文件后端可换对象存储， Store 接口不变（§15）。
2
内容注入走 user 消息，行为指令走 system
prompt.go 已定约定：会话内可变内容不进 system 行（前缀缓存）。所以 Profile 的稳定指令段进 system prompt，索引与选中正文拼进当轮 user 消息——与 expandMentions 的 <attachments> 块同一形态（§6）。
3
写入面由专用工具封死
RH 没有 write_file，写文件只能经 run_command——模型每存一条记忆都会撞 Gate3 确认弹窗，且无法限制写哪里。memory 工具把写盘封死在记忆目录内：slug 清洗、保留名拒绝、索引重建全部在代码侧（§7.1）。
4
提取是 side-query，不是 forked agent
CC 用 forked agent（共享 prompt 缓存、受限工具表、maxTurns=5）。v1 用单次 Chat：输入 = Profile 提取提示 + 已有清单 + 新原始行，输出 = JSON ops 数组，代码执行写盘。读改写在文件小时成立；升级路径是换成迷你 agent loop（§15）。
明确不做（v1）

四件事不在本方案内：embedding 向量检索（文件 ≤200 篇，LLM 直选足够）、session memory 免摘要压缩（RH 已有滚动摘要管线，internal/compact）、多层空间（private + team 双目录，留扩展缝）、远端记忆同步。

读法

CC 实装里真正值得连文案一起抄的是提示词段落：TYPES_SECTION_*、 WHAT_NOT_TO_SAVE_SECTION、WHEN_TO_ACCESS_SECTION、 TRUSTING_RECALL_SECTION 都标注了 eval 案例（如"ignore memory"反模式、H1 验证-再推荐）。这些是磨出来的行为约束，重写一遍只会更差。机制层则可裁剪——forked agent 换成 side-query 属于降级，但游标、互斥、门控这些"形状"必须保留。

第 3 章 · 现状约束

RH 里六条已经定死的边界

方案不是从白纸画的，是从现有代码的六个事实倒推的。每条事实直接排除掉一类做法。

现状 位置 排除掉的做法 / 推出的结论
没有 write_file，写文件只能经 run_command，未白名单命令弹 Gate3 确认 internal/tools、internal/permission "教模型用 shell 写记忆"不可行（每存一条弹一次窗，路径还封不住）⇒ 必须有专用写工具

append-only 消息行 + 控制行；Fold 组装视图 = system + 首部 + 最新摘要 + 尾部 internal/session/view.go 注入块是普通 user 消息内容，随 fold/摘要/卸载自然消化——不需要新消息种类，也不需要"过期清理"

第 4 章 · 核心抽象

Space 定"记在哪"，Profile 定"记什么、怎么取"

4.1 Space：一个目录 = 一个隔离的记忆全集

Space 是隔离与寻址单元。它由 Profile.Space 声明键型，由 memory.New 从 ctx 的 scope 解析出具体目录。模型从始至终不知道路径——写工具参数只有 name/type/description/body，读侧由召回器代读。

SpaceKind 键来源 适用 persona 本地形态
workspace scope.Workspace 清洗为 slug（对齐 CC 的 git-root 口径：worktree 归并到同一根） coding agent ~/.rune/memory/ws/<slug>/
subject scope.SubjectID（新增字段，云端入口注入终端用户 id） 陪伴 / 专家 agent ~/.rune/memory/subject/<tenant>/<subject>/；SubjectID 为空时回落 local-user
tenant scope.TenantID 租户级共享知识（预留） ~/.rune/memory/tenant/<tenant>/
注意 · scope 加一个字段

subject 空间需要 Scope.SubjectID：云端请求入口按 auth 身份注入，本地 CLI 恒为 local-user。这是本方案对既有代码唯一的横切改动；其余全部在新包 internal/memory 内闭环。

4.2 Profile：记忆画像

Profile 是"这套 agent 该长什么样的记忆"的全部答案。它不进存储层——存储层只看到目录与文件；它只进 prompt 装配与读写节奏。

type SpaceKind string // workspace | subject | tenant
type Mode     string // indexed  | journal

// TypeDef 是一类记忆的完整说明：名字进 frontmatter，文案进
// system 指令段与提取提示（对齐 CC TYPES_SECTION 的逐类型结构）。
type TypeDef struct {
    Name    string // frontmatter type 值，如 "feedback"
    Desc    string // 这类记忆是什么
    Save    string // 何时存
    Use     string // 读到后怎么用
    Body    string // body 结构约定（如 "**Why:** / **How to apply:**"）
    Example string // 一两条对话示例
}

type ExtractCfg struct {
    MinNewRows   int // 新原始行数下限，不足不提取（默认 2）
    EveryTurns   int // 每 N 个可提取轮跑一次（coding=1，companion=1）
    BodyBudget   int // 提取输入里允许携带的已有正文总字节（默认 24KB）
}

type RecallCfg struct {
    MaxFiles     int // 单轮正文注入上限（默认 5）
    MaxFileBytes int // 单篇正文上限（默认 4KB，对齐 CC 4096B）
    MaxTurnBytes int // 单轮正文合计上限（默认 16KB）
    Selector     string // "llm" | "keyword"；llm 失败自动降级
}

type Profile struct {
    Name    string
    Space   SpaceKind
    Mode    Mode
    Types   []TypeDef
    DoNot   []string // "不存"清单
    Focus   string   // 提取侧重点（提取提示的第一段）
    Extract ExtractCfg
    Recall  RecallCfg
    WriteTool bool // 是否向模型暴露 memory 写工具
}

Profile 两份来源：内置 Go 常量（coding / companion / generic，见 §9）+ 文件覆盖 ~/.rune/profiles/<name>.md（frontmatter 写旋钮，正文写辞典与 Focus——与 skill 的 SKILL.md 同一渐进披露形态）。选择顺序：RUNE_MEMORY_PROFILE > 文件 > 内置。

第 5 章 · 存储

目录布局与文件格式

~/.rune/memory/<space-kind>/<key>/
├── MEMORY.md            # 索引：一行一条目，≤200 行 / 25KB（超出截断+警告行，对齐 CC）
├── user-role.md         # 一条记忆一个文件，YAML frontmatter + 正文
├── feedback-testing.md
├── logs/YYYY/MM/YYYY-MM-DD.md   # 仅 journal 模式：追加日志
├── .state.json          # 代码自管状态：提取游标、熔断计数、上次整理时间
└── .consolidate.lock    # 整理锁；mtime 即 lastConsolidatedAt，1h 过期

5.1 记忆文件

---
name: user-role
description: User is a senior Go engineer, new to React — frame frontend answers via backend analogues
type: user
---

正文。feedback / project 类建议结构：规则或事实先行，随后 **Why:**（用户给过的理由）
与 **How to apply:**（何时何地生效）两行——知道 why 才能判断边界情况。
  • 文件名 = slug(name)：小写、非字母数字折叠为 -、去 .. 与分隔符——路径逃逸在参数层就不成立。
  • 保留名拒绝：MEMORY.md、.state.json、.consolidate.lock、logs/ 下的名字不能由工具写入。
  • 写入原子化：tmp + rename。多进程同空间下最后一个写者赢单文件，索引总是再生成，不失一致性。

5.2 索引

- [user-role](user-role.md) — User is a senior Go engineer, new to React
- [feedback-testing](feedback-testing.md) — Integration tests must hit a real database, not mocks

索引由代码在每次写/删/整理后从 frontmatter 扫描重建，按 type 分组、mtime 降序。单行 ≤150 字符。模型只读索引、不写索引——CC 的"两步保存"在 RH 里被收成一步。

5.3 配额（全部对齐 CC 数值）

位置 上限 超出后的行为
扫描文件数 200 个 .md（mtime 降序） 更老的只存在目录里，不进清单——整理流程负责收敛
frontmatter 读取 前 30 行 截断解析
MEMORY.md 注入 200 行 / 25KB 截断 + 追加警告行（写明哪条限命中）
单篇正文注入 4KB 截断 + [truncated] 标记
单轮正文合计 16KB（Profile.Recall.MaxTurnBytes） 截断候选清单
第 6 章 · 读路径

索引常驻当轮，正文按需附加

读路径全部挂在 OnUserPromptSubmit：每用户轮恰好一次，hook 的 replace 返回值把记忆块拼进 user 消息本体。与 expandMentions 的 <attachments> 同一形态——落库、回放、压缩都不需要新机制。

6.1 索引注入：变了才注，丢了自愈

索引若每轮重复注入会成为膨胀源（它随每条 user 消息进原始行）。hook 持两个事实做判断：

  1. lastIndexHash：上轮注入的索引内容哈希。哈希变化 ⇒ 重新注入完整索引块。
  2. 自愈扫描：视图尾部 40 条消息内不存在 <memory-index> 标记 ⇒ 重新注入。压缩把中段连同旧标记摘要掉之后，规则自动复活索引，不需要水印机制。

注入形态（附加在 user 消息尾部）：

<memory-index dir="…" updated="2026-10-06T18:23+08:00">
- [user-role](user-role.md) — …
- [feedback-testing](feedback-testing.md) — …
</memory-index>

6.2 正文召回：LLM 选，关键词兜底

1
扫描清单
读目录下 ≤200 个 .md 的 frontmatter（≤30 行/个），渲染 manifest： - [type] filename (mtime): description。空清单直接短路，不花调用。
2
side-query 选择
单次 Chat：system 为选择提示（"不确定就不选"；近期在用的工具不选其用法文档，但仍选其坑——抄 findRelevantMemories.ts 的区分规则），user 为 query + manifest，输出 JSON schema {selected: [filename]} ≤5。硬超时 3s。
3
降级链
超时/解析失败 → 关键词重叠（query 与 name+description 的词面交集）；清单 ≤N 小 ⇒ 也可直接跳过选择全部带上（Profile 配阈值，默认清单 ≤8 篇时全带）。
4
去重与限流
alreadySurfaced：本进程已注入且 mtime 未变的文件不再注——选择器的 5 个槽位留给新候选（CC 同款过滤）。命中文件读正文、按 §5.3 配额截断，拼 <memory> 块。
// user 消息尾部形态
{用户原文}

<attachments>…</attachments>        // 既有 @path 展开
<memory-index>…</memory-index>       // 仅在变化或丢失时出现
<memory name="feedback-testing" type="feedback">
正文（≤4KB）…
</memory>
为什么不用 embedding

文件上限 200 篇、manifest 总量 ≤25KB——向量检索在这个量级只增加依赖与模糊度，不增加命中率。LLM 直选还能用语言能力区分"工具用法文档"与"该工具的坑"这类语义差别（CC 选择提示里的真实失败案例）。向量检索留作清单超过千篇后的扩展缝。

第 7 章 · 写路径

显式直写 + 隐式提取，互为补位

用户说"记住这个"时模型立即直写；用户没明说但反复表达偏好时，后台提取兜底。两条路径写同一套文件，索引都由代码重建。

7.1 memory 工具：模型可见的写口

name: memory
description: Read and update the persistent memory store for this space.
  Save durable facts (op=save: name, type, description, body),
  remove stale ones (op=forget: name), or list the index (op=list).
  Memories persist across sessions — do not store ephemeral task state.
params:
  op:    save | forget | list
  name, type, description, body   # save 必填；forget 只要 name
  • 注册进 SafeTools：写面被工具实现封死在空间目录内，等价于 CC 的 isAutoMemPath carve-out，但更强——模型连路径都给不了。
  • 写后代码重建 MEMORY.md；工具的返回串固定为 saved: <file> / forgotten: <file>，不在返回里回填索引全文（省 token，模型可从 list 自取）。
  • Profile.WriteTool=false 时不注册——陪伴场景可选择"只由后台提取写"，模型不感知记忆的存在（人设更稳）。

7.2 后台提取：Stop hook + side-query

触发点在 OnStop——模型产出纯文本回复、本轮告一段落时。hook 返回 ""（不续跑），只起一个 goroutine：

func (m *Memory) extractAsync(ctx, history) {
    // WithoutCancel：取消停的是未来工作，提取是已发生对话的收尾——
    // 与 record() 落库同一口径（agent.go:461）。
    ctx = context.WithoutCancel(ctx)
    ctx, cancel := context.WithTimeout(ctx, 60*time.Second)
    defer cancel()
    // 单飞：inFlight 标志位去重；本轮到达时已有提取在跑 → 标记 dirty，
    // 跑完接着跑一轮 trailing（CC pendingContext 同构，最多合并一轮）。
}
1
游标取增量
.state.json 存 {sessions: {<sid>: lastRowID}}。提取输入 = LoadRawHistory 中 id > lastRowID 的非控制行。读原始行而非视图：中段可能已被摘要， 原始行不受压缩影响；spill 过的工具结果只剩预览+指针，偏好类信号几乎都在 user/assistant 文本里，预览够用。渲染口径对齐 summary.go 的 renderEvent（inject 行标 harness notice）。
2
三道跳过闸
新行数 < MinNewRows；距上次提取不足 EveryTurns 轮；本批消息里主代理已调用过 memory 工具（hasMemoryWrites 同构：模型自己写了，后台不再重复）。命中即推游标返回。
3
提取调用
输入 = Profile 提取提示（Focus + 类型辞典 + DoNot + ops 格式）+ 已有清单（正文总量 ≤ BodyBudget 时连正文一起给，否则只给 manifest）+ 新行渲染。输出 JSON： [{op: upsert|delete, name, type, description, body}]。
4
落盘与熔断
ops 逐条校验（类型须在辞典内、slug 合法、delete 指向已存在文件）后写盘、重建索引、推游标。失败计 .state.json.extractFailures，连续 3 次熔断——与 compact 同一口径。成功后触发 OnChange(n) 回调，TUI 落一行提示；整理检查顺手跑（§8）。
提取提示骨架（以 coding profile 为例）

三段式：Focus（本 profile 该捕捉什么，一段散文）→ 类型辞典（逐类型的 save/use/structure，抄 TYPES_SECTION_INDIVIDUAL）→ 不存清单 + ops 契约（"没有新信息就返回 []"；已有清单前置给模型做去重）。写记忆的语言跟随对话语言。

7.3 journal 模式：长驻会话的追加日志

Mode=journal 时提取的产出形态换掉：ops 变为日志条目数组，代码追加到 logs/YYYY/MM/YYYY-MM-DD.md，不写主题文件、不动索引。索引由整理流程定期从日志蒸馏重建（§8）。 这是 CC KAIROS 的对应物，适合长期运行的陪伴/值守 agent——写入永远 append-only，模型不需要做"改哪篇文件"的决策。

第 8 章 · 整理

Dream：三门之后才动手

整理在提取完成后顺手检查，三门全开才执行（CC 四层门控裁剪掉多进程扫描节流——RH 单进程不需要）：

  1. 时间门：距上次整理 ≥24h（.consolidate.lock 的 mtime）。
  2. 物量门：索引条目 ≥30，或自上次整理以来新增/修改文件 ≥10。
  3. 锁门：无未过期锁文件（1h 过期抗崩溃；执行前先落锁）。

执行方式与提取同构——单次 side-query 输入全部 manifest + 正文（超预算时按 mtime 分批），输出 ops 数组（upsert/delete/merge-into），代码落盘重建索引、滚动锁 mtime。失败回滚锁 mtime 让时间门下次重新放行；连续失败同样熔断。

注意 · 整理的对象按模式区分

indexed 模式整理主题文件：去重、合并矛盾、淘汰过时条目。journal 模式整理日志：把日志蒸馏成主题文件 + 重建 MEMORY.md——蒸馏完的日志段可截断，原始行保留在文件里。

第 9 章 · 内置 Profile

两个内置画像：coding 与 companion

9.1 coding：记工程经验

类型辞典直接沿用 CC 四类与 eval 校准过的文案：

type 回答什么 示例
user 用户是谁：角色、目标、知识背景 "十年 Go，第一次碰 React——前端解释用后端类比"
feedback 怎么做事：纠正与被验证的做法，含 why "别 mock 数据库——上季度被坑过"
project 正在发生什么：代码与 git 推不出的动机、期限、干系人 "auth 重写是合规驱动"（相对日期一律转绝对日期）
reference 东西在哪找：外部系统指针 "pipeline bug 都在 Linear INGEST"

DoNot 照抄 WHAT_NOT_TO_SAVE_SECTION：代码模式、架构、git 历史、修法、CLAUDE.md 已有内容、临时任务状态——能从当前项目状态推导的一律不存，即使用户显式要求（此时追问"这里面非显然的部分是什么"）。

9.2 companion：记人

类型辞典换成面向"人"的四类，Focus 指向情绪与关系线索：

type 回答什么 示例
persona 用户是谁：身份、经历、处境、在意的东西 "用户是初三学生的家长，孩子今年中考——谈学习计划时多从这个身份出发"
bond 我们共同经历过什么：事件、约定、梗、关系进展 "2026-09 一起完成了第一次长途徒步，用户称其为'雪山之行'"

  • Focus：情绪变化（"今天语气明显低落"）、人称细节（家人/同事的名字与关系）、未兑现的承诺与约定、 表达习惯的纠正。
  • DoNot：一次性寒暄与流水账、能从前几轮对话直接看出的即时状态、任何用户标了"别记"的内容。

第 11 章 · 边界

记忆与压缩各管一段，互不读写对方状态

压缩（internal/compact） 记忆（internal/memory）
管什么 本会话的发送形态：卸载、摘要、熔断 跨会话的知识：偏好、事实、指针
存哪 session.Store：消息行、控制行、blob、session_state 文件系统：空间目录
谁写 循环内 Maintain/Compact/Backfill 模型（memory 工具）+ Stop hook goroutine
谁读 Fold 组装视图 OnUserPromptSubmit 拼进 user 消息
读对方吗 不读记忆——压缩只动消息行 不读压缩状态——提取走 LoadRawHistory 原始行，天然越过折叠

两个交互点都已确认无害：

  • 提取落在压缩之后：提取读原始行，视图折叠与否不影响输入；游标按原始行 id 记，压缩不产生新行 id 之外的洞。
  • blob 指针：原始行里的 <persisted-output src="blob://…"> 只给预览进提取输入； 提取目标是偏好与事实，不依赖工具输出全文。确需全文时提取提示允许模型放弃该条线索（不读 blob——提取无权访问存储面）。
第 12 章 · 安全与隐私

写面封死在空间内，隔离靠 scope 不靠参数

  • 写面：memory 工具与提取代码只允许写空间目录内 <slug>.md； slug 清洗去 ../分隔符/保留名；目录 0700、文件 0600。
  • 隔离：空间键全部从 ctx scope 派生（tenant/subject/workspace），模型参数里没有空间字段——跨租户读写在参数层不存在。
  • 不存凭据：所有 Profile 的 DoNot 固定含一条"密钥、凭据、token 一律不存"；提取提示复述这条。
  • 遗忘权：用户说"忘掉 X"时模型用 op=forget 立即删；陪伴场景还要求提取提示复述"用户标了别记的内容不进记忆"。
  • 索引不泄密：索引描述行是模型可见文本，提取提示要求 description 只写主题不写敏感值。
警告 · 云端部署的敏感面

陪伴/专家场景的记忆本质是用户画像——属于个人数据。云端落地时：文件后端挂每租户隔离的卷或对象存储前缀； 提取产物跨会话可见，必须保证 SubjectID 注入正确——错一次就是画像串号。上线前建议把 "提取输入不跨 subject"写进审计清单。

第 15 章 · 未决事项

留给第二个真实用例的四件事

  • 提取器升级为迷你 agent：side-query 无法"读已有正文再合并"（现靠 BodyBudget 前置正文缓解）。 若 ops 质量问题真实出现，换成 agent.New + 受限注册表（read_file + memory）跑读写循环—— hook、游标、ops 契约不变。
  • 文件后端可换：云端形态若不用本地盘，定义 memory.FS 接口（read/write/list/stat）接对象存储即可——本方案已把所有 I/O 收进 internal/memory 内部。
  • 多层空间：private + team 双目录（CC TEAMMEM）有真实多用户需求时再加；届时 Space 从单值变 []Space，索引渲染两段式，类型辞典加 <scope> 标签——文案在 CC 源码里是现成的。
  • session memory：CC 用每会话 memory.md 替代摘要调用来省一次 LLM 请求。RH 压缩已走滚动摘要且成本可控；若侧重回撤质量可考虑，属独立增量。
