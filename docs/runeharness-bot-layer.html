代码解析 · RUNEBOT / GATEWAY / RUNNER

Bot 层解析：同一内核的 headless 网关形态

cmd/runebot 把同一套内核（agent / tools / permission / compact / memory / cron）装配成无 TUI 的常驻进程。与 CLI 的差异只在三处： 接入面（WS + HTTP 两条轨）、每 chat 一个的执行槽位、权限确认的应答路由。 本文覆盖：文件与职责、组件总览、一条消息的完整调用链、槽位状态机、下行事件账本。

范围：cmd/runebot · internal/gateway · internal/runner 基线：go 1.2x · OpenAI 兼容端点 · SQLite · coder/websocket 配套：runeharness-api.html · runeharness-gateway-plan.html · runeharness-architecture.html

第 1 章 · 定位与文件清单

Bot 层 = 一层装配 + 两个新包

入口是 cmd/runebot/main.go（382 行）。它只做装配， 不含业务逻辑——把 internal/* 串成一个常驻 HTTP 进程。 真正的新代码是两个包：internal/gateway（接入面）与 internal/runner（执行面），合计约 2400 行。

与 CLI 的对照（同一内核，两套前端）：

维度 CLI（main.go + internal/tui） Bot（cmd/runebot）
会话数 一进程一会话 N 个 chat → N 个 slot
事件出口 Program.Send → Bubble Tea emit → 每 chat 事件账本 → WS/SSE/NDJSON
权限确认 TUI 弹窗 ask 事件挂起 → 客户端 answer 帧 / POST /actions
bg/cron 交付 TUI 空闲时 drain 注入当前会话 cron 写通知 outbox（App 轮询）+ pending 队列在下一轮注入
system prompt prompt.Build（coding agent 身份） prompt.BuildBot（SOUL 人设即身份）
会话标题 手动 OnTurnComplete → naming 自动命名

第 2 章 · 架构总览

三条竖向分层 + 右侧持久层 + 旁路组件

箭头方向是"数据/调用流向"。三个虚线框是包边界； 右列是进程唯一持久层；左列是旁挂组件。

三层边界各自只说一种话：gateway 只见 ChatKey+TurnInput，runner 只见 TurnRunner，agent 只见 history+hooks
设计 接口而不是耦合：三层各自只认一种抽象

gateway 不碰 agent。它只把 HTTP/WS 帧翻译成 ChatKey{tenant, channel, chatID, subject} 加 TurnInput{prompt, attachments}，调 Manager.Submit / Interrupt / Answer / Subscribe。

runner 不碰 HTTP。slot 只认 TurnRunner 函数签名与 emit/ask 两个回调——TUI 若要复用同一执行层，换一个 Harness 实现即可。

agent 不碰渠道。循环内只触发五类 hook 与四个回调 （OnPartial/OnToolCall/OnToolResult/OnInject）；bot 特有的事 （事件账本、权限路由、bg/cron drain）全部在装配层经回调挂进去。

第 3 章 · 调用链

一条消息从进来到回答：先订阅，再提交，逐行落库

以 POST /v1/chats/{id}/stream 为例（WS message 帧同路径， 只是应答出口不同）。订阅先于提交——本轮事件必然落在订阅窗口内。

时序压缩了三处展开：工具批（逐个 hook+执行）、ask 回路（事件挂起→客户端应答）、loop 出口（stop → turn_end）
1
鉴权与寻址
claims() 把 Bearer token 解析成 {tenant, subject}； chatKey() 拼上渠道名与路径里的 chatID，得到槽位键 ChatKey{tenant, "bear", chatID, subject}。 subject 进 ChatKey——session.subject_id 与记忆空间归属全靠它。 gateway.go:163-183
2
先订阅后提交（/stream 特有）
SubscribeLive 只转发订阅建立后的事件、不回放存量—— 避免在旧轮的 turn_end 处提前收流。随后 Submit， 首个 turn_start 锚定本轮 turn_id，其余轮次事件不转发。 handlers.go:450-526 · slot.go:392-419
3
Submit → slotFor 惰性建槽
首条消息走慢路径：GetBinding 查 chat_bindings， 未命中则 CreateSession + UpsertBinding， 命中则 LoadHistory 载入视图；然后 newSlot 调 Harness.New 装配 agent。槽位 ctx 独立于请求 ctx——HTTP 响应结束不杀槽位。 忙时 QueueDepth=0 直接返回 BusyError（HTTP 409 / WS error 帧 / stream 内联 error）。 slot.go:281-307, 435-495
4
runTurn：记账 → 落库 → 跑轮
turnSeq+1 → 发 turn_start → user 消息先 Append 落库再进 history → 调 TurnRunner。包装层做三件事：剥掉上轮挂的旧 system（保证恰好一份）、 触发 UserPromptSubmit 钩子链（todos 轮次归零 + 记忆首条注入）、 挂 BuildBot system。AgentHarness 再检查 bg/cron 队列， 有则先注入 KindInject 消息，最后才进 a.Run。 slot.go:115-165 · main.go:299-315 · harness.go:52-92
5
agent.Run 循环（内核，与 CLI 同构）
每 step：PreChat 钩子（breaker nag / bg drain / 压缩提醒 / todo nag）→ Compactor.Maintain → llm.Chat 流式（ OnPartial→delta 事件）→ push assistant → 有 tool_calls 则逐个 PreToolUse（permission 三道闸，判 Ask 时经 slot 的 routeAsk 挂起等客户端）→ Registry.Call → PostToolUse → Backfill（超限结果落 blob）→ push 结果 → 下一步。上下文超限做一次 reactive 压缩重试。 agent.go:177-385
6
turn_end + 异步命名
终态（completed / interrupted / error）写 turn_end 控制行并发事件； /stream 在此关流。status=completed 时 OnTurnComplete 异步触发 namer.NameChat——取首轮 user+assistant 各 500 字做一次性 completion， ≤12 字写回 sessions.title；已是非默认标题则跳过。 slot.go:168-200 · naming.go:67-111
ask 回路（图里虚线支路）

permission 判 Ask → slot routeAsk 发 ask 事件（含 ask_id、tool_call、seq/total）、 登记 pendingAsk、挂 120s 超时 → 客户端经 WS answer 帧或 POST /actions {type:"answer"} 应答 → Mgr.Answer → resolveAsk 写回 reply channel。三条兜底：客户端 answer、 120s 超时 deny、slotCtx 取消 deny。AskTimeout 默认 120s。 slot.go:232-277, 330-348 · handlers.go:199-238 · ws.go:117-129

第 4 章 · 槽位与轮次状态

槽位状态极简：空闲 ⇄ 轮次中，ask 是轮次内的挂起子态

并发语义全部收敛在 slot.mu 一把锁里： busy 标志认领轮链、queue 缓冲排队、 pendingAsk 单槽挂起、cancel 持有当前轮取消。

锁内三元组：busy 认领、queue 排空、pendingAsk 挂起——竞态只在 Submit/Interrupt/Answer 三个入口收敛
并发 为什么轮间取队列和释放 busy 在同一把锁内

Submit 见 busy=true 而入队成功，那条消息会不会没人收？

不会。runChain 每轮跑完在锁内做"取 queue → 空则 busy=false"； Submit 在锁内做"见 busy → 尝试入队"。两个检查互斥： 要么入队先于排空检查（消息必然被取走），要么排空先完成（Submit 改走 "认领 busy + 起新链"分支）——消息不会留在无人收的 queue 里。 slot.go:94-110, 281-307

第 5 章 · 事件账本与下行轨

一份内存账本，三种消费方式

每个 chat 一个 Ledger：cap=2000 的 ring buffer， seq 会话内单调递增。Append 即广播； 慢消费者丢帧、靠 seq 间隙自检。账本不落盘——历史回放在 SQLite， 断线续传用 since 追增量。

事件只有一种载体：runner.Event{seq, event, turn_id, turn_seq, timestamp, data}——三条轨只是它的三种订阅姿势

事件目录（12 种）

事件 产生方 data 载荷 说明
turn_start slot.runTurn {turn_seq} 轮次开跑；/stream 用它锚定本轮 turn_id
delta OnPartial {thinking?, content?} 本轮累积快照（全量替换，不是增量）
reasoning_delta —（预留） — 常量已声明，当前无产出方
tool_call OnToolCall {id, name, arguments} 先于执行发射——被 hook 阻止的调用也可见
tool_result OnToolResult {id, output, is_error, blocked, duration_ms} blocked=true 表示被权限闸拦下未执行
inject OnInject {content} hook 注入消息（todo nag、压缩提醒、bg/cron 交付）
ask routeAsk {ask_id, call, reason, seq, total} 权限确认挂起；等 answer 或 120s 超时
interrupt Mgr.Interrupt {reason} 客户端 cancel 触发
turn_end finishTurn {status, turn_seq, duration_ms, usage?, error?} 轮次唯一终结信号；同内容落库为控制行
notification harness drain {kind: bg|cron, content?, count?} 旁路输入已注入本轮
reset ws attach（ErrLag） {reason} since 落后出窗；客户端应全量重拉
error gateway 各轨 {message} 请求级错误帧，不占账本 seq
第 6 章 · 旁路输入与守护组件

谁能在没有用户消息时开口，谁管收尾

6.1 cron：双写交付——outbox 通知 + pending 注入

bot 模式下 Scheduler.OnFire 做两件事，不是一件：

  • 通知 outbox：store.PushNotification(tenant, "cron", title, prompt) 落 notifications 表——App 轮询 GET /v1/notifications 弹窗， 不会唤醒空闲 chat（ALF-133）。
  • pending 队列：任务同时进调度器 pending， 由 AgentHarness 在某次轮次起跑前 Drain 出来、 过 UserPromptSubmit 钩子后注入为 KindInject 消息。
注意：Drain 队列是进程全局，不带会话归属

cron.Scheduler.pending 与 bgtask.Manager.pending 都是进程级队列。 多 chat 场景下，一条 bg/cron 通知会注入到"下一个跑轮的槽位"—— 不一定是发起任务的那个 chat。outbox 通知有 tenant 归属、无此问题； 会话内注入的归属语义目前是"先到先得"，不是定向投递。

6.2 bg 任务：两个挂点，同一队列

bgm.Drain() 挂在两处：turn 起跑前的 harness 轮间检查（注入成一轮的旁路信息）， 和 PreChat 钩子（轮次中途到达的通知在下个 step 注入）。 task_kill 置 notified 抑制完成通知；停滞看门狗发一次性提醒。 交付落库失败经 Requeue 归还队首——通知不丢。

6.3 memory：首条注入 + dream 后台消化

mem.InjectOnce 挂 UserPromptSubmit：每个会话的首条 user 消息 注入记忆索引与常驻正文（借 TurnRunner 包装层触发，bg 注入轮不触发）。 DreamTicker 按画像节奏跑、DreamOnExit 收尾兜底； dream 可换轻量模型（RUNE_MEMORY_MODEL）。 /v1/memory* 三个端点只是查看/手动触发口，Mem=nil 时 503。

6.4 naming：turn_end 的一次性收尾

mgr.OnTurnComplete 只在 status=completed 时异步触发—— interrupted/error 的残轮不构成"完整一轮"。命名脱离调用方生命周期 （自建 30s 超时 ctx），任何失败静默只打日志。

6.5 优雅退出

SIGINT/SIGTERM → httpSrv.Shutdown(5s) → bgm.Shutdown() （级联 SIGKILL 进程组）→ mem.DreamOnExit（若开 dream）。 槽位与账本是纯内存，进程退出即消失；重启后由首条消息惰性重建—— 历史从 SQLite 回载，但进行中的轮次不会续跑（见第 7 章）。

第 7 章 · 观察与风险

读代码时值得知道的七个事实

# 事实 影响 / 依据
1 runner.Config.DrainInterval（默认 3s）已定义但无消费者 死配置字段。注入实际是轮次边界驱动（harness 轮间 + PreChat），不是周期探。 runner.go:283-301
2 turn_end.status 协议含 crashed，DB 文档还提 maxsteps； 当前代码只写 completed | interrupted | error 进程崩溃的接管修复（Fold 补悬空 call + 补记 crashed）是 gateway-plan §5.2 的规划项，未落地；MaxStepsError 归并为 error。
3 bg/cron 的 pending 队列进程全局、无会话归属 多 chat 下通知落到"下一个跑轮的槽位"；cron 另有 outbox 通道兜底触达（见 6.1）。
4 槽位无空闲回收：slots map 常驻至进程退出 每槽含 history 全量视图 + 2000 容量账本；长进程+多 chat 会累积内存。 目前无 LRU/idle reaper。
5 忙时语义是"拒"，不是"排" QueueDepth=0：HTTP 409、WS error 帧、stream 内联 error。 串行责任在客户端（等 turn_end 再发下一条）——这是明确的协议边界。
6 槽位生命周期独立于请求 ctx slotFor 用 context.Background() 建槽； HTTP/WS 请求结束不会杀掉跑着的轮次。Interrupt 是唯一停轮手段。
7 附件三道轨同构校验，文档附件"失败不拒消息" ≤8 个、单个/合计 ≤220MB；PDF/Office 抽取失败降级为 "打不开"占位分片交给模型如实回答——只有 ctx 取消才返回错误。 docattach.go:44-69
一句话总结

Bot 层的全部新意是"把隐式的单会话前提显式化"：ChatKey 路由、每 chat 槽位、 事件账本、ask 回话通道。内核（agent loop、hooks、压缩、权限、记忆）一行未改—— 这验证了"装配层"这条架构线的成立。
