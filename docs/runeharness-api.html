接口契约 · RuneHarness API

外部接入 API 设计

runebot 对外暴露的完整接口面：一条 WS 轨（兼容 bigbigbear 现有协议）、 一条 HTTP/SSE 轨（fetch + ReadableStream 消费）、一组只读查询端点。 契约先行——三条轨共享同一个 (chat_id, seq) 事件账本，客户端任选其一接入。

版本 v1.0 草案 状态：设计，未实现 依赖：docs/runeharness-gateway-plan.html（账本与槽位） 首个消费者：Bear APP（WS 轨）
怎么读
  1. 接入方 → 第 1 章（概念）+ 第 2 章（鉴权）+ 所用轨的那一章。
  2. 实现方 → 第 6 章（事件 schema）+ 第 7 章（错误与边界）。
  3. 排障 → 第 8 章（部署与中间层要求）。
第 1 章 · 概念与不变量

三个资源，一个不变量

一句话：客户端永远只在跟 Chat 打交道——提交 Message、 订阅 Event 流、对 Ask 作答。所有事件按 seq 单调递增， 断线后带 since 续传是唯一的恢复机制。
资源标识说明
Chatchat_id（客户端给出，^[A-Za-z0-9_:-]{1,64}$） 一个外部对话。服务端把它映射到一条内部 session——这个映射对客户端不透明。
Message无独立 id（属轮次的一部分） 一次用户输入。异步处理：submit 返回 ≠ 回复开始。
Eventseq（每 chat 递增） 轮次的全部外部可见事实：delta、tool_call、tool_result、inject、ask、turn_end、reset。
Askask_id 权限询问。60 秒无应答按 deny 处理。

1.1 会话的语义边界

chat_id 是客户端拥有的标识——同一个客户端可以在同一 WS 连接上 attach 多个 chat，也可以用同一 chat_id 跨连接续传。服务端不创建 chat： 第一个 attach 或 message 到来时惰性建立映射。

场景 为什么 chat_id 由客户端给，不由服务端发

因为"哪个会话"是客户端的上下文：APP 的一个聊天页、QQ 的一个会话、 一个 cron 触发的定时对话，都是客户端自己知道边界的。 服务端发 id 会逼客户端先等握手再渲染——bigbigbear 的 ready → attach 两步协议就是这个顺序。

1.2 两条轨的等价性

WS 与 SSE/fetch 在语义上完全等价，只是帧格式不同：

操作WS 轨SSE/HTTP 轨
提交消息{"type":"message"}POST /v1/chats/{id}/messages
订阅事件{"type":"attach"}GET /v1/chats/{id}/events
断线续传attach 带 sinceLast-Event-ID 头
中断轮次{"type":"cancel"}POST /v1/chats/{id}/actions {"type":"cancel"}
应答权限{"type":"answer"}POST /v1/chats/{id}/actions {"type":"answer"}
历史读取同连接 {"type":"history"} 或走 HTTPGET /v1/chats/{id}/history

客户端选轨的标准不是功能，是连接形态：要一条全双工连接选 WS， 要"普通 HTTP 请求"的简单心智选 SSE。两条轨可以并存于同一个部署。

第 2 章 · 鉴权与租户

Bearer token 一把梭，v1 不引入签发体系

第一阶段沿用 bigbigbear 的静态 token 模型：部署方在服务端配置 一组 token → {tenant, subject} 的映射。每个 token 是一个身份， 不做用户表、不做过期轮换、不做 scope 细分。

# runebot 配置（服务端持有）
tokens:
  "tok_8f2a…": { tenant: "local", subject: "ray" }
  "tok_b71c…": { tenant: "local", subject: "bear-admin" }
  • WS 轨：?token=<tok> 查询参数（兼容 bigbigbear 现状）。握手时校验， 失败回 401 或 403，不升级。
  • HTTP 轨：Authorization: Bearer <tok>。三个读端点之外全部要鉴权。
  • 租户推导：token → scope.Scope{TenantID, SubjectID} 由网关注入 ctx； 工具与模型参数永远接触不到 tenant。
单用户的边界

v1 假设"token 持有者即本人"。多用户接入（群聊、共享 bot）需要把 subject 细化为"token + 消息来源用户"的复合键，以及按 sender 隔离会话——这是 v2 的事，本版接口为此预留了 sender_id 字段位。

2.1 速率与资源限制

限制值理由
单 token 并发 WS 连接8防端口耗尽；正常客户端 1–2 条足够
message 频率每 chat 串行入队，无并发轮次轮次本来就串行，第二条自动排队
单条消息大小32 KB对齐 read_file 单文件上限；超限 413
SSE/WS 空闲超时无（服务端 ping 每 20 秒）心跳是中间层要求，不是业务超时
ask 应答窗口60 秒超时按 deny，见中断矩阵 S3
第 3 章 · WS 轨（bigbigbear 兼容）

协议面与 nanobot 逐字段对齐

端点 wss://bear.alfred-develop.online/?client_id=<id>&token=<tok>。 实现目标是：现有 Bear APP 不改一行代码即可连上 runebot。

3.1 连接生命周期

1
握手
校验 token。失败：401（无效）/403（不在 allow_from）。
2
服务端首发 ready
{"event":"ready","chat_id":"<uuid>","client_id":"…"}——chat_id 是服务端默认生成的值，客户端可换成自己的。
3
客户端 attach 订阅
{"type":"attach","chat_id":"…","since":<int>}（since 为新增可选字段）。回 {"event":"attached","chat_id":"…"}。
4
正常收发
message → delta 流 → turn_end；期间可有 tool_call/ask。
5
断开
服务端 ping 每 20s；客户端超时未 pong 则判定断开，重连后带 since attach 续传。

3.2 命令帧（客户端 → 服务端）

type字段语义对应内部动作
attachchat_id · since? 订阅该 chat 的出站事件Subscribe(chat, since)
detachchat_id 取消订阅（不关连接）从 subscribers 摘除
messagechat_id · content · client_msg_id? 提交一轮输入Enqueue(chat, content)
cancelchat_id 中断当前轮Interrupt(chat)
answerchat_id · ask_id · allow 应答权限询问写 pendingAsk reply channel
ping— 应用层心跳（可选）回 pong

3.3 事件帧（服务端 → 客户端）

event何时出现关键字段
ready握手成功即推chat_id · client_id
attachedattach 成功chat_id · synced_seq
delta流式正文seq · chat_id · text（增量）
reasoning_delta推理模型思考链seq · chat_id · text
tool_call模型请求工具seq · chat_id · name · args_preview
tool_result工具返回seq · chat_id · ok · dur_ms · summary
ask权限询问seq · chat_id · ask_id · tool · reason · ttl_ms
injecthook 注入（nag/bg/cron 通知）seq · chat_id · content · source
stream_end一段输出结束（非轮次结束）seq · chat_id · text?
turn_end一轮真正结束seq · chat_id · turn_id · status
resetsince 越界 / 服务端重启seq · chat_id · reason
error协议级错误code · message · chat_id?

turn_end.status 取值为 completed | interrupted | error | crashed | maxsteps。 stream_end 只标记"一段流结束"——一轮可以有多段（工具调用之间）， 客户端应以 turn_end 为轮次边界，与现有 APP 行为一致。

与 nanobot 的差异点

新增字段全部是 additive：since（attach 续传）、seq（所有事件帧）、 ask（权限询问，nanobot 没有）、inject（bg/cron 通知）。 未实现的旧字段（retry_status、goal_status）先不承诺， 等到有真实需求再补——协议面只加不减。

第 4 章 · SSE / HTTP 轨

普通 HTTP 语义，fetch + ReadableStream 消费

面向"不想维护 WS 连接"的客户端：Web 前端、小程序、脚本。 全部端点走 /v1 前缀，鉴权用 Authorization: Bearer。

POST /v1/chats/{chat_id}/messages

提交一条用户消息，异步触发一轮轮次。

请求体
{"content": "帮我看看这个函数的边界条件", "client_msg_id": "c-001"}
响应 202
{"chat_id": "main", "turn_id": "t_7f3a", "queued": false}

queued:true 表示该 chat 正有轮次在跑，本条排队。 client_msg_id 用于幂等去重（重发安全）。

错误
401 invalid_token · 413 content_too_large · 429 chat_flood
SSE /v1/chats/{chat_id}/events

订阅该 chat 的事件流。响应体是 text/event-stream， 与 WS 轨下发的是同一份账本事件。

请求头
Authorization: Bearer <tok>
Last-Event-ID: 141          # 可选；缺省从最新开始
响应
HTTP/1.1 200
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no       # 关 nginx 缓冲

: connected
id: 142
event: delta
data: {"chat_id":"main","text":"好的，我来看看"}

id: 143
event: tool_call
data: {"chat_id":"main","name":"read_file","args_preview":"…"}

: ping                     # 每 15–20s 一次注释帧心跳

id: 199
event: turn_end
data: {"chat_id":"main","turn_id":"t_7f3a","status":"completed"}
断线恢复

客户端断开后重发同一请求，带 Last-Event-ID: <seq>。 服务端从 seq+1 补发；游标已滚出窗口时先发一条 reset 事件再转实时。

POST /v1/chats/{chat_id}/actions

对当前轮次施加动作。SSE 是单向通道，上行控制全部走这里。

两种动作
{"type": "cancel"}                              # 中断当前轮
{"type": "answer", "ask_id": "a_9x", "allow": true}  # 权限应答
响应
200 {"ok": true}
409 {"error": {"code": "no_active_turn", "message": "…"}}
410 {"error": {"code": "ask_expired",  "message": "…"}}
GET /v1/chats/{chat_id}/history?limit=&before=

读消息历史（等价现有 /svc/history）。返回按轮次聚合的消息行， 不含 delta 等瞬态事件。

响应
{"chat_id": "main",
 "items": [{"i": 1042, "role": "user", "content": "…", "timestamp": 1760…},
            {"i": 1043, "role": "assistant", "content": "…", "timestamp": 1760…}],
 "has_more": true,
 "next_before": 1042}
GET /v1/chats

列当前 token 可见的 chat（按最近活跃排序）。用于"换设备继续聊"。

{"chats": [{"chat_id": "main", "title": "…", "last_active": 1760…, "has_pending": false}]}

4.1 为什么"提交"和"流"是两条端点

场景 能不能 POST /messages 直接返回流式响应？

可以，但不宜作为唯一形态。合一的形态下，客户端要先发请求才能拿到流， 这意味着没订阅的客户端看不到回复——后台通知、cron 触发的轮次就丢失了。 分开以后，events 是纯粹的订阅通道：任何时刻连上都能看到在跑的轮次， 这正是"账本与传输分离"的落地形态。

第 5 章 · 只读端点（替代现有 sidecar）

历史与搜索并入 runebot，sidecar 退役

bigbigbear 现有的 /svc/history 与 /svc/search 由独立 Go sidecar 读 transcript jsonl 提供。接入 RuneHarness 后， 数据源换成 sqlite 会话库，这两个端点直接收编进 runebot 的 HTTP 面。

端点方法说明
/svc/history?limit=&before=GET 按绝对索引分页的消息历史（与现有 sidecar 返回形态兼容）
/svc/search?q=&limit=GET user/assistant 子串搜索，±80 字摘要（改查 messages.content）
/svc/healthGET 免鉴权健康检查：库可写、LLM 端点可达（探测不消耗配额）

迁移路径：sidecar 继续挂 RO 挂载读 sqlite（它与 runebot 共享同一文件， WAL 模式下多读安全）；或直接在 runebot 里实现这两个 handler。推荐后者—— 少一个进程，少一份清单。

第 6 章 · 事件 Schema 规范

所有轨共用的事件契约

JSON schema 是协议的真身。WS 帧与 SSE data: 行里的 JSON 负载使用同一套定义——下面是权威结构。

// 所有事件的公共信封
{
  "seq":      142,              // 每 chat 单调递增（含瞬态）
  "chat_id":  "main",
  "turn_id":  "t_7f3a",        // 该事件归属的轮次；跨轮次事件为空
  "event":    "delta",         // delta | reasoning_delta | tool_call | tool_result | inject | ask | stream_end | turn_end | reset | error
  "timestamp": 1760…,      // unix 毫秒；事件发生时刻
  "data":     { … }              // 事件专有载荷
}
eventdata 字段说明
deltatext本次增量正文（服务端把累积快照 diff 成增量）
reasoning_deltatext思考链增量
tool_callname · args_preview · call_id参数预览截断 200 字
tool_resultcall_id · ok · dur_ms · summary · blocked?summary 单行摘要
injectcontent · sourcesource: nag / compact / bg / cron / memory
askask_id · tool · reason · ttl_ms · depthdepth>0 表示来自子代理
stream_endtext?一段流结束；一轮可有多段
turn_endstatus · reason?轮次唯一终结信号
resetreason · synced_seq游标失效，客户端应全量刷新视图
errorcode · message协议错误（不入 turn）
幂等与顺序

seq 是唯一的排序与去重键。客户端应把 (chat_id, seq) 当主键处理；重复帧（重连补发重叠部分）按 seq 去重。 client_msg_id 只用于上行去重，不参与事件流。

第 7 章 · 错误与边界

错误只有两种形态：HTTP 状态码和 error 事件

场景WSHTTP
鉴权失败握手 401/403401
chat 不存在（且非 attach/message 首发）error{code:"unknown_chat"}404
消息过大 / 队列满error{code:"too_large"|"queue_full"}413 / 429
无活跃轮次时发 cancelerror{code:"no_active_turn"}409
ask 已过期 / ask_id 错error{code:"ask_expired"}410
轮次内 LLM/工具失败不是协议错误——走 turn_end{status:"error"} + 错误详情进对话
服务端重启中连接断开，重连后收 reset503 + Retry-After

设计原则：业务失败不是协议失败。模型报错、工具被拒、轮次被中断， 都是对话内容的一部分，走事件流和 turn_end 状态；协议错误只覆盖 "这个请求本身无法受理"的情况。

第 8 章 · 部署与中间层

单端口 + 路径分流，k3s 现状兼容

# ingress 路由（host: bear.alfred-develop.online）
/          → runebot :8765   # WS 升级（bigbigbear APP）
/v1/       → runebot :8765   # HTTP + SSE
/svc/      → runebot :8765   # 只读端点（替代 sidecar）
  • SSE 应关缓冲：nginx-ingress 加 proxy_buffering off、 proxy_http_version 1.1、proxy_read_timeout 1h。
  • CF→origin：TLS 沿用现状；WS 的 20s ping 防 CF 空闲掐线。
  • pod 即边界：L2 profile 的 run_command 落在 per-session workspace PVC；pod 文件系统是可写层，崩坏不影响宿主。
