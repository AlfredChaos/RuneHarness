接口契约 · RuneHarness API

外部接入 API 设计

runebot 对外暴露的完整接口面：一条 WS 轨（兼容 bigbigbear 现有协议）、 一条 HTTP/SSE 轨（fetch + ReadableStream 消费）、一组只读查询端点。 契约先行——三条轨共享同一个 (chat_id, seq) 事件账本，客户端任选其一接入。

版本 v1.0 草案 状态：设计，未实现 依赖：docs/runeharness-gateway-plan.html（账本与槽位） 首个消费者：Bear APP（WS 轨）
怎么读
  1. 接入方 → 第 1 章（概念）+ 第 2 章（鉴权）+ 所用轨的那一章。
  2. 实现方 → 第 6 章（事件 schema）+ 第 7 章（错误与边界）。

第 1 章 · 概念与不变量

三个资源，一个不变量

一句话：客户端永远只在跟 Chat 打交道——提交 Message、 订阅 Event 流、对 Ask 作答。所有事件按 seq 单调递增， 断线后带 since 续传是唯一的恢复机制。
资源标识说明
Chatchat_id（客户端给出，^[A-Za-z0-9_:-]{1,64}$） 一个外部对话。服务端把它映射到一条内部 session——这个映射对客户端不透明。
Message无独立 id（属轮次的一部分） 一次用户输入。异步处理：submit 返回 ≠ 回复开始。
Eventseq（每 chat 递增） 轮次的全部外部可见事实：delta、tool_call、tool_result、inject、ask、turn_end、reset。
Askask_id 权限询问。60 秒无应答按 deny 处理。

1.1 会话的语义边界

chat_id 是客户端拥有的标识——同一个客户端可以在同一 WS 连接上 attach 多个 chat，也可以用同一 chat_id 跨连接续传。服务端不创建 chat： 第一个 attach 或 message 到来时惰性建立映射。

场景 为什么 chat_id 由客户端给，不由服务端发

因为"哪个会话"是客户端的上下文：APP 的一个聊天页、QQ 的一个会话、 一个 cron 触发的定时对话，都是客户端自己知道边界的。 服务端发 id 会逼客户端先等握手再渲染——bigbigbear 的 ready → attach 两步协议就是这个顺序。

1.2 两条轨的等价性

WS 与 SSE/fetch 在语义上完全等价，只是帧格式不同：

操作WS 轨SSE/HTTP 轨
提交消息{"type":"message"}POST /v1/chats/{id}/messages
订阅事件{"type":"attach"}GET /v1/chats/{id}/events
断线续传attach 带 sinceLast-Event-ID 头
中断轮次{"type":"cancel"}POST /v1/chats/{id}/actions {"type":"cancel"}
应答权限{"type":"answer"}POST /v1/chats/{id}/actions {"type":"answer"}
历史读取同连接 {"type":"history"} 或走 HTTPGET /v1/chats/{id}/history

客户端选轨的标准不是功能，是连接形态：要一条全双工连接选 WS， 要"普通 HTTP 请求"的简单心智选 SSE。两条轨可以并存于同一个部署。

第 2 章 · 鉴权与租户

Bearer token 一把梭，v1 不引入签发体系

第一阶段沿用 bigbigbear 的静态 token 模型：部署方在服务端配置 一组 token → {tenant, subject} 的映射。每个 token 是一个身份， 不做用户表、不做过期轮换、不做 scope 细分。

# runebot 配置（服务端持有）
tokens:
  "tok_8f2a…": { tenant: "local", subject: "ray" }
  "tok_b71c…": { tenant: "local", subject: "bear-admin" }
  • WS 轨：Authorization: Bearer <tok> 请求头（升级前校验）。 失败回 HTTP 401，不升级。
  • HTTP 轨：Authorization: Bearer <tok>。三个读端点之外全部要鉴权。
  • 租户推导：token → scope.Scope{TenantID, SubjectID} 由网关注入 ctx； 工具与模型参数永远接触不到 tenant。
单用户的边界

v1 假设"token 持有者即本人"。多用户接入（群聊、共享 bot）需要把 subject 细化为"token + 消息来源用户"的复合键，以及按 sender 隔离会话——这是 v2 的事，本版接口为此预留了 sender_id 字段位。

2.1 速率与资源限制

限制值理由
单 token 并发 WS 连接未限制v1 未实现连接数上限
message 频率每 chat 串行，忙时拒绝服务端不吞积压（HTTP 409 / WS 忙帧），客户端自行串行
单条消息大小未限制v1 未做大小校验
SSE/WS 空闲超时无；SSE 每 20s 一个 : ping 注释帧，WS 无服务端心跳（预留）心跳是中间层要求，不是业务超时
ask 应答窗口60 秒超时按 deny，见中断矩阵 S3
第 3 章 · WS 轨

一条连接多路 chat：type 帧控制，账本事件原样透传

端点 ws(s)://<host>/ws（coder/websocket 实现，internal/gateway/ws.go）。 升级前用 Authorization: Bearer <tok> 请求头鉴权，失败回 HTTP 401、不升级。 一条连接可同时订阅多个 chat：协议帧自带 chat_id，客户端据此多路分发。

3.1 连接生命周期

1
握手
Authorization: Bearer 校验。失败：HTTP 401，连接不建立。
2
服务端首发 ready
{"type":"ready","timestamp":<unix ms>}——首帧不必等 ready，任一客户端帧均可起手。
3
客户端 attach 订阅
{"type":"attach","chat_id":"…","since":<int>}。回 {"type":"attached","chat_id":"…","latest_seq":<int>}；chat 未绑定则惰性建立。同 chat 重复 attach 只保留最新一泵。
4
正常收发
message → ack；随后账本事件按信封原样下发（含 seq/chat_id/turn_id/turn_seq），直到 turn_end；期间可有 tool_call/ask。
5
断开
服务端无 keepalive ping（预留未实现）；需要心跳用应用层 ping→pong。断线无服务端状态要清，重连后带 since attach 续传。

3.2 命令帧（客户端 → 服务端）

type字段语义成功回帧
attachchat_id · since? 订阅该 chat 事件（since 断线续传；越界先回 reset 帧）attached{latest_seq}
detachchat_id 取消订阅（不关连接）—
messagechat_id · content 提交一轮输入ack；忙时 error{code:409,"chat is busy"}
cancelchat_id 中断当前轮—（随后 interrupt + turn_end 事件）
answerchat_id · ask_id · approved(bool) 应答权限询问—；ask 不存在/已应答回 error{code:404}
historychat_id · before? · limit? · req_id? 拉一页历史（limit 缺省/越界钳到 50，上限 200）history{req_id,items,has_more,next_before}
ping— 应用层心跳（可选）pong{timestamp}

未知 type 或坏 JSON 回协议错误帧 {"type":"error","message":…}（无 code、无 chat_id），连接不断。

3.3 下行帧（服务端 → 客户端）：两个家族

下行分两类，客户端按有无 type 字段区分：

家族形态说明
账本事件 {seq, chat_id, turn_id, turn_seq, timestamp, event, data}——信封原样转发 event ∈ delta · reasoning_delta · tool_call · tool_result · inject · ask · interrupt · turn_start · turn_end · reset · error · notification；载荷见第 6 章
协议帧 {"type": …} + chat_id ready · attached · ack · pong · history · error——连接级控制与命令应答；下行单写者串行，写超时 5s

特殊情况：attach 的 since 已跌出保留窗口时，先回 {"type":"event","chat_id":"…","event":"reset","data":{"reason":"seq_fell_behind"}}， 客户端应全量刷新视图后重新 attach。

turn_end.data.status 取值为 completed | interrupted | error | crashed， 并携带 turn_seq 与 duration_ms——它是轮次唯一终结信号。

与旧草案（bigbigbear 对齐版）的差异

鉴权走 Authorization 头而非 ?token=； ready 不再携带服务端生成的 chat_id/client_id—— chat_id 永远由客户端拥有；事件帧即账本信封（event + data）， 旧草案的扁平 text 字段与 stream_end 事件不存在； reasoning_delta 已声明常量但当前无产出方（预留）。

第 4 章 · SSE / HTTP 轨

普通 HTTP 语义，fetch + ReadableStream 消费

面向"不想维护 WS 连接"的客户端：Web 前端、小程序、脚本。 全部端点走 /v1 前缀，鉴权用 Authorization: Bearer。

POST /v1/chats/{chat_id}/messages

提交一条用户消息，异步触发一轮轮次。忙时直接拒绝——服务端不吞积压，客户端自行串行。

请求体
{"content": "帮我看看这个函数的边界条件"}
响应 202
{"status": "queued", "chat_id": "main"}

回复不在这条响应里——订阅 /events 收事件， 或改用下面的 /stream 一次请求收完本轮。

错误
400 bad_json / content 为空 · 401 token 缺失/无效 · 409 chat is busy（等 turn_end 后重试）
POST /v1/chats/{chat_id}/stream

提交消息并在同一次响应里收完本轮事件。响应体是 NDJSON （application/x-ndjson），每行一个账本事件信封——与 /events 同一份。

请求体
{"content": "帮我看看这个函数的边界条件"}
响应 200（帧序：turn_start → N×delta → turn_end）
{"seq":141,"chat_id":"main","turn_id":"t_7f3a","turn_seq":1,"event":"turn_start","timestamp":…,"data":{…}}
{"seq":142,…,"event":"delta","data":{"content":"好的，我来看"}}      # 累积快照，全量替换
{"seq":143,…,"event":"delta","data":{"content":"好的，我来看看这个"}} # 前缀一致累加
{"seq":144,…,"event":"turn_end","data":{"status":"completed","turn_seq":1,"duration_ms":3210}}

delta.data.content 是累积快照（不是增量块）； seq 每 chat 单调 +1；turn_end（status=completed， 带 turn_seq、duration_ms）关闭响应。 忙时不报 4xx：返回 200 + 单条内联 error 帧 （信封带 chat_id/turn_id，data.message 为 "chat is busy"）。 客户端中途断开不取消服务端轮次——本轮照常跑完并写入历史。

SSE /v1/chats/{chat_id}/events

订阅该 chat 的事件流。响应体是 text/event-stream， 与 WS 轨下发的是同一份账本事件。

请求头
Authorization: Bearer <tok>
Last-Event-ID: 141          # 可选；缺省从最新开始
响应
HTTP/1.1 200
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no       # 关 nginx 缓冲

id: 142
event: delta
data: {"seq":142,"chat_id":"main","turn_id":"t_7f3a","turn_seq":1,"event":"delta","timestamp":…,"data":{"content":"好的，我来看看"}}

id: 143
event: tool_call
data: {"seq":143,…,"event":"tool_call","data":{"id":"c1","name":"read_file","arguments":"…"}}

: ping                     # 每 20s 一次注释帧心跳

id: 144
event: turn_end
data: {"seq":144,…,"event":"turn_end","data":{"status":"completed","turn_seq":1,"duration_ms":3210}}
断线恢复

客户端断开后重发同一请求，带 Last-Event-ID: <seq>。 服务端从 seq+1 补发；游标已滚出保留窗口时先发一条 reset 事件再转实时。

POST /v1/chats/{chat_id}/actions

对当前轮次施加动作。SSE 是单向通道，上行控制全部走这里。

两种动作
{"type": "cancel"}                                 # 中断当前轮
{"type": "answer", "ask_id": "a_9x", "approved": true} # 权限应答
响应
200 {"status": "interrupted"}
200 {"status": "answered"}

错误：400 未知动作/缺字段（answer 需要 ask_id + approved）、 404 ask 不存在或已应答、500 无可中断的活跃轮次。

GET /v1/chats/{chat_id}/history?limit=&before=

读消息历史（等价现有 /svc/history）。返回按轮次聚合的消息行， 不含 delta 等瞬态事件。

响应
{"chat_id": "main",
 "items": [{"i": 1042, "role": "user", "content": "…", "timestamp": 1760…},
            {"i": 1043, "role": "assistant", "content": "…", "timestamp": 1760…}],
 "has_more": true,
 "next_before": 1042}
GET /v1/chats

列当前 token 租户下的 chat 绑定。用于"换设备继续聊"。

{"chats": [{"chat_id": "main", "channel": "bear", "session_id": "…", "subject_id": "ray", "count": 12, "active": true, "last_active": 1760…}]}

空库返回 {"chats":[]}，不是 null。 count 是该会话非控制消息条数（与 /history 跳过的控制行口径一致），空会话为 0。

4.1 为什么"提交"和"流"是两条端点

场景 能不能 POST /messages 直接返回流式响应？

可以，但不宜作为唯一形态。合一的形态下，客户端要先发请求才能拿到流， 这意味着没订阅的客户端看不到回复——后台通知、cron 触发的轮次就丢失了。 分开以后，events 是纯粹的订阅通道：任何时刻连上都能看到在跑的轮次， 这正是"账本与传输分离"的落地形态。

4.2 附件字段（三条上行轨通用）/ Attachments

WS 的 message 帧、POST /messages、 POST /stream 三个上行入口都接受可选的 attachments 数组，与 content 并列；附件作为 user 消息的内容分片 （parts）随消息落库并参与本轮模型请求。

请求体（示例）
{"content": "帮我看看这张截图",
 "attachments": [{"kind": "image", "media_type": "image/png", "filename": "shot.png",
                  "data_b64": "<base64>", "detail": ""}]}
字段约束
kind必填，"image" 或 "document"（PDF）；其余值报 unsupported attachment kind
media_type必填，image 须以 image/ 为前缀；document 只认 application/pdf
filename可选展示名，≤255 字节
data_b64必填，标准 base64（不带 data: 前缀）；解码失败报 invalid base64 attachment
detail可选，仅 "" | auto | low | high；"default" 不存在（SDK 客户端侧校验会拒绝），其余值同样拒绝
数量与体积（解码后计）
单轮 ≤ 8 个附件 · 单个 ≤ 10MB · 合计 ≤ 30MB

校验在提交前完成：HTTP 轨直接 400（error.message 即上表原因），WS 轨回协议错误帧 {"type":"error","message":…}，连接不断。 超限错误文案：too many attachments / attachment too large / attachments too large overall。

附件分片随 user 消息持久化、随历史与 API 回传；面对纯文本模型时， 图片分片在发送形态里降级为占位文本 [image omitted: model is text-only]。

PDF 附件（kind=document）的服务端行为

服务端用 poppler 抽取 PDF 文字层：一个入站 PDF 展开成一个 document 分片 （抽出全文，按页标注）加零到若干 image 分片——只覆盖文字层不足或位图占比高 的页面（扫描件、截图型幻灯片）。纯文字 PDF 不产生图片。页数上限 40、 渲染上限 8 页/份、文字上限 8 万字符，超出在分片文字里如实标注。 加密/损坏/超时的 PDF 不会 400：消息照常入队，document 分片里带一条 「此文件打不开」的说明，由模型转告用户。PDF 原始二进制不入库。

第 5 章 · 只读端点（替代现有 sidecar）

历史与搜索并入 runebot，sidecar 退役

bigbigbear 现有的 /svc/history 与 /svc/search 由独立 Go sidecar 读 transcript jsonl 提供。接入 RuneHarness 后， 数据源换成 sqlite 会话库，这两个端点直接收编进 runebot 的 HTTP 面。

端点方法说明
/svc/history?limit=&before=GET 按绝对索引分页的消息历史（与现有 sidecar 返回形态兼容）
/svc/search?q=&limit=GET 501 占位——尚未实现，固定返回 svc/search not implemented
/svc/healthGET 免鉴权健康检查：库可写、LLM 端点可达（探测不消耗配额）

迁移路径：sidecar 继续挂 RO 挂载读 sqlite（它与 runebot 共享同一文件， WAL 模式下多读安全）；或直接在 runebot 里实现这两个 handler。推荐后者—— 少一个进程，少一份清单。

第 6 章 · 事件 Schema 规范

所有轨共用的事件契约

JSON schema 是协议的真身。WS 帧与 SSE data: 行里的 JSON 负载使用同一套定义——下面是权威结构。

// 所有事件的公共信封
{
  "seq":      142,              // 每 chat 单调递增（含瞬态）
  "chat_id":  "main",
  "turn_id":  "t_7f3a",        // 该事件归属的轮次；跨轮次事件为空
  "event":    "delta",         // delta | reasoning_delta | tool_call | tool_result | inject | ask | interrupt | turn_start | turn_end | reset | error | notification
  "timestamp": 1760…,      // unix 毫秒；事件发生时刻
  "data":     { … }              // 事件专有载荷
}
eventdata 字段说明
turn_startturn_seq · queued_from?轮次开跑（queued → running 每次 +1）
deltathinking? · content?本轮累积快照——全量替换，不是增量
reasoning_delta—思考链（常量已声明，当前无产出方——预留）
tool_callid · name · arguments一次工具调用分发
tool_resultid · output · is_error · blocked · duration_ms工具返回
askask_id · call · reason · seq · total权限确认挂起；60s 无应答按 deny
interruptreason?本轮被打断
injectcontenthook 注入的消息（todo nag、压缩提醒等）
notificationkind · task_id? · prompt?旁路输入已注入；kind: bg | cron | missed
turn_endstatus · turn_seq · duration_ms · usage? · error?轮次唯一终结信号；status: completed | interrupted | error | crashed
resetreason会话边界后移（压缩、seq 越界），since 前序作废，客户端应全量刷新视图
errormessage轮次内非致命异常
幂等与顺序

seq 是唯一的排序与去重键。客户端应把 (chat_id, seq) 当主键处理；重复帧（重连补发重叠部分）按 seq 去重。

第 7 章 · 错误与边界

错误只有两种形态：HTTP 状态码和 error 事件

场景WSHTTP
鉴权失败升级前 HTTP 401（连接不建立）401
chat 未绑定不是错误——attach/message 惰性建立绑定；history 返回空页，GET /chats/{id} 返回 200 + active 标记
chat 忙（队列满）error{code:409,"chat is busy"}/messages 409 · /stream 200 + 内联 error 帧
无活跃轮次时发 cancelerror 帧500
ask_id 错 / 已应答error{code:404}404
轮次内 LLM/工具失败不是协议错误——走 turn_end{status:"error"} + 错误详情进对话
服务端重启中连接断开，重连后收 reset503 + Retry-After

设计原则：业务失败不是协议失败。模型报错、工具被拒、轮次被中断， 都是对话内容的一部分，走事件流和 turn_end 状态；协议错误只覆盖 "这个请求本身无法受理"的情况。

第 8 章 · 部署与中间层

单端口 + 路径分流，k3s 现状兼容

# ingress 路由（host: bear.alfred-develop.online）
/          → runebot :8765   # WS 升级（bigbigbear APP）
/v1/       → runebot :8765   # HTTP + SSE
/svc/      → runebot :8765   # 只读端点（替代 sidecar）
  • SSE 应关缓冲：nginx-ingress 加 proxy_buffering off、 proxy_http_version 1.1、proxy_read_timeout 1h。
  • CF→origin：TLS 沿用现状；WS 无服务端心跳——中间层空闲超时调大，或靠客户端应用层 ping。
  • pod 即边界：L2 profile 的 run_command 落在 per-session workspace PVC；pod 文件系统是可写层，崩坏不影响宿主。
验收清单

① WS 客户端按第 3 章协议完成 ready→attach→message→turn_end 闭环；② curl 起 SSE 流看到 delta→tool_call→turn_end 完整序列；③ Last-Event-ID 续传不丢不重； ④ POST /actions cancel 后 turn_end{status:"interrupted"} 出现； ⑤ ask 60s 无应答自动 deny，轮次继续。
