存储

记忆放哪

D1统一 DB，不落文件user

选定
~/.rune/memory.db（SQLite）。云端换 memory.Store 的 Postgres 实现。接口签名里没有路径和租户参数，空间键从 ctx 的 scope 派生。
否掉
Markdown 文件目录（CC 形态）。本地固然能读能改能 grep，但云端多租户下进程盘既不隔离也不持久； read_file 不限路径，文件形态本身就是越界口。
代价
用户不能拿编辑器直接改记忆。由 /memory 命令和 memory 工具的 list/read/forget 补读写口。
反悔条件
出现"用户手写/批量导入记忆文件"的真实需求时，可加一个文件后端实现 Store，或做导入导出工具。

D2独立库文件，不复用 sessions.db分析

选定
memory.db 与 sessions.db 分文件、分连接。
否掉
共享连接：要把 *sql.DB 漏出 session.Store 接口。各自连接同写一库：两个包的 schema 迁移在同一文件里纠缠。
代价
~/.rune/ 下多一个文件；备份要备两份。
反悔条件
若部署方明确要求单文件管理，装配层改一行即可，schema 本身不冲突。

D3索引不落盘，是查询渲染的文本分析

选定
索引 = SELECT name,type,descr 渲染出的文本块，随注入进消息。
否掉
维护一份 MEMORY.md 文件（CC 形态）。DB 形态下它是多余的第二份事实，还要处理与表的一致性。
代价
索引只能整体重算，不能局部追加——百行量级下无关紧要。
反悔条件
记忆规模大到索引渲染成瓶颈时再说，预计不会发生。

记忆怎么进上下文

D4启动注入第一条 user 消息，借 Fold 首部常驻user

选定
本会话第一条 user 消息附加 <memory-index> + AlwaysInject 类型的正文。Fold 首部永远保留前 3 条 user 消息，所以一次注入全程在场，压缩也甩不掉。
否掉
每轮注入（膨胀）；每轮 side-query 选正文（CC 做法，多一次每轮 LLM 调用）。
代价
首部是快照会旧：dream 改了记忆后首部不更新。缓解：dream 后下一条 user 消息重注带时间戳的新索引，模型以最新份为准。非常驻类型的正文要模型主动 op=read 取，有"该翻不翻"的风险。
反悔条件
"该翻不翻"成为真实失败案例时，加回每轮 side-query 选择，挂同一个 OnUserPromptSubmit hook，不动存储。
写路径

记忆怎么产生

D5dream 是唯一提取入口，消化全部未消化行user

选定
/dream 三触发器：手动命令、进程内 ticker（10–15 分钟空转检查）、正常退出收尾一次。dream 按会话水位消化本空间所有未消化行，不只当前会话。
否掉
每轮 OnStop 后台提取（CC 做法）：LLM 调用次数多一个量级；"只消化当前会话"：进程被 kill 或用户从不触发时记忆永久丢失——水位模式把丢失面缩到零。
代价
记忆延迟 = dream 间隔（coding 60min，companion 120min）或会话结束。user 显式"记住 X"的即时性由 memory 工具兜住。
反悔条件
若"隐式偏好要立刻生效"成为真实需求，加回每轮提取；或加"未消化行 >N 直接触发"的事件驱动触发器。

D6提取用 side-query，不用 forked agent分析

选定
一次 Chat：画像提示 + 已有清单 + 未消化行渲染 + tombstone 清单 → JSON ops，代码校验后落库写流水。
否掉
CC 的 forked agent（受限工具表自己读写记忆文件）：v1 里已有正文由 BodyBudget 前置进输入，读写循环的必要性不足。
代价
超预算时模型看不到全部已有正文，可能重复提取相近条目——整理阶段合并兜底。
反悔条件
ops 质量问题真实出现时，换 agent.New + 受限注册表跑读写循环，hook/水位/ops 契约不变。

D7冷却 = 画像参数，ticker 是心跳不是节奏user

选定
IntervalMin：coding=60，companion=120。ticker 固定 10–15 分钟检查一次，物量门和间隔门决定是否真跑。
否掉
把 ticker 间隔当节奏调：空转检查只是一次 meta 读，调大反而让该 dream 的时刻晚到半个周期。
代价
companion 120min 看似粗，实际记忆延迟 = "会话结束或 2 小时先到为准"，退出收尾兜住大多数场景。
反悔条件
陪伴场景反馈"跨会话没记住刚聊的"时先查退出收尾是否生效，再调小冷却。
语义层

关系与版本

D8关系用两列 + 结构化正文，不上图谱分析

选定
entities（关于谁）+ related（关联哪条）两列；实体归一在写入时由模型做；bond 正文定死事件结构（事件/时间/起因/经过/结果/影响）；op=about 聚合查询。
否掉
知识图谱/三元组表：消费者是 LLM 不是查询引擎，正文里的关系模型读得懂；图结构反而要再序列化成文本。
代价
多跳查询和程序化实体归一做不了。
反悔条件
单空间记忆 >500 条、需要多跳查询、或实体归一必须程序保证时，把 related 从提示列升级为真图结构。

D9版本用 append-only 流水，不加版本表分析

选定
memories 存当前信念，memory_log 记每次 upsert/supersede/delete 的旧值、新值、reason、会话、时间。supersede 是一等 op，矛盾更替带理由。
否掉
版本链/双时态（valid_from/valid_to）：当前视图查询变复杂，收益只有"当时的信念"——流水折叠同样给得出。
代价
回放要写"折叠流水"的读路径，不是一行 SQL；这个读路径只在 history 调试和审计时用。
反悔条件
需要按时间点全空间回放（而不只是单条变更史）且频次高时，评估双时态列。
安全

边界怎么守

D10隔离靠 ctx scope，凭据靠双层防线分析

选定
空间键全部从 ctx 的 scope 派生（Scope 新增 SubjectID），模型参数里没有租户和空间字段。凭据防护双层：提示词 DoNot + Upsert 前代码级密钥模式扫描。
否掉
靠模型自觉不乱写路径/不传 tenant 参数——参数层就不该有这两个字段。
代价
Scope.SubjectID 是对既有代码唯一的横切改动，云端入口要正确注入。
反悔条件
云端落地前必须补 read_file/run_command 的每租户沙箱——这是既有缺口，记忆只是让它更显化。
