设计文档 · RuneHarness Gateway

Bot 网关：一套事件账本，两条传输轨

把 RuneHarness 从"单进程 CLI"演化为"可同时挂 TUI 与远端 app 的 agent 运行时"。 本文定义网关的三个核心件——事件账本、会话运行器、传输轨——以及中断与生命周期语义。 第一个落地渠道是 bigbigbear 的 WS 协议，SSE/fetch 轨是同一账本上的第二个消费者。

版本 v1.0 草案 状态：设计，未实现 依赖：session.Store / agent.Hooks / bgtask / cron（均已落地） 首个渠道：bigbigbear（bear.alfred-develop.online）
怎么读
  1. 只看决策 → 第 1 章 + 每章开头的结论段。
  2. 要动手实现 → 第 3 章（账本）、第 5 章（槽位状态机）、第 8 章（落地顺序）。
  3. 要理解为什么 → 每节的"场景"卡，每条决策都从一个会出事的场景讲起。
第 1 章 · 结论先行

CLI 和 bot 不是两个产品，是一套内核的两套前端

一个断言：coding agent 是 bot 的一个 profile，不是另一个架构。本文把断言落成三个新组件—— EventLedger（每会话 seq 递增的事件账本）、SessionRunner（每会话的串行轮次执行器）、 Rail（传输适配层：WS / SSE / 轮询共用账本）。现有 agent/session/compact/memory/tools 一行不改。
1
账本与传输分离
"不丢"由账本负责，"快"由传输负责。WS 和 SSE 只是账本的两种订阅视图， 断线重连用同一个 seq 游标续传——bigbigbear APP 和未来的 Web 端共享全部服务端逻辑。
2
轮次与订阅分离
客户端断开只动订阅，不杀轮次。杀掉一轮的唯一入口是 SessionRunner.Interrupt——这是"fetch 断线≠丢生成"这条业界共识在 agent 侧的精确翻译。
3
崩溃修复在读侧，不在写侧
进程死会留下"assistant 发了 tool_calls、结果没落库"的悬空行。 session.Fold 组装视图时合成占位结果——零写入、老会话自动覆盖、审计保留真实现场。
明确不做

不引入第三个传输协议；不给 sessions 表加生命周期状态列；不在 服务端做"帮客户端断代"——游标管理永远是客户端的职责，服务端只提供 since 语义和 reset 兜底事件。

第 2 章 · 目标与定位

先把"coding agent"和"bot"的关系说清

现状代码已经是"框架"形状：scope.Scope 的租户边界、 agent.Hooks 的横切挂点、tools.Registry 的能力插拔、 session.Store 的存储抽象，全都与前端无关。缺的只是把 main.go 里隐含的装配显式化。

两种形态共享同一个内核，差异只在三个面上：

差异面 CLI coding agent（现状） 云端 bot（本文新增）
前端 Bubble Tea TUI，程序内 Program.Send 投递 WS / SSE 网络轨，JSON 事件帧
会话定位 一进程一会话，启动即定（--resume/--continue/新建） (channel, chat_id, subject) → sessionID，由 SessionRunner 惰性装载
能力集 run_command + 文件工具 + 三道权限闸 按 profile 挂工具；陪伴型可不挂 shell，工程型挂到受约束 workspace
场景 同一份记忆，QQ 和 app 两个嘴

bigbigbear 的 nanobot 已经做到"QQ 消息回 QQ、APP 消息回 APP、共享同一 transcript"。RuneHarness 复刻这件事需要什么？

只需要一层"渠道 → 会话"的路由。memory 的注入挂在 UserPromptSubmit，与入口无关；session 的存储按 SessionID 隔离，与渠道无关。bot 唯一新增的是"哪个外部对话写进哪条 session"这个映射——它不属于任何现有包，所以单独成层。

三条传输轨全部汇入 SessionRunner；EventLedger 是唯一的出站事实源
第 3 章 · 核心设计

EventLedger：一轮 agent turn 长什么样，账本说了算

agent 的四个回调（OnPartial/OnToolCall/OnToolResult/OnInject） 加上权限询问，就是一轮轮次的全部外部可见事实。EventLedger 把它们落成 (chat_id, seq) → Event 的单调递增序列——传输轨不再各自翻译 agent 语义，只翻译账本格式。

场景 为什么不是"回调直接推给 channel"

WS 掉线 3 秒，期间 agent 流出了 12 个 delta、调了 1 个工具。客户端重连后怎么补？

没有账本时，两个办法都不对：重发"当前快照"会丢掉工具行；让客户端从头拉 history 会重复已显示的内容。有了账本，答案只剩一句：客户端带 since=上次 seq 重连，服务端把那 13 条事件原样补发。重放逻辑只有一处，三种传输共用。

3.1 事件类型：七种，不多不少

事件 来源回调 载荷要点 落盘
delta OnPartial thinking/content 增量文本 否（瞬态）
tool_call OnToolCall name + 参数摘要 否
tool_result OnToolResult ok/dur/摘要/blocked 否
inject OnInject hook 注入文本（nag/bg/cron/压缩提醒） 是（kind=inject）
ask PermRequestMsg ask_id + tool + reason + depth 否
turn_end Run 返回 status：completed / interrupted / error / crashed 是（轮次边界）
reset 账本内部 since 越界或进程重启，客户端应全量刷新 否

turn_end.status 是中断语义的总开关：客户端重连后只要看最近一条 turn_end 就知道"上一轮算完没完"，不用猜。四种取值对应第 6 章的中断矩阵。

3.2 seq：会话内单调递增，不依赖消息行 id

seq 是账本自己的计数器。不能用消息行 id 代替——delta/tool_call 这些瞬态事件不落消息表，行 id 里它们不存在。两个事件源共用同一计数器： 消息行的 Append 回报 id，账本把它映射成 seq；瞬态事件只占 seq 不落行。

3.3 存储分档：持久事件走库，瞬态事件走内存环

不落库（内存 ring buffer，每 chat 512 条）
delta        # 流式增量，半截已蕴含在最终 assistant 消息里
tool_call    # 有对应的消息行可查
tool_result  # 同上
ask          # 超时即 deny，不需要审计到重放层
reset        # 进程内信号
落库（复用现有 append-only 存储）
inject       # Kind=inject 的消息行
turn_end     # 控制行 Kind=turn_end，content=meta JSON
             #   含 status + 轮次起止行 id 水印

分档标准只有一条：客户端重连后需要看到"现在长什么样"的，落库；只需要"过程长什么样"的，不落。 delta 的半截内容重连后可以从最终 assistant 消息重建，所以不落； turn_end 是状态边界，不落就分不清"跑完了"和"崩了"。

3.4 断线续传：since 游标 + reset 兜底

客户端订阅时带 since（期望的第一条 seq 减一）。三种响应：

  • 正常：内存环里有 since+1 起的窗口，直接补发后接实时流。
  • 窗口已滚出：先发 reset 事件（含最新 turn 边界），客户端清屏重绘——等价于 kapibala 的"前缀游标失效，取最新快照"。
  • 进程重启：内存环清空，新账本首事件是 reset。客户端的 since 直接失效走同一条路径。
为什么不用消息行 id 当游标

delta 没有行 id。用混合游标会让客户端同时维护两套续传语义； 账本 seq 把"持久"与"瞬态"统一成一个坐标系。

第 4 章 · 传输轨

WS 与 SSE 是同一份账本的两种读法

两条轨的职责完全对称：上行把"用户消息/动作"递到 SessionRunner， 下行把账本事件编成自己的帧格式。差异只在协议壳。

4.1 WS 轨：复用 bigbigbear 现有协议

bigbigbear APP 的协议（server/README.md 速查表）已经是"命令帧上行 + 事件帧下行"的形状， 映射是机械的：

nanobot 协议 RuneHarness 对应 备注
{"type":"attach","chat_id":…} Subscribe(chatID, since) 协议加可选 since 字段做续传，向后兼容
{"type":"message",…,"turn_id"…} Enqueue(chatID, content) busy 时排队，闲时起跑
delta 事件 账本 delta 我们的 OnPartial 是累积快照，adapter 侧 diff
stream_end / turn_end 分段流 / Run 返回 一轮多段 = 工具调用间自然分段，语义天然对齐
reasoning_delta Partial.Thinking 推理模型的思考链
服务端 ping 20s WS 心跳 保持现状，防中间层掐空闲连接

4.2 SSE/fetch 轨：HTTP 语义，单向只读

# 下行：事件流（长连接）
GET /v1/chats/{chatID}/events
  Headers: Authorization: Bearer <tok>  ·  Last-Event-ID: <seq>   # 续传点
  → 200 text/event-stream
     id: 142\nevent: delta\ndata: {"text":"你好"}\n\n
     id: 143\nevent: tool_call\ndata: {"name":"read_file",…}\n\n
     : ping            # 每 15–20s 心跳注释帧

# 上行：两条控制面 POST（短请求）
POST /v1/chats/{chatID}/messages   # {"content":"…"} → Enqueue
POST /v1/chats/{chatID}/actions    # {"type":"cancel"} 或 {"type":"answer","ask_id":"…","allow":true}

SSE 是单向通道：上行只能走短请求。所以"中断"和"权限应答"各自有一个 actions 端点——这比往事件流里塞双向语义干净，也不违反 SSE 协议形态。

场景 为什么不让 SSE 流也接上行

用户在流式中途按"停止"，客户端想让服务端停——SSE 通道能捎带这个请求吗？

不能，SSE 响应体是只读的。所以"停止"要走第二条 HTTP 请求 POST /actions。WS 轨天然双向，同一件事是一条命令帧。 两条轨功能等价，上行路径不同——客户端选 WS 还是 SSE，取决于它要不要省一条连接，不取决于功能差异。

4.3 部署形态：单端口，nginx 分流

# k3s pod 内单端口 :8765，ingress 按路径分流（bigbigbear 现状兼容）
/          → WS 升级（Upgrade: websocket）           # bigbigbear APP
/v1/...    → HTTP（含 SSE 的 GET /events）          # 新轨
/svc/...   → 历史/搜索 HTTP API                     # sidecar 收编进 runebot

SSE 过 nginx-ingress 要三个配置：proxy_buffering off、 proxy_read_timeout 拉到 1h 以上、强制 HTTP/1.1 upstream （proxy_http_version 1.1）。Cloudflare 侧 WS 与 SSE 都已支持； Retry-After 之外没有额外要求。bigbigbear 的 CF→ingress→pod 链路原样复用。

协议面冻结点

对外只承诺两件事：事件是 (seq, type, data) 三元组、 续传游标是 since。具体的帧格式（WS JSON / SSE data 行）是轨私有的， 未来加新轨不动账本。

第 5 章 · 会话运行器

槽位有状态机，session 行没有

持久层的 sessions 行永远是"有效"的——append-only 账本没有非法中间态。 需要状态机的是运行层的槽位：这个会话现在归谁管、能不能塞新轮、崩了以后谁来接管。

槽位生命周期：COLD → LOADING → IDLE ⇄ TURN；崩溃接管从 COLD 直接进，补记 turn_end(crashed)

5.1 槽位持有的运行态（全部内存，不落库）

字段 职责 为什么要独立
turnCtx / cancel Interrupt 的唯一靶子 轮次取消与订阅断开要分开——订阅走光不能杀轮次
pendingAsk 权限询问路由 + 超时计时 客户端不在时 ask 不能死等，60s 无应答按 deny
inbox bg/cron 通知的待交付队列 复用现有 Drain/Requeue 语义：被消费才出队
subscribers WS/SSE 订阅者集合 客户端断开只动这个集合，不影响 turnCtx

5.2 接管修复：进程重启后第一个动作

场景 pod 被驱逐时发生了什么

runebot pod 在 agent 跑到一半时被 k8s 驱逐（OOM / 滚动升级）。sqlite 在 PVC 上没丢， 但内存里的 Run 死了。库里现在是什么样？

库里留下了：user 消息、一些 assistant（可能带 tool_calls）、 已执行的部分 tool 结果——但没有 turn_end， tool_calls 的结果行可能缺一半。这就是"悬空 tool_call"。

接管序列：新进程把这个会话装载进槽位时做三件事—— ① Fold 检测到最后 assistant 的 tool_calls 有未配对项，合成 "error: execution interrupted" 占位结果进视图； ② 账本补记 turn_end{status:"crashed"}； ③ 槽位落到 IDLE，客户端重连 since 后看到"上一轮死于崩溃"的完整现场。

5.3 为什么不给 session 行加状态机

状态机建在内存槽位上，而不建在 sessions 表上，是两条独立的理由叠加：

  • 账本已是终态：append-only 消息行不存在"半死不活"。每行都是已发生的事实， 崩溃留下的悬空行经 Fold 修补后是合法视图。加一个 status 列等于引入第二个事实源。
  • "活着"是内存事实：session 的"占用"只存在于某个进程的某次 Run 里， 进程死了它自然释放。把这个事实写库，就要处理"库里说占用、进程已死"的脑裂—— 而内核级 flock（cron 已在用）就是现成的答案，不需要表里再写一遍。
第 6 章 · 中断语义

两类中断，五个场景，一个出口

中断不是一个按钮，是六条不同的路径。本文把它们归到"客户端断开" 与"服务端终结"两类，每类给出确定的行为与账本痕迹。

中断分类：C1 不断轮次，C2 主动取消；S1/S2 是终结，S3 是局部超时

6.1 C1 是误解最深的一条

场景 "abort 了请求就省 token"——对 agent 不成立

笔记里说"用 AbortController 取消 fetch，不然服务端还在算浪费 token"。对纯文本补全是对的，对 agent 为什么错？

因为 agent 的"还在算"不是白算——它可能已经执行了三个工具、写了文件、 发了通知。把请求断了只断了投递通道，工作已经发生且落库。 正确姿势是投递与轮次解耦：fetch abort → detach subscriber → Run 继续到 turn_end → 客户端重连补看结果。真正要停的时候才走 C2 显式取消。

6.2 C2 的取消路径

两条轨语义等价、路径不同，但都收敛到 SessionRunner.Interrupt(chatID)：

  • WS：命令帧 {"type":"cancel"}。
  • SSE：POST /v1/chats/{id}/actions {"type":"cancel"}。

Interrupt 内部走现有 context.Cancel → InterruptedError 路径：已执行工具结果照常落库，未执行的 tool_calls 补占位，账本补记 turn_end{status:"interrupted"}。部分进度保留，可续跑——这是现有语义的原样复用。

6.3 S3：权限询问不能死等

场景 模型要 run_command，但用户在地铁上没看手机

ask 事件发出去了，通道那头没人。agent 卡在哪？

卡在 permission.NewHook 的 reply channel 读上—— 现状实现是裸等（main.go:159-165）。bot 形态下应给这个 channel 加超时：60s 无应答按 deny 回填 "error: permission denied (timeout)"， 轮次继续而不是僵死。WS 订阅者断开的那一刻起计时，不问"还会不会回来"。

警告

S2 是唯一会留下"悬空 tool_calls"的路径。运行期中断（C2）有 loop 补占位； 崩溃（S2）没有——所以 Fold 的读侧修补是必要的兜底， 不是可选优化。没有它，崩溃后第一次 LoadHistory 发出的请求会被 OpenAI 协议拒掉（每个 tool_call 都应有配对结果）。

第 7 章 · 能力集与沙盒

profile 是一组命名配置，沙盒是 profile 的属性

bot 与 coding agent 的差异不是架构差异，是"这轮会话挂了哪些工具、权限闸多紧、 工作目录在哪"的配置差异。把这三个要素打包成 Profile，"bot 会不会写代码"就退化成一行配置。

7.1 能力分级

档 形态 沙盒需求 对应 profile
L0 问答陪伴：memory + cron + 聊天工具 无。模型无副作用。 companion
L1 只读工程助理：读文件、列目录、安全前缀命令 工作区围墙（cwd + ForbiddenPaths）。 reader
L2 workspace 内执行：run_command + 写文件 进程 cwd 锚定 workspace + 三道闸；pod 即边界。 coding
L3 不可信代码执行：装依赖、联网、跑任意脚本 真隔离：namespace / 容器 / VM。 （暂不实现）

bigbigbear 的陪伴 bot 停在 L0；云端工程助理停在 L2； L3 等"模型跑别人给的代码"这个真实需求出现再上，用现成的 OCI runtime 而不是手写 namespace。

7.2 L2 的边界具体是什么

场景 工程助理 bot 的一次 "run_command"

bot 接到"帮我把这个仓库的测试跑一下"——命令落在哪？

会话绑定一个 workspace（~/.rune/workspaces/<tenant>/<session>/， 或 PVC 下的 per-session 目录）。run_command 的 exec.Cmd.Dir 锚到这里，ForbiddenPaths 挡敏感文件， 命令白名单挡系统级操作。pod 文件系统本身是容器边界——模型最多搞坏自己的 workspace 和 pod 的可写层，宿主与其他 pod 不受影响。

个人 CLI 的 coding agent 是另一种 L2：没有 pod 边界，靠的是"三道闸 + 用户盯弹窗"。 两者共用同一个 permission.Config 结构，只是闸的严格度和 workspace 位置不同。

第 8 章 · 落地顺序

五个增量，每个都可独立验证

排序按依赖关系，不按功能酷炫度。前三个是纯重构——改完 CLI 行为不变； 第四个起才有新行为。

1
装配外提：internal/harness
把 main.go 的接线收进 Harness{Agent, Registry, Compactor, Store, Memory, BGM, Cron} + Builder。验收：CLI 启动路径不变，go test ./internal/... 全绿。
2
事件收口：Events 接口
OnPartial/OnToolCall/OnToolResult/OnInject + ask 回调收敛成单一接口； TUI 实现它，gateway 也实现它。验收：TUI 显示不变。
3
SessionRunner + EventLedger
槽位状态机 + 账本环形缓冲 + Interrupt。验收：CLI 里 Interrupt（Esc）语义不变； 新跑一个注入测试证明 Fold 补悬空 call。
4
WS rail：bigbigbear 协议
cmd/runebot：ready/attach/message/delta/turn_end + /svc 历史端点。验收：Bear APP 直接连 runebot，Phase 0/1 清单全过。
5
SSE rail + actions 通道
GET /v1/chats/{id}/events + POST /messages + POST /actions。验收：curl 流式拉一轮，断线 Last-Event-ID 续传。

验收清单（最小可用）

  • Bear APP 连 runebot：握手 101 → ready → attach → attached → message → delta 流 → turn_end，与现有 nanobot 行为逐帧一致。
  • 断 WS 5 秒重连带 since：补发期间漏掉的 delta/tool_call/turn_end，不重不漏。
  • SSE curl GET /events：中途 Ctrl-C 断流，重连带 Last-Event-ID 继续，顺序与 WS 轨一致。
  • 中断（C2）：跑一轮时发 cancel，库里出现 interrupted 占位 + turn_end(interrupted)；重连客户端看到半截内容+中断标记。
  • 崩溃（S2）：kill -9 模拟 pod 死，重启后该会话 Fold 视图含占位结果，账本补记 crashed。
回滚路径

每步都是 additive：轨是新挂的 handler，账本只读不改写消息行， Fold 的修补只影响读侧视图。任何一步出问题，摘掉对应组件即可退回纯 CLI， 数据库里不留新写入形态。

待补

  • 多实例部署：单 pod 假设。多副本需要把账本 seq 外置到共享存储（PG 序列或 Redis）， 以及把 turnCtx 换成跨进程 lease。当前版本按单副本设计。
  • 进程内事件顺序：OnPartial 与消息行 Append 的相对顺序 依赖 loop 执行序，尚未在协议层强约束；账本 seq 按事件到达序即可，不必对齐行 id。
