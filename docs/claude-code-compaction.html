第 1 章 · 全景

一个会话的一生：上下文曲线上的五道关卡

你让 Claude Code 帮你重构一个项目。它开始读文件、跑测试、改代码——每一轮工具结果都往上下文里塞东西。下面这条曲线就是这次会话的"体重变化"，每个转折点对应一道压缩关卡。

示意图：同一会话内上下文 token 随轮次的变化 · ②③是零成本维护，④花一次 LLM 调用，⑤是最后的救生圈
一句话原理：压缩不是等模型想起来要压，而是 harness 每轮发请求前都检查一遍体重秤。轻的手段（改内容、砍旧结果）每轮白跑；重的手段（让 LLM 写摘要）只在撞线那一刻出手；API 报错还有最后一层兜底。模型从头到尾没有被问意见——这是刻意设计。
第 2 章 · 第一道关

场景：模型一口气 cat 了个 80KB 的日志

场景 A单条工具结果太大 → 整个存盘，留 2KB 预览

调试线上问题，模型执行 tail -2000 app.log，返回 152KB 文本。按 4 字节/token 粗算就是 ~38K tokens——一次调用吃掉窗口的五分之一。

Claude Code 在结果回到上下文的那一刻就拦下来：阈值是 min(工具自声明上限, 50K 字符)，全局硬顶 400KB。超了就把全文写到会话目录 tool-results/{tool_use_id}.txt，上下文里换成一张"收据"：

存盘前 · 发给模型的内容
tool_result (id=call_x9):
  [152KB 日志原文…
   38000+ tokens]
存盘后 · 模型实际看到
tool_result (id=call_x9):
<persisted-output>
Output too large (152KB).
Full output saved to:
  ~/.claude/…/tool-results/call_x9.txt
Preview (first 2.0KB):
  2025-01-08 ERROR …
</persisted-output>

关键：信息没丢，只是换了位置。模型知道全文在哪，需要细节时用 Read 自取。这比"截断丢弃"强得多——截断是不可逆损失，落盘是可回溯的。

源码 src/utils/toolResultStorage.ts → maybePersistLargeToolResult

场景 B一轮并行 10 个工具，每个 30KB → 聚合预算

单条都没超 50K，但模型一轮发了 10 个并行搜索——合计 300KB。单条拦截管不住这种"蚂蚁搬家"。

于是还有一层聚合预算：同一个 wire 级 user 消息里（Anthropic 协议中一轮并行结果会合并进一条消息），所有 tool_result 合计超 200K 字符，就从最大的开始逐个落盘换预览，直到达标。消息之间互不影响——这轮超了这轮管，上一轮 150K 不动。

为什么决策要"冻结"

这层有个反直觉设计：每个 tool_use_id 的命运见一次就定型。已经换成预览的，每轮重放同一个预览串（逐字节一致）；当初没换的，以后上下文再挤也不换它。原因是 prompt cache——服务端按前缀缓存，同一前缀每轮重发，只要有一段内容变了，后面全部缓存失效。所以"这轮替换成 A、下轮想换成 B"的自由只能放弃。决策记录还会写进 transcript，resume 后原样重建。

源码 enforceToolResultBudget · 分组时还精确模拟了 wire 合并：同 message.id 的 streaming 拆分片段归一组，否则在"看不见的合并处"漏管。

顺带一个防呆

空的工具结果会被填成 "(xxx completed with no output)"。因为空结果会让某些模型误触发 \n\nHuman: 停止序列、一句话不说就结束回合（线上事故 inc-4586）。

第 3 章 · 第二道关

场景：你去吃了个饭，一小时后回来

场景 C闲置超 60 分钟 → 旧工具结果原地清空

上午模型读了 20 个文件找 bug，你去开会一小时。回来时上下文里还挂着一堆一小时前的文件内容——反正服务端 prompt cache（1 小时 TTL）肯定过期了，整个前缀横竖要重写，不如趁这机会瘦身。

触发时（now − 最近 assistant 时间戳 > 60min），把除最近 5 条外所有可压缩工具的结果体原地清掉：

清空前
tool_result (id=call_31):
src/auth.ts:1-200 完整内容…
（两小时前读的，40 个结果类似）
清空后 · 结构纹丝不动
tool_result (id=call_31):
[Old tool result content cleared]

# id、is_error、配对关系全保留

注意它只换 content 字符串——块还在、id 还在、和 tool_use 的配对关系纹丝不动。可清空的工具有白名单：Read、Bash 系、Grep、Glob、WebSearch、WebFetch、Edit、Write。为什么挑这些？它们的结果可再取——文件还在盘上、命令还能重跑。

源码 src/services/compact/microCompact.ts → maybeTimeBasedMicrocompact · 默认配置 60min / 保留最近 5 条，GrowthBook flag 控制（默认关闭）。

进阶版服务端直接删缓存里的旧结果（ant-only）

本地清空会破坏缓存前缀。内部版还有两条更精细的路径：

  • cached microcompact：不改本地消息，在 API 请求里带 cache_edits 指令，让服务端把缓存中的旧 tool_result 标记删除——缓存命中和瘦身兼得。
  • API 原生 context_management：请求体里声明策略——"input_tokens 超 180K 时，服务端自动清掉够降到 40K 的旧 tool_result"；thinking 块单独一条策略（默认全留，闲置超 1h 只留最后一轮）。

源码 cachedMicrocompact.ts / apiMicrocompact.ts · 均为 ant 内部特性，开源构建中被裁剪，但思路可借鉴。

第 4 章 · 第三道关（核心）

场景：曲线涨到 167K，代码不问意见直接动手

这是你问的"托底指标"。先看公式，再看它为什么信得过。

4.1 阈值公式：两行减法，每段都有出处

公式本身只有两步。先列出它，再代入数字算一遍，最后讲每一段缓冲在为谁付费。

// src/services/compact/autoCompact.ts:33-49, 72-91 —— 没有玄学，全是减法
有效窗口 = getContextWindowForModel(model)          // 200K，[1m] 模型为 1M
        − min(getMaxOutputTokensForModel(model), 20_000)  // 输出预留

触发线 = 有效窗口 − 13_000   // AUTOCOMPACT_BUFFER_TOKENS
警告线 = 触发线 − 20_000   // WARNING / ERROR 共用这条
阻断线 = 有效窗口 − 3_000   // MANUAL_COMPACT_BUFFER_TOKENS

先算一遍：200K 窗口、max_output 为 32K 的模型

步骤 算式 结果 这笔钱给谁花
物理窗口 getContextWindowForModel 200,000 API 接受的总量上限
− 输出预留 min(32,000, 20,000) −20,000 压缩时那次摘要调用的产出
= 有效窗口 200,000 − 20,000 180,000 历史部分允许涨到的高度
− 触发缓冲 AUTOCOMPACT_BUFFER_TOKENS −13,000 压线过检那一轮的 overshoot
= auto-compact 触发线 180,000 − 13,000 167,000 到线即压，不问模型意见
− 警告偏移 WARNING_THRESHOLD_BUFFER_TOKENS −20,000 给用户的提前量
= 警告线 167,000 − 20,000 147,000 Context low · Run /compact
− 阻断偏移 MANUAL_COMPACT_BUFFER_TOKENS −3,000 手动 /compact 的发送空间
= 阻断线 180,000 − 3,000 177,000 到线拒发普通请求

再看一眼：200K 是怎么被分掉的

每一段缓冲为什么是这个数

1
输出预留 20K——为什么第一道减的是输出
因为测量口径把输入和输出记在同一份账里。getTokenCountFromUsage 把 input + cache + output 加在一起（utils/tokens.ts），所以"窗口预算"装的其实是"历史 + 模型要吐的响应"两样东西。有效窗口先划出输出的位置，剩下的才是历史允许涨到的高度。
为什么是 20K：代码注释写明出处——线上摘要输出的 p99.99 是 17,387 tok，向上取整。为什么是 min()：模型的 max_output 被压到 8K 时（tengu_otk_slot_v1 开关），预留跟着缩成 8K，触发线相应从 167K 抬到 179K。模型吐不出 20K，就不该替它留 20K。
2
触发缓冲 13K——兜住"压线过检"的那一轮
代码没写这个数字的出处，下面是按检查点位置的推断。检查是离散的、按轮做的，上下文却是按"一整轮"为单位涨的。166.9K 通过检查后发出的请求，回来时可能带着一整轮新内容：模型输出加一批工具结果。13K 吸收这个 overshoot，让触发压缩的下一轮摘要调用仍落在有效窗口内。它也顺带兜住尾部 chars/4 粗估的误差和摘要请求 prompt 自身的几千 token。
3
警告偏移 20K——给人看的，不是给代码看的
剩约 10% 窗口时 UI 显示 Context low · Run /compact。此刻手动压缩还来得及挑选要保留的内容，所以提前量给到 20K 而不是 3K。UI 的 percentLeft 按"距下一次动作"计算：auto 开时相对触发线，auto 关时相对有效窗口。warning 和 error 两个标志共用 −20K，是同一位置的两个提示级别。
4
阻断偏移 3K——给手动 /compact 留的发送空间
query.ts:592 的注释写明用途："reserves space so users can still run /compact manually"。压缩请求也是一次 API 调用，余量耗到 0 时连自救都发不出去，所以提前 3K 拒发普通请求。注释原文标明它只在主动压缩不接管时生效——auto 关闭，或者 auto 开着但压缩已熔断。到线后系统合成一个 prompt-too-long 错误直接退出。
为什么全是绝对值，不是百分比

每段缓冲对应一笔具体的账：一篇摘要输出、一轮 overshoot、一次手动压缩的发送成本。这些账的大小跟窗口大小无关，所以不按窗口缩放。推论：1M 窗口的模型用同一套公式，触发线在 967K，占窗口 96.7%——窗口越大，代码越敢压到更晚才动手。

测试和逃生用的旋钮：CLAUDE_CODE_AUTO_COMPACT_WINDOW 从输入侧压低窗口上限；CLAUDE_AUTOCOMPACT_PCT_OVERRIDE 按有效窗口的百分比覆盖触发线；DISABLE_AUTO_COMPACT 关掉自动压缩但保留手动 /compact。

所以 200K 窗口 + 默认 max_output 的模型：有效窗口 180K，警告线 147K，强制压缩线 167K（≈83.5%）；触发线到物理上限之间其实隔着 33K，够一次压缩动作从容完成。

4.2 测量靠什么：不是数字符，是 API 自己报的账

每次 API 响应都带回精确的 usage（input_tokens + cache 读写 + output_tokens，即整个窗口的真实占用）。Claude Code 把它存在 assistant 消息上，下次测量时：

…
更早的消息（已在锚点内）
assistant
usage: input 148K + cache_read + output ← 锚点：真实精确值
tool ×3
三条工具结果（锚点之后的新货）
user
你的新消息
→ 当前估值 = 锚点 usage + 尾部字符粗估（len/4），准且零成本

有个坑它专门处理了：并行工具调用会把一次响应拆成多条同 message.id 的 assistant 记录，中间穿插 tool_result。如果锚点只取最后一条，会漏估前面穿插的结果——所以实现会沿同 id 向前走到第一个兄弟节点再开估。

4.3 判定链上还有哪些保险

1
递归护栏
压缩 agent / session-memory agent 自己继承全量历史，它们内部再触发压缩会死锁——querySource 白名单直接挡掉。
2
多层开关
DISABLE_COMPACT、DISABLE_AUTO_COMPACT、用户设置、reactive-only 实验、context-collapse 接管——每一层都能喊停。
3
失败熔断
连续失败 3 次就放弃本会话的自动压缩。注释里的真实数据：曾有 1,279 个会话各连续失败 50+ 次（最高 3,272 次），每天白烧约 25 万次 API 调用，熔断是血的教训。
为什么不让模型自己决定——源码实证

这个构建里模型根本没有 compact 工具可调（教学版 s08 里的"compact 工具"是简化）。原因你很清楚：上下文越满幻觉越重，一个快被自己上下文喂傻的模型指望它想起"我该压缩了"，不如指望代码里的一个 >=。模型层的唯一自救是 flag-gated 的 SnipTool（内部特性）。压缩决策权 100% 在 harness，这正是"工程托底"的含义。

第 5 章 · 压缩全过程

场景：撞线那一刻，后台发生了什么

从"判定该压了"到"模型拿到新上下文"，中间是一整条流水线。跟你想象的可能不一样——它甚至能不调就不调 LLM。

5.1 先走捷径：有现成笔记就不写摘要

flag 开启时，后台早有一个 session-memory fork 在持续把对话要点写进 notes 文件（增量维护，游标记到 lastSummarizedMessageId）。需要压缩时直接把这份笔记当摘要，保留"游标之后 + 向前扩展到 ≥10K tokens 且 ≥5 条文本消息、≤40K 封顶"的尾部原文——零额外 LLM 调用。notes 是空模板才回落到传统摘要。

5.2 正经摘要：一次"很会省钱"的 LLM 调用

1
拼请求
全量历史（压缩边界后的投影）+ 末尾追加一条 user 消息："请给这段对话写详细摘要"，prompt 结构见 5.3。
2
首选：fork agent 共享缓存
用和主线程完全相同的 cache-key 参数（system、tools、消息前缀）起个 fork——命中已有 prompt cache，几乎不产生 cache_creation。不共享时实测 98% cache miss。单回合、禁止一切工具调用。
3
兜底：独立流式调用
fork 拿不到文本就走独立请求：system prompt 换成摘要专用、thinking 关掉、max_output 限 20K、工具只挂 Read。
4
摘要请求自己也可能超限
快爆的历史再发一次当然可能 413。解法：按"一次 API 往返一组"从头丢弃——能从报错里解析出 N tokens > M maximum 就按差额丢，否则丢 20%；最多重试 3 次；砍完若以 assistant 开头就补一条合成 user 占位。
5
组装新消息集（当轮生效）
边界标记 → 摘要消息 → 保留的尾部消息 → 回补附件 → hook 结果。不删旧历史，只是加了条"分界线"，本轮直接拿新集合去调模型。

5.3 摘要 prompt 解剖：损失最小化的秘密在结构

头部
CRITICAL: Respond with TEXT ONLY. Do NOT call any tools… will be REJECTED and will waste your only turn.
放最前不是修辞：fork 继承全套工具（缓存键要求），Sonnet 4.6 有 2.79% 概率无视提醒去调工具——单回合下调工具 = 这次压缩白做。头部 + 尾部提醒 + canUseTool 强制拒绝，三重冗余。
草稿垫
把分析包在 <analysis> 里：按时间顺序过一遍对话，识别意图、方法、决策、文件名、完整代码片段、函数签名、错误与修复、用户纠正过什么…
本质是 CoT 召回器：强制先全文通读再动笔。写完 formatCompactSummary 把 analysis 整块剥掉——草稿不进上下文，白赚质量。
正文
<summary> 九段固定 schema ↓
尾部
REMINDER: Do NOT call any tools… + 可选的用户自定义侧重（/compact 重点保留测试输出）

九段 schema——每段堵一类已知丢失点

# 段落 它在防什么
1 Primary Request and Intent 用户全部显式请求 压缩后忘了最初要干嘛（目标漂移）
2 Key Technical Concepts 领域词汇丢失，后续选型/用词跑偏
3 Files and Code Sections 文件名 + 完整代码片段 + 为什么读它 最疼的实物损失：文件内容没了被迫重读或凭印象重写
4 Errors and fixes 错误与修法 + 用户纠正 把用户刚否掉的方案又做一遍
5 Problem Solving 已解决 + 进行中 推理结论蒸发、重走弯路
6 All user messages 列出全部非工具结果的用户消息 用户中途改需求被"平均化"抹掉——用户消息是意图最高保真源
7 Pending Tasks 任务清单蒸发
8 Current Work 压缩瞬间在做什么 断点丢失、不知从哪续
9 Optional Next Step + 逐字引用最近对话 verbatim quote 防摘要生成一个"听着合理但偏离原意"的下一步

源码 src/services/compact/prompt.ts · 另有 partial compact 两个变体（'from' 保前缀缓存 / 'up_to' 摘要前置缓存失效）。

5.5 摘要之外：把"工作记忆"重新挂上

摘要记的是"发生过什么"，记不住"手里有什么"。所以压缩后还要重挂一批附件：

重挂什么 细节 为什么需要
最近读过的 5 个文件 重新 Read 拿新内容，每个 ≤5K tok、总 ≤50K；保留尾部已有的不重挂 摘要只说"读过 auth.ts"，但模型改代码要看到内容
plan 文件 + plan-mode 指令 全文重挂 否则压缩后模型忘了自己还在 plan 模式/计划是什么
调用过的 skills 按调用时间倒序，每个 ≤5K、总 ≤25K，截断保头部 skill 是外部注入的知识，摘要写不进去
后台 agent 状态卡 running / 已完成未取结果的 防止压缩后重复 spawn
deferred tools / agent / MCP 增量 + SessionStart('compact') hooks 按空历史基线重算 保证压缩后第一轮工具上下文完整（CLAUDE.md 等重挂入口）
第 6 章 · 压缩之后

模型看到的上下文长什么样

压缩后发给 API 的消息序列，大概是这个样子：

system
原 system prompt（不变，保住缓存前缀）
user
摘要消息：九段总结 + transcript 路径 + "直接续上别寒暄"（auto 时）
user
保留尾部：最近的对话原文
assistant
最近的回复原文（含 tool_use）
tool
最近工具结果原文
attach
回补：最近文件内容 / plan / skills / 后台 agent 状态 / 增量指令
hook
SessionStart('compact') hooks 输出（如 CLAUDE.md 重注入）
压缩 ≠ 删除：boundary 语义

transcript 里的旧消息一条不删。只是在数组里插一条 compact_boundary 标记（带 trigger、压缩前 token 数、衔接元数据 logicalParentUuid/preservedSegment）。每轮开头 getMessagesAfterCompactBoundary() 取"最后一个 boundary 之后"的切片给模型；UI 滚动仍看全量。多次压缩天然兼容——永远以最后一条边界为准。resume 时 loader 按元数据把保留段重新接回消息链。

第 7 章 · 一条不能越过的红线

为什么不能随便"从中间砍"

Anthropic 协议规定：tool_use（assistant 消息里）和 tool_result（user 消息里）按 tool_use_id 一一成对。切错了地方，API 直接 400 拒收。

错误切法 · 从 tool_use 和它的结果之间劈开
…(摘要掉)… | asst: tool_use id=X
user: tool_result for X   ← 孤儿：前面没有 id=X 的调用
→ API 400: unexpected tool_use_id
正确切法 · 只在"新 assistant 响应"之前下刀
asst(id=A): tool_use X     ┐
user:        tool_result X  ├ 同一次 API 往返，同进同退asst(id=B): 新回合          ← 安全切点在这里

Claude Code 的切分单位就是 groupMessagesByApiRound：以"出现新 message.id 的 assistant 消息"为组界——API 协议保证每个 tool_use 在下一轮 assistant 之前必有结果，所以组界天然就是协议安全切点（连流式拆分的同 id 片段也归同组）。

但仍要兜底：API 边界前的修复器

压缩只是可能切坏历史的原因之一——中断续传、旧数据 bug 都会留下畸形对子。所以发请求前还有 ensureToolResultPairing 统一修复：

畸形 修复方式
tool_use 缺结果（中断/截断） 注入合成错误结果 [Tool result missing due to internal error]（is_error）
孤儿 tool_result（无对应调用） 剥除该块；首条消息因此变空就填占位，保住 user-first 结构
tool_use_id / tool_result_id 重复 跨消息去重
服务端工具的 use 无 result（流中断） 剥 use 块；assistant 变空填 [Tool use interrupted]
HFI 训练数据采集场景（strict 模式） 不修直接抛——合成占位会污染训练轨迹
同一思想在 RuneHarness 的 OpenAI 形态下

你的配对是 assistant.tool_calls[].id ↔ role=tool 的 tool_call_id，且一条 assistant 可挂 N 个 call、后随 N 条 tool 消息。原子组 = "带 tool_calls 的 assistant + 连续 tool 消息段"整体。裁剪只在组间下刀；microcompact 式清空只改 tool 消息 content；兜底修复同样适用（缺结果的 call 补合成 tool 消息、孤儿 tool 消息剥除）。

第 8 章 · 最后一道保险

场景：估算失手，API 真的返回 413 了

前面全是启发式估算（字符/4 不可能完全准）。当 API 亲自说"too long"，还有一条 reactive 链路把这次会话救回来。

1
流内暂扣（withhold）
流式响应里识别出 prompt-too-long / 媒体过大错误 → 不抛给用户、不进消息流，先攒着。开关在进入流前快照一次——避免 30 秒流式中途实验开关翻转导致"扣了不修"。
2
先兑现便宜的手段
context-collapse（内部系统）有暂存的折叠先 drain——比全量摘要便宜且保细粒度。
3
reactive compact
做一次全量摘要 → 组新消息集 → continue 重发本轮。每 query 只许一次（hasAttemptedReactiveCompact）：媒体错误若在被保留尾部会重复触发，靠这个闸门防死循环。
4
救不回来就如实报错
yield 错误 + 只跑 StopFailure hooks。普通 stop hook 不跑——模型没产出有效响应，hook 注入只会"错误→注入更多 token→再错"地打转。

同样值得注意的两个手动入口：/compact [可选指令]（先走 session-memory 捷径 → 跑一遍 microcompact 缩小待摘要体积 → 全量摘要，用户指令注入 prompt）；esc-esc 圈选消息做部分压缩（两个方向可选：摘要"所选之前"保住前缀缓存，或摘要"所选之后"保住最新对话）。

第 9 章 · 落地

搬到 RuneHarness：一张移植清单

按"单位工作量收益"排序，标注哪些是直搬、哪些要按 OpenAI 形态改造。

优先级 做什么 怎么搬
P0 确定性阈值 + API 口径估算 config 加 context_window / max_output；阈值 = window − min(maxOut, 20K) − buffer。估算锚点用响应 usage.prompt_tokens + completion_tokens；尾部粗估算 ToolCalls(name+arguments) 不算 Thinking（你的 thinking 不回传 API，这点比 CC 干净）。中文为主 char/token 取 ~2 而非 4。
P0 循环内挂压缩管线 Agent.Run 的 for 里：PreChat 注入之后、llm.Chat 之前。不进现有 hook 体系（hook 是观察/注入契约）。子代理自动继承。
P1 microcompact 清旧结果 除最近 N 条外，tool 消息 content 超阈值 → [Old tool result content cleared]。只改 content 不动配对，实现最小。
P1 配对保护 + 发送前修复 原子组 = assistant(tool_calls) + 连续 tool 消息。加 ensureToolCallPairing：缺结果补合成 tool 消息，孤儿剥除。你已有 InterruptedError 补占位的雏形。
P2 LLM 摘要 + boundary 9 段 prompt 近乎照抄；摘要消息写 session id 当回溯出口（你有 SQLite raw transcript，比 transcript 文件更强）。boundary 存 DB + 投影读取。摘要请求自身要有 PTL 截断重试。
P2 聚合结果预算 单条 8KB 截断已有；补"一批 tool_calls 的合计"维度，超限落盘换 <persisted-output> 预览。
P3 reactive 兜底 依赖 internal/llm 错误归一化：各家 context_length_exceeded/413/"prompt is too long: N>M" → PromptTooLongError{gap}。每 query 重试 1 次 + 熔断 3 次。
P4 附件回补 / 增量笔记 可缓。最小替代：摘要后保留末尾 K 条原文（SM-compact 的保尾思想）。长期看"平时记笔记"是唯一能把摘要成本降到零的路。
你比 CC 简单的地方

① OpenAI 形态下 tool 消息本来就是独立的，不用模拟 wire 合并；② Thinking 不回传，估算口径天然干净；③ OpenAI 兼容端点没有承诺 prompt cache 语义——CC 那套"逐字节稳定前缀"的精细状态机（冻结替换、wx 幂等、fork 共享）可降级为"尽量幂等"，不必照搬。
