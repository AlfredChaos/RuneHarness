Codex 会话压缩（Compaction）机制全景拆解

对话超出上下文窗口时，Codex 不直接截断历史。Codex 把历史压缩成一份交接摘要，再带着摘要继续工作。本文按 codex-rs 源码拆解四个问题：什么时候触发压缩、压缩请求怎么构造、压缩后历史变成什么样、为什么这样设计。

阅读导引：第一章讲触发条件和阈值。第二至四章拆解三条压缩路径：服务端 Compaction V2、本地摘要、Token Budget 重置。同一次压缩只走其中一条路径。第五章讲压缩结果怎么写回历史、怎么落盘。第六章集中回答"为什么这么设计、不这么做会怎样"。
Chapter 01 · Overview

一次压缩的完整生命周期

Codex 把压缩当成一个独立任务来执行。压缩有独立的 turn 生命周期事件、分析埋点和 PreCompact / PostCompact 钩子，最后以一条 ContextCompaction turn item 结束。

压缩生命周期 · compact.rs / compact_remote_v2.rs / session/mod.rs

三条互斥的实现路径

同一个压缩动作，Codex 按会话能力在三条路径里选一条。手动压缩的分发点在 tasks/compact.rs，自动压缩的分发点在 session/turn.rs 的 run_auto_compact。

Path A · 默认（OpenAI 后端）

Remote Compaction V2

客户端在历史尾部追加 CompactionTrigger 请求控制项，发给服务端。服务端返回一个 Compaction 条目（带 encrypted_content）。新历史 = 保留的用户消息和代理消息 + 该条目。

provider.capabilities().remote_compaction == V2
（OpenAI / Azure Responses 默认开启）
Path B · 第三方 provider 回退

本地摘要（Local）

客户端把总结指令作为一条 user 消息追加到历史尾部，让当前模型再跑一个 turn 产出文字摘要。新历史 = 保留的用户消息（上限 20k tokens）+ SUMMARY_PREFIX + 摘要文本。

RemoteCompactionSupport::Unsupported
（非 OpenAI provider 默认）
Path C · 实验特性

Token Budget 重置

开启 token_budget feature 后，压缩不再产出摘要。客户端丢弃旧历史，从当前环境重建一份初始上下文（world state + 环境信息）。效果相当于开新窗口、保留工作区。

Feature::TokenBudget enabled
compact_token_budget.rs
分发依据：core/src/tasks/compact.rs:43-75 与 core/src/session/turn.rs:1499-1544。provider 能力判定见 model-provider/src/capabilities.rs:31-39。
Chapter 02 · Triggers

什么时候触发压缩

压缩有两类触发方式。第一类是用户手动输入 /compact，走 StandaloneTurn 阶段。第二类是 token 阈值驱动的自动压缩，按发生时机分成 PreTurn、MidTurn、PostTurn 三个阶段。

阈值怎么算

每轮采样前后，core 调用 context_window_token_status() 算出一组状态位。核心规则见 session/context_window.rs:53-130：

  • auto_compact_token_limit：自动压缩阈值。模型元数据可以给出这个值，model_auto_compact_token_limit 配置可以覆盖它。缺省值是 context_window 的 90%（openai_models.rs 的 auto_compact_token_limit()）。
  • full_context_window_limit：硬上限 = context_window × effective_context_window_percent，默认 95%。
  • token_limit_reached：scope_tokens ≥（压缩阈值 + fallback buffer），或者 active_tokens ≥ 95% 硬上限。满足任一条件就触发压缩。
  • scope 口径（AutoCompactTokenLimitScope）：Total（默认）统计整个活动上下文；BodyAfterPrefix 只统计压缩窗口前缀之后新增的 token，计数基线来自 auto_compact_window.rs 记录的 prefill 值。

场景 A 连续编译报错对话 20 轮后触发 PreTurn 压缩

用户让 codex 修一个 Rust workspace 的编译错误。模型反复执行 cargo build，每轮输出几千行日志，改代码，再执行 build。到第 20 轮时，累计 token 用量越过 90% 阈值。

第 21 轮开始，run_turn 在采样之前调用 run_pre_sampling_compact（turn.rs:1304）。该函数发现 token_limit_reached = true，先执行压缩，压缩完成后才继续正常采样。用户这条新输入已先写入历史（compact.rs:264），所以压缩请求里包含用户的最新诉求。

为什么是 PreTurn，而不是等 ContextWindowExceeded 错误

压缩是预防性动作：core 在服务端拒绝请求之前主动压缩。如果等 400 错误再补救，会浪费一次完整上行流量的延迟，有些 provider 还会直接断开连接。压缩失败时，PreTurn 阶段会保留用户输入，由 run_turn 外层统一上报错误（compact.rs:240-245）。

场景 B 模型调用 new_context 工具 → MidTurn 压缩

模型在长任务中途自己判断该换窗口了，调用 new_context_window 工具。该 handler 只置一个标志位 request_new_context_window()（new_context_window.rs:38），不立即重置。

采样结束回到 turn 循环，should_roll_over = needs_follow_up && (take_new_context_window_request() || token_limit_reached) 成立，触发 MidTurn 压缩。这次压缩用 InitialContextInjection::BeforeLastUserMessage 模式注入环境上下文（后述）。工具调用继续，对话不中断。

为什么 MidTurn 要把 initial context 注入压缩后历史

源码注释写明：模型按训练预期，压缩摘要应是历史中的最后一条内容（compact.rs:67-69）。MidTurn 之后马上接同一段对话的后续采样，所以环境上下文（cwd、git 状态、AGENTS.md）应保留且位置正确：插在"最后一条真实用户消息之前"。PreTurn 和 StandaloneTurn 不注入（DoNotInject），因为下一个常规 turn 会完整重建 initial context，注入两份只会浪费 token。

场景 C 用户觉得对话太长，输入 /compact

用户在 TUI 底部输入 /compact。

调用链：slash_dispatch.rs:329 → app_event_tx.compact() → 提交 Op::Compact 给 core → handlers.rs:252 启动 CompactTask。任务按 provider 能力分发：OpenAI 后端走远端 V2，其他 provider 走本地摘要。压缩期间 TUI 状态栏显示 "Compacting context — Making room to continue."，完成后在转录区输出 "Context compacted · 12s"（chatwidget/compaction.rs）。

两种辅助触发

GuardianGuardian 审查上下文超限时（finalize_guardian_input 返回 ContextWindowExceeded），core 先执行 PreTurn 压缩，再用 HistoryTruncation::Allow 重试（turn.rs:325-366）。MidTurn 中 guardian budget 超限也会触发一次压缩，每步只重试一次，防止死循环（turn.rs:759-791）。
模型切换用户切换到窗口更小的模型、且当前用量超过新模型阈值时，core 执行 ModelDownshift 压缩。两个模型的 comp_hash（压缩兼容哈希）不同时，core 执行 CompHashChanged 压缩，保证压缩产物由与历史兼容的模型产出。旧模型压缩失败时，core 用当前模型重试一次（compact_model_fallback.rs）。
Chapter 03 · Local Compaction

路径 B：本地摘要（第三方 provider 的默认实现）

provider 不支持远端压缩（RemoteCompactionSupport::Unsupported）时，Codex 在客户端完成摘要。实现见 core/src/compact.rs。

压缩 prompt：一条伪装成用户消息的指令

本地压缩不引入新协议。core 把内置指令作为 UserInput::Text 追加进历史（compact.rs:121-131），再让模型正常跑一个流式 turn。内置 prompt 全文见 prompts/templates/compact/prompt.md：

You are performing a CONTEXT CHECKPOINT COMPACTION.
Create a handoff summary for another LLM that will resume the task.

Include:
- Current progress and key decisions made
- Important context, constraints, or user preferences
- What remains to be done (clear next steps)
- Any critical data, examples, or references needed to continue

Be concise, structured, and focused on helping the next LLM
seamlessly continue the work.

用户可以用 compact_prompt 配置或 experimental_compact_prompt_file 覆盖这段指令（config/mod.rs:3996-4082）。

设计理由 · 为什么 prompt 说"总结给下一个 LLM"

场景：prompt 如果写成"总结这段对话"，模型会输出"我们讨论了 XX"这类面向人的叙事。文件路径、错误码、下一步命令会在叙事中丢失，压缩后的模型拿不到恢复工作所需的精确信息。

摘要的读者是另一个模型，不是人。这个措辞让模型输出交接清单（进度、决策、待办、关键数据），而不是叙事报告。

请求构造与流式收集

1
记录压缩指令
core 把 summarization prompt 作为 user 消息写入历史副本（record_items，compact.rs:262-267）。core 同时采集 input_goal_ids：用户目标消息的 id 集合，写回时用于保序。
2
构建 Prompt
history.for_prompt() 按模型输入模态过滤历史。executed_tool_calls.attach_to_compaction_prompt() 给每条历史项附上"工具实际执行结果"元数据（request_metadata.rs:12），让摘要模型看到工具真实做了什么。
3
流式请求 + 重试
drain_to_completed 消费响应流。每个 OutputItemDone 立即以 compaction_output: true 元数据写回 live history（PostTurn 阶段例外：先缓存，成功才提交，compact.rs:789-807）。重试复用同一个 ModelClientSession，保住 sticky routing。
4
超限自救
压缩请求本身撞 ContextWindowExceeded 时，history.remove_first_item() 删掉最旧条目再试（compact.rs:317-328）。从头删而不是从尾删，是为了保留前缀缓存。注释原文："Trim from the beginning to preserve cache (prefix-based) and keep recent messages intact"。
5
取摘要文本
core 取最后一条 assistant 消息作为摘要正文，前面拼 SUMMARY_PREFIX。前缀文本见 prompts/templates/compact/summary_prefix.md，内容是"另一个语言模型解决了这个问题并给出了其思路摘要……"。摘要为空时兜底为 (no summary available)。
6
造新历史
build_compacted_history 从新到旧选取保留的 user 消息，总上限 20_000 tokens，再压上摘要消息。摘要恒为最后一项。

保留什么、丢什么

  • 只保留 user 消息：collect_annotated_user_messages 过滤出 TurnItem::UserMessage。assistant 回复、工具调用、reasoning 全部丢弃（compact.rs:557-564）。
  • 排除旧摘要：is_summary_message 剔除以 SUMMARY_PREFIX 开头的消息（compact.rs:584-586）。没有这一步，上次压缩的摘要会被当成用户原话再次保留，第二次压缩后历史里会叠两层摘要。
  • 从新往旧选，预算 20k tokens：最新的用户消息优先保留。放不下时，truncate_text 截断最后一条，并标记 mark_retained_sources_incomplete（compact.rs:669-747）。
  • 非文本内容降级：超预算或含非 InputText 部件的消息只重建文本部分，图片等媒体不克隆（compact.rs:697-711，注释 "never clone discarded media"）。
  • 初始上下文重建而非拷贝：环境信息不进保留列表。MidTurn 时 build_compaction_initial_context 从当前 world state 重新渲染后插入；PreTurn 和 StandaloneTurn 等下一轮自然重建。
设计理由 · 为什么只保留用户消息

场景：用户在第 3 轮说过"不要改 public API"，这个约束只有 user 消息里有。如果连 user 消息都丢，模型只能靠摘要的二手转述。摘要漏掉这条偏好，模型就可能改 public API。

用户消息是需求侧的权威记录：目标、约束、偏好都在里面，而且通常很短。assistant 的推理和工具输出占 token 的大头，但其中的信息模型可以从摘要和工作区状态重建。全部保留会让压缩收益太小，全部丢弃会让模型失去用户原话。20k tokens 上限是安全网：防止用户贴了整份日志的超长消息再次挤爆窗口。

Chapter 04 · Remote Compaction V2

路径 A：服务端压缩（OpenAI 后端默认）

OpenAI / Azure Responses provider 默认启用 RemoteCompactionSupport::V2（capabilities.rs:33-39）。这条路径里"怎么总结"由服务端负责，客户端只做三件事：发触发器、收压缩条目、重组历史。实现见 core/src/compact_remote_v2.rs（1302 行）。

请求侧：历史 + CompactionTrigger

1
瘦身历史（可选）
trim_function_call_history_to_fit_context_window：历史超过模型窗口时，从尾部向前截短过大的 function call output，直到估算 token 落回窗口内（compact_remote_history.rs）。标记文本："Output exceeded the available model context and was truncated"。
2
追加触发器
input.push(ResponseItem::CompactionTrigger {})。CompactionTrigger 是不持久化的请求控制项，放在历史尾部告诉服务端"对这个输入做压缩"（compact_remote_v2_attempt.rs:83；models.rs:1241，注释 "request controls, not durable response items"）。
3
流式请求 + 校验
服务端应返回恰好一个 ResponseItem::Compaction 输出项（含 encrypted_content）。数量不对直接报 CodexErr::Fatal（collect_compaction_output，490-494）。重试上限比常规流式更保守：min（provider 重试数，2）。注释说明原因：压缩可能跑很久，所以传输层重试预算收紧。
4
重组新历史
build_v2_compacted_history = 过滤保留项（预算 64_000 tokens）+ 服务端返回的 Compaction 条目压尾。
设计理由 · 为什么把压缩交给服务端、产出加密条目

场景：走本地路径时，压缩要把整段历史再发一遍，消耗一整轮输入 token 和一整轮输出 token，还占用用户模型的推理配额。服务端压缩是平台内建能力，不经过这条链路。

摘要和检查点以 encrypted_content 加密形式存在：模型读得懂，客户端和用户看不到明文（CompactionCheckpoint::is_usable 检查 id 和非空 encrypted_content，history/src/compaction_checkpoint.rs:36-50）。好处有两个：服务端可以用专用摘要能力，checkpoint 还可以携带对人不透明的状态。代价是非 OpenAI provider 用不了，所以保留 Path B 兜底。

保留过滤规则（is_retained_for_remote_compaction_v2）

条目类型 保留？ 规则细节（compact_remote_v2.rs:557-602）
user 消息（真实用户输入 / hook prompt） ✅ role="user" 且解析为 UserMessage 或 HookPrompt
developer 消息（客户端作者） 条件保留 仅当 RetainClientDeveloperMessages feature 开启且 metadata.client_authored
AgentMessage（多代理间消息） 条件保留 排除子代理进度汇报（MESSAGE / CHANNEL_POST），排除 FINAL_ANSWER，且单条 ≤ 10_000 tokens
工具调用 / 输出 / reasoning / 其他 ❌ 一律不保留

保留集合再从新到旧套 64k tokens 预算（truncate_retained_messages）：整条放得下就整条收，放不下就按 token 截断文本部件后收尾。开启 CompactionImageBudget 后图片也计入预算；图片过大时直接停止回填更早的消息（662-675）。

远端路径与本地路径的关键差异：摘要不是可见的 user 文本，而是 Compaction / ContextCompaction 专用条目。压缩条目类型独立，所以 V2 不需要本地路径那套 "SUMMARY_PREFIX 排除旧摘要" 的逻辑。V2 同样用 insert_initial_context_before_last_real_user_or_summary 做 MidTurn 上下文注入，同样走 advance_auto_compact_window 和 replace_compacted_history 落盘。

模型切换时的压缩兼容性

V2 压缩条目记录产出它的模型哈希（compaction_model_hash）。用户切换模型导致 comp_hash 变化时，两个模型对压缩格式的解读不兼容。core 会在下一轮采样前用上一轮的旧模型再跑一次压缩（maybe_run_previous_model_inline_compact，turn.rs:1374-1425）。旧模型压缩失败时，core 用当前模型兜底重试，并上报埋点 codex.compaction.model_fallback（compact_model_fallback.rs）。

设计理由 · 为什么先用旧模型压一遍

场景：用户从窗口 272k 的模型切到窗口更小的模型。旧 checkpoint 是大模型产出的加密 blob，小模型直接读会读错或报格式错误。core 先用旧模型把历史重新压成新格式，新模型再接续工作。

加密 checkpoint 的读者应与作者是同族模型。comp_hash 就是压缩格式的版本号：两边都给出且不等才触发重压，缺失时不臆测（comp_hash_changed，turn.rs:1337）。

Chapter 05 · Token Budget Path

路径 C：Token Budget — 不总结，直接换新窗口

实验特性 features.token_budget 开启后，压缩语义改变。compact_token_budget.rs（84 行）跳过一切模型侧和服务端侧总结，直接调用 start_new_context_window。

      + 保留的客户端 developer 消息（可选）

零推理成本；工具结果是权威状态
  • 手动 /compact 和自动超限走同一个 run_compact_task_inner：PreCompact hooks → ContextCompaction item started → start_new_context_window → completed → PostCompact hooks。生命周期事件与 A/B 路径一致。注释原文："still modeled as compaction so compact hooks and ContextCompaction turn items observe the same lifecycle"。
  • start_new_context_window（session/mod.rs:4536）用当前 StepContext 重建 initial context 和 world state 快照。模型声明 token_budget 默认值时，core 在模型激活时自动启用该 feature（token_budget.rs:123-159，受订阅计划门槛约束）。
  • 辅助机制：reminder_threshold_tokens 接近阈值时，core 往历史里插一条提醒。窗口耗尽且配置了 auto_compact_fallback_prompt 时，core 先给模型一次"主动收尾"的 fallback prompt，再强制重置（token_budget.rs:161-224，每窗口只发一次）。
设计理由 · 为什么敢于不总结

场景：长会话末尾，用户在第 5 轮口头约定"不要改 public API"，该约定没有写进任何文件。TokenBudget 重置后模型读不到这条约定，可能直接修改 public API。

编码 agent 的状态大头在文件系统和工具输出里，不在对话里。摘要里的"我改了 lib.rs:42"随时可以重新读文件验证。不总结省掉一整轮推理调用，也消除了摘要丢细节导致跑偏的风险。代价同样清楚：只存在于语言层的上下文（用户口头偏好、讨论过但未落地的决策理由）会全部丢失。所以该特性关在 feature flag 后面，由模型声明默认值、按订阅计划放行，不默认开启。

Chapter 06 · Persistence & UX

压缩结果怎么写回、落盘、呈现

replace_compacted_history：一次原子替换

三条路径殊途同归（C 路径走 start_new_context_window 的等价逻辑），最终都调 session/mod.rs::replace_compacted_history（3993-4119）。该函数做六件事：

  1. 给所有新历史项补 item id，把 MCP attribution checkpoint 记到最后一项；
  2. 新历史含 Compaction / ContextCompaction 条目时，写入 compaction_model_hash；
  3. 把压缩之后用户新编辑的 goal 消息按原序补到替换历史尾部，防止压缩瞬间的用户编辑被吞（4041-4059）；
  4. 替换 live history，更新 world state baseline，把 reasoning effort pin 置为 Compacted；
  5. 落盘 RolloutItem::Compacted(CompactedItem)。内容包括 replacement_history、window_number、三个 window id、compaction_response_id、token usage 快照和 resume 元数据。随后追加 WorldState / TurnContext / 设置事件项；
  6. 排队一个 SessionStartSource::Compact 的 session-start hook，重算 token usage，发出"长线程多次压缩会降低准确性"的 Warning 事件。

恢复会话（resume）时，rollout_reconstruction.rs 只认"最新一条带 replacement_history 的 Compacted"作为完整历史基线，再重放其后的输入事件（select_input_compaction，61-140）。旧格式压缩项（无 window_number）走兼容分支。

AutoCompactWindow：压缩窗口编号

每次压缩时 advance_auto_compact_window() 递增 window_number，并滚动一组 UUID（first / previous / current window id）。这组编号有三个用途：

  • BodyAfterPrefix 口径下，计算"前缀之后新增 token"的基线（prefill_input_tokens，服务器观测值优先于估算值）；
  • resume 时，判断压缩边界与 replay 段的一致性；
  • 限制 token-budget 提醒和 fallback prompt 每窗口只发一次（claim_* 一次性位）。

用户能看到什么

STATUS
状态栏：Compacting context — Making room to continue.（独立计时）
TURN ITEM
ContextCompaction item started → completed，转录区显示 "Context compacted · 12s"
WARNING
"Heads up: Long threads and multiple compactions can cause the model to be less accurate. Start a new thread when possible to keep threads small and targeted."（compact.rs:404-407）
HISTORY
对话记录照旧展示；压缩条目和摘要写入 rollout 文件（~/.codex/sessions/*.jsonl），可用 --resume 恢复
设计理由 · 为什么压缩也要发 PreCompact / PostCompact hooks

场景：用户写了 PreCompact hook，用于在压缩前把关键笔记追加进历史。如果 TokenBudget 路径不走 hook，这条脚本对 Path C 失效，上下文会被"隐形清空"。

压缩是有损的上下文操作，扩展系统应有机会拦截。PreCompact 返回 Stopped 时整个压缩放弃，PostCompact 也可中止。三条路径统一走 hook（包括不做总结的 TokenBudget 路径），用户脚本监听一对事件即可感知全部压缩行为。

Chapter 07 · Design Decisions

为什么这么设计，不这么做会怎样

决策阈值设 90%（硬上限 95%），而不是 100%
为什么

压缩请求本身要消耗上下文（整段历史 + 指令），服务端还要给输出留余量。effective_context_window_percent（默认 95）为系统提示、工具开销和模型输出预留余量。90% 的压缩阈值再留 5%，让"压缩那一轮"本身不超窗。

不这么做会怎样

场景：第 40 轮对话，token 用量到 91%。压缩这一轮要把整段历史再发一遍。若阈值设在 100%，压缩请求本身就超限，core 只能靠"删最旧条目重试"兜底；极端情况下压缩请求发不出去，会话卡死，用户只能手动开新线程。

决策本地压缩失败后，从头删历史再试，而非从尾删或放弃
为什么

LLM 推理缓存是前缀式的：删最早的一条，剩余前缀仍可能命中缓存；且最新消息（当前任务状态）价值最高。注释原话："Trim from the beginning to preserve cache (prefix-based) and keep recent messages intact"（compact.rs:319）。

不这么做会怎样

场景：压缩请求超限，历史尾部是刚跑完的 cargo test 结果。从尾删会丢掉这段结果，摘要把"测试已通过"记成"未验证"。直接放弃会让会话不可用。从头删只丢最早的环境信息，近期状态保留。

决策摘要伪装成 user 消息 + SUMMARY_PREFIX 标记，而非新类型
为什么

本地路径要兼容任意 OpenAI 兼容 provider，这些 provider 只认标准 message role。前缀标记告诉下游：这是机器交接摘要，不是用户新指令。下一次压缩也能用 is_summary_message 按前缀把旧摘要从保留列表剔除。

不这么做会怎样

场景：第二次压缩时，历史里有上一次压缩的摘要。没有 SUMMARY_PREFIX，这条摘要会被当成"用户说过的话"保留进新历史，摘要套摘要，模型分不清哪个是权威。用自定义类型则非 OpenAI 后端不认。

决策MidTurn 压缩把 initial context 插回历史，PreTurn 不插
为什么

MidTurn 后紧接着还是同一段对话的采样。模型按训练预期"摘要是历史最后一项"，所以环境上下文应保留在正确位置：最后一条真实用户消息之前。PreTurn / StandaloneTurn 的下一个常规 turn 本来就完整重建 initial context，插进去就是重复（InitialContextInjection 文档，compact.rs:61-69）。

不这么做会怎样

场景：模型在一个 turn 中途触发压缩，下一段采样马上开始。不注入 initial context，模型不知道 cwd 和 git 分支，apply_patch 可能写错路径。PreTurn 注入则同一内容出现两份，吃掉压缩省下的 token。

决策持久化整条 replacement_history，而非只存摘要文本
为什么

resume 重建需要精确的 item 序列（含 id、metadata、mcp attribution）。CompactedItem.replacement_history 让"最新一条完整压缩"可以直接作为 replay 基线，不用重新推导保留规则（rollout_reconstruction.rs:57-140）。

不这么做会怎样

场景：用户压缩后关掉终端，三天后执行 codex resume。若只存摘要文本，resume 要重新执行保留算法，任何版本差异都会重建出与压缩时不一致的历史，"续跑"变成"跑一条分叉的历史"。

决策压缩条目记录 comp_hash；模型切换先按旧模型重压
为什么

远端压缩产物是加密 blob，格式与产出模型绑定。切换到 comp_hash 不同的模型时，core 先用旧模型把历史重新压成兼容形态，新模型才能正确消费（turn.rs:1370-1425）。

不这么做会怎样

场景：会话中途用户从模型 A 切到模型 B，两者 comp_hash 不同。模型 B 直接读模型 A 的加密 checkpoint，请求被拒或上下文静默错乱。用户看到的症状是"换模型后模型突然失忆、行为怪异"。

一句话总结：Codex 的压缩是"带检查点的有损历史重写"。阈值（90% 软 / 95% 硬）预防超限。三条实现路径按 provider 能力降级：服务端加密 checkpoint → 本地文本摘要 → 无总结窗口重置。保留策略只留需求侧的用户消息加一段交接摘要。写回时同步持久化整条替换历史，保证 resume 一致。所有取舍围绕同一目标：让对话能持续下去，同时把"忘掉的代价"控制在摘要质量这一个变量上。
