0总览：一条信任链，两条数据流

信任链：main.go 启动时构造一次 scope.Scope 塞进 ctx， 之后 loop / 工具 / Store 全部从 ctx 取——Store 的 API 上干脆没有 tenant 参数，模型给的任何参数都碰不到隔离边界。
写流：loop 内 5 个 append 点 → Rec.Append → SQLite； 读流：--resume → LoadHistory（校验 tenant）→ 重建 history。

1信任边界：为什么必须是 ctx 注入 — 而不是参数或全局变量

问题：模型参数不可信

  • • 工具入参是模型生成的 JSON——它会幻觉出 session_id=别人的、path=../../etc/passwd
  • • 如果 tenant/session 是参数，隔离靠模型自觉，等于没有隔离
  • • ctx 值由调用方代码写入，模型无法触碰——隔离是函数侧事实

现成的先例：historyCtxKey

  • • agent.go 已用同款机制把 history 快照塞进 toolCtx 供 task 工具读
  • • scope 是同一招的推广：WithValue + 私有 key + FromContext 读取
  • • runCtx 从父 ctx 派生 → 子代理自动继承，零额外布线

为什么不是全局变量

  • • 云端多租户并发时全局 tenant 是数据竞争的温床
  • • ctx 绑定每次调用的生命周期：中断/超时天然传播
  • • 缺 scope 显式报错——没有「默认租户」兜底，装配 bug 第一天就暴露

为什么 Store 不带 tenant 参数

  • • CreateSession(ctx, meta) / Append(ctx, msg)——签名里没有 tenant 可填错
  • • 同一个 Store 实例服务主代理与所有子代理，靠 ctx 区分写入目标
  • • LoadHistory 内部校验 session.tenant_id == ctx.TenantID，越权读返回错误

2存储 Schema — 两张表，raw transcript 语义

DB 记录的是发生过的一切（raw transcript），不是内存 working context 的镜像。这与将来的 context compact 正交：压缩改写内存 history，落库的原文不动，摘要本身作为新消息再落库。

sessions
id TEXT PRIMARY KEY -- UUIDv7 时间有序，ORDER BY id ≈ 创建序
tenant_id TEXT NOT NULL · idx
parent_id TEXT → sessions.id -- 子代理挂父会话
kind TEXT -- main | subagent
title TEXT -- 首条 user 消息回填
model TEXT · workspace TEXT
created_at · updated_at -- 每次 append 刷新
depth INTEGER -- 0 主代理
messages
id INTEGER PRIMARY KEY AUTOINCREMENT -- bigint，id 即全局时序
session_id TEXT NOT NULL → sessions.id · INDEX(session_id, id)
role TEXT · content TEXT · thinking TEXT
tool_calls TEXT -- JSON 原文，含 id/name/arguments
tool_call_id TEXT · is_error INTEGER
created_at INTEGER
— 无需 seq 列：同会话内 ORDER BY id；多会话交错写入时 id 是全局序

3模块拆解 — 按依赖序排列，逐个审批实现

M1

internal/scope — 租户上下文基元

新包 · ~70 LOC · 依赖：无

为什么最先做：Store、tools、装配层都读它，是整张图的信任根，必须先冻结形状。 为什么带 Workspace：租户隔离不止会话数据——文件系统是另一半（M6 消费它）。 为什么 FromContext 返回 error 而非默认值：默认租户意味着装配漏了也能跑，数据就悄悄写错租户；显式失败让 bug 当天暴露。

type Scope struct { TenantID string // 租户（本地固定 "local"） SessionID string // 当前会话；子代理 spawn 时被替换 Workspace string // 租户工作区根（本地 = cwd） } func WithScope(ctx, s Scope) ctx // 注入（main/TUI 用） func FromContext(ctx) (Scope, error) // 读取；缺失 → error func WithSession(ctx, id string) ctx // 仅换 SessionID（subagent 用）
  • roundtrip：注入后可读回；WithSession 只换 SessionID、不动 TenantID/Workspace
  • 缺失时 FromContext 返回 error；空 Scope（零值字段）也视为缺失

审批点：字段集合（TenantID/SessionID/Workspace 三个够不够）、缺失即错的策略。

M2

internal/session — Store 接口与类型

新包 · ~90 LOC · 依赖：M1 + agent.Message

为什么接口先行：本地/云端同一调用面，未来换 Postgres 只换实现； 接口签名里没有 tenant 参数——隔离边界在参数层面就不存在。 为什么 Append 也从 ctx 读 SessionID：这样同一个 Store 实例能服务主代理和所有子代理（M7 零布线收益）， 也天然满足「写入目标由函数侧 ctx 决定」的隔离要求。 为什么 LoadHistory 收 sessionID 参数但 tenant 走 ctx：resume 的会话 ID 是用户合法输入（--resume 参数）， tenant 是权限边界——前者可选，后者必须注入。

type Store interface { CreateSession(ctx, meta Meta) (Session, error) // tenant 取 ctx Append(ctx, msg agent.Message) error // tenant+session 取 ctx；error→fail turn LoadHistory(ctx, sessionID string) ([]agent.Message, error) // 越租户 → error ListSessions(ctx, limit int) ([]Session, error) // 隐式按 ctx 租户过滤 Close() error } type Meta struct { ParentID, Title, Model, Workspace, Kind string; Depth int }
  • 接口即文档：签名评审通过后再写实现
  • agent 包内另定小接口 type Recorder interface{ Append(ctx, Message) error }——Store 结构满足，agent 不反向依赖 session（无环）

审批点：接口面宽窄（五个方法够不够）、Kind/Depth 字段是否必要、Meta 字段。

M3

internal/session/sqlite — SQLite 实现

新包 · ~280 LOC + 测试 · 依赖：M1 M2 · 新依赖 modernc.org/sqlite

为什么 modernc.org/sqlite 而非 mattn/go-sqlite3：纯 Go 无 CGO——本地交叉编译、云端 distroless 镜像都不受 C 工具链拖累；性能对「每条消息一行」的写入量绰绰有余。 为什么 WAL + 单写者连接：WAL 让读不阻塞写；SetMaxOpenConns(1) + busy_timeout 把 SQLite 的单写者限制变成显式串行，杜绝 SQLITE_BUSY 偶发。 为什么用 user_version 做迁移：两行 pragma + 一个 migration 函数，不引入迁移框架。 为什么 tool_calls 存 JSON 原文：schema 演化不动表结构；LoadHistory 反序列化回 []ToolCall。 ID 方案（已确认）：sessions.id = UUIDv7——时间有序（ORDER BY id ≈ 创建序， 列表/取最新零额外索引成本）、随机位保证多实例生成不冲突；用 google/uuid 的 NewV7()（唯一新增依赖）。messages.id = bigint AUTOINCREMENT——id 本身就是全局时序， 省掉 seq 列与 MAX(seq)+1 子查询，Append 退化为纯 INSERT。

// 打开即迁移；失败即启动失败（不写半拉子记录） func Open(path string) (*Store, error) // Append：一条 tx 内 INSERT messages + UPDATE sessions.updated_at（id 自增即时序） // LoadHistory：先查 session 校验 tenant，再按 id 升序回放全量消息
  • 全部测试跑 :memory: 库，不落地文件
  • append 顺序与 id 单调一致；tool_calls / thinking / is_error 完整 roundtrip
  • UUIDv7 生成：两次 CreateSession 的 id 严格递增且可解析出时间
  • LoadHistory 越租户被拒；ListSessions 只见本租户
  • 并发 append（模拟子代理+主代理同写）不丢序、不报 BUSY

审批点：driver 选型、google/uuid 依赖、schema 定稿。

M4

Agent loop 逐条落库

改 agent.go · ~+20 LOC · 依赖：M2（agent.Recorder）

为什么是字段而不是 hook：现有 hook 点覆盖不全——assistant 消息没有对应 hook， 且 hook 语义是「只读观察/注入」，Append 是写入职责。与 OnToolCall/OnInject/OnToolResult 同为 Agent 字段，风格一致；用接口而非 func 是因为要返回 error。 为什么 Append 失败就 return err：已确认 fail-the-turn；partial history 里已落库的部分不丢， 正好与 InterruptedError 的部分进度语义对齐。 成本：5 个 append 点各一行 a.record(ctx, msg)，封装在一个私有方法里判空。

type Recorder interface { Append(ctx context.Context, msg Message) error } // Agent.Rec Recorder · 零值 nil = 不记录（测试/裸用零开销） func (a *Agent) record(ctx, msg) error { /* Rec==nil → nil */ }
  • fake LLM + spy Recorder：5 类 append 全到达、顺序与 history 一致
  • Recorder 返回 error → Run 返回 error，且之前 append 的已落库
  • Rec=nil 时行为与现状完全相同（回归）

审批点：字段形态（接口 vs func）、失败即返的边界。

M5

装配：main.go + config + TUI 上下文

改 3 文件 · ~+90 LOC · 依赖：M1–M4 · 此处功能首次可用

职责：开库 → 建会话（tenant="local"、workspace=cwd）→ 构造 Scope → a.Rec = store → 把 scope+store 传进 TUI。 时序保证：进程启动即建 session（--resume/--continue 除外，见 M8）—— SessionID 在 tea.NewProgram 之前焊进 scope，全程不变，每条 append（含 TUI 自落的 system/user） 都进同一 session。 TUI 侧：Model 持 scope 与 store；submit() 把 context.Background() 换成 scope.WithScope(bg, m.scope) 再 WithCancel；system prompt 与每条用户消息由 TUI 自己 Append （它们不经过 loop，但语义上「凡进 history 皆落库」要一致）。 为什么 DB 打开失败要启动即死：半拉子记录比没有记录更难排查；本地文件打不开属于装配错误。 配置：RUNE_DB 覆盖；默认 ~/.rune/sessions.db （各平台统一，目录随启动自动创建）。

// tui.New 签名扩展：传入初始 history + scope + store func New(a *agent.Agent, info Info, initial []agent.Message, sc scope.Scope, st session.Store) *Model
  • 跑一轮对话后 sqlite3 能查到完整消息序列（含 tool 段）
  • Ctrl+C 中断的轮次：已 append 的部分在库，占位结果也在
  • 无 DB 路径权限/坏盘 → 启动报错而非静默降级

审批点：默认路径选址、tui.New 参数形态（散参 vs 结构体）。

M6

工具侧 scope 化：文件与命令的租户边界

改 fs.go / shell.go · ~+50 LOC · 依赖：M1 · 可与 M5 并行

为什么这是隔离闭环的另一半：Store 侧保证会话数据不越租户； 文件侧要保证模型给的 path / command 碰不到别的租户目录—— 本地 workspace=cwd 行为不变，云端每租户一根目录即物理隔离。 做法：resolve(scope.Workspace, argPath) = Join+Clean+ 拒绝逃逸根目录的相对/绝对路径；RunCommand 加 cmd.Dir = ws。 注意：shell 命令可用 cd/绝对路径 逃逸 Dir 限制——本地单租户无碍， 云端真隔离需要容器/沙箱兜底（本计划不覆盖，列为已知边界）。

  • ../../etc/passwd、绝对路径越根 → 明确错误回填给模型
  • scope 缺失 → 工具报错（不信任裸跑）
  • workspace=cwd 时全部现有行为回归通过

审批点：是否本期做；逃逸规则严格度（绝对路径一刀切拒 vs 允许根内绝对路径）。

M7

子代理入库

改 subagent.go · ~+40 LOC · 依赖：M1–M4（可晚于 M5）

为什么几乎免费：runCtx 本就派生自父 ctx——tenant 自动继承； task.Run 里三步：CreateSession(parent=ctx.SessionID) → WithSession 换绑 → sub.Rec = 同一个 Store。 嵌套自动成立：child() 按值拷贝 Tool 字段，depth-2 的子代理其父 ID 就是 depth-1 的会话。 Tool 加一个字段：Store（CreateSession 最小面），Wire 签名不动。 UI 联动：子会话 kind=subagent + depth 落库，事后可按 parent_id 还原调用树。

初始历史的落库：子会话的首批消息不经过 loop 的 append 点（initialHistory 在 Run 之前组装），由 task.Run 在 spawn 后显式 Append。两型有别： general_purpose 全落 system+task 两条；normal 型不整份复制父会话快照 （嵌套时 O(n²) 膨胀），只落「继承标记 + task 消息」，完整上下文经 parent_id 链回溯。

  • spawn 后子会话 parent_id/kind/depth 正确
  • 子代理消息落在子 session，不污染主会话
  • 子会话首批消息完整：general_purpose = system+task；normal = 继承标记+task
  • 嵌套 spawn 的 parent 链正确；Store=nil 时行为与现状一致

审批点：Tool 加 Store 字段的形态；normal 型「继承标记不落全量快照」的取舍；子会话 title 取任务描述前 N 字符。

M8

resume / continue

改 main.go + tui · ~+80 LOC · 依赖：M3 M5

CLI：--resume <id> 精确恢复；--continue 取本租户最近会话。 语义：续写同一 session——不新建会话，LoadHistory 回放为初始 history， 之后的新消息继续 append（id 自增接续，天然有序）。这是「会话」而非「会话副本」的语义，审计链不中断。 title：首条 user 消息截前 40 字符，第一次 append 后 UPDATE 回填； --continue 无会话时退化为新会话。 已知边界：resume 回放的是 raw transcript（含 compact 前原文）——将来上 s08 压缩管线时自然重新压缩，无额外工作。

  • 写入→退出→--resume：history 逐条一致，tool_calls 配对完整可直接续跑
  • --continue 选中最近 updated_at 的本租户会话；跨租户 ID 拒绝
  • resume 后新消息 id 继续递增，回放顺序无歧义

审批点：flag 命名与交互（是否要 /sessions 列表选择器，本期建议不做）。

5已知边界与开放问题

shell 命令的真隔离

  • • cmd.Dir 只定工作目录，cd / + 绝对路径仍可逃逸
  • • 云端多租户真隔离要靠容器/沙箱（每租户独立进程或命名空间）
  • • 本期结论：ctx 隔离覆盖数据面，OS 面留给部署形态

云端形态的缝

  • • SQLite 单写者：多租户高并发写入会成为瓶颈
  • • Store 接口已是缝——换 Postgres 时只动 M3 实现
  • • scope 由「请求入口」构造（HTTP auth → tenant），main.go 是现在的入口

与 s08 compact 的接口

  • • DB=raw transcript：compact 裁掉的原文保留，摘要作为新消息落库
  • • resume 回放原文，下一轮 PreChat 前跑压缩即可——无额外联动
  • • L4 的 write_transcript 直接就是这张 messages 表，天然兑现

故意没做的

  • • 会话列表 UI（/sessions 选择器）——M8 用 CLI flag 先跑通语义
  • • 消息事件溯源/回放 UI、跨 session 搜索
  • • 加密 at-rest、消息脱敏——上了云端再谈

审批方式：按 M1→M8 顺序，逐模块确认后实现 · 每个模块自带验收测试
