RuneHarness 对标旗舰 Agent 能力差距分析

结论先行 · Executive Summary

七条结论，读这一节就够

评级口径：无 基本持平或领先 · 小 有差距不致命 · 中 局部场景受限 · 大 存在代差。总评：七个维度中四个为大差距，但落后的面集中在 「生态、并行、权限、分发」四条线上；压缩与持久化的底层设计反而领先于多数对标对象。

C1无 MCP、无插件加载点：工具生态是最大代差 大

事实
模型可调 12 个工具，全部在 main.go:187-243 与 cmd/runebot/main.go:154-186 硬编码装配；全仓无 MCP/plugin/extern tool 命中（go.mod:5-18 无 SDK）。四家旗舰全部支持 MCP。
为什么
工具生态决定 agent 能触达什么。数据库、浏览器、SaaS 连接器在 RuneHarness 上不可达，只能靠 run_command 走 shell 变通——易错且权限判定粗糙。
不做会怎样
用户真实工作流一旦需要外部工具即流失；这是四家旗舰的共同基线，不是加分项。

C2子代理纯串行：多任务委派吞吐落后一整代 大

事实
task 是普通工具，Run 同步阻塞跑完子 loop 才返回；同批多个 task 按序执行 （internal/subagent/subagent.go:149-258；工具批为顺序 for 循环 internal/agent/agent.go:294-355）。无 agent 间消息、无 fan-out。
为什么
Claude Code 有 /batch 5–30 个 worktree 并行与 agent teams；Cursor 一条消息多个 Task 即并行； Codex 有 agent message board。「委派 N 个独立任务」是最常见的旗舰用法。
不做会怎样
N 个任务耗时 ×N；在探索-委托型工作流上与 CC/Cursor/Codex 无可比性（仅与 OpenHands 同档）。

C3零分发工程：用户拿不到，能力全部归零 大

事实
无 Makefile、无 goreleaser、无 CI workflow、无 Dockerfile、无 install 脚本、无版本号； 安装 = 自行 go build。竞品均有安装脚本/包管理/发布二进制，另有桌面、Web、IDE、SDK 等形态。
为什么
分发是产品闭环的第一环。依赖面极简（纯 Go、modernc sqlite 无 cgo），补齐成本在七项差距里最低。
不做会怎样
没有用户就没有反馈循环；本文其余所有差距的修复优先级都建立在「有人用」之上。

C4权限无持久化、无模式：确认疲劳 + headless 卡死 大

事实
三道闸实现本身不差（硬拒绝/前缀白名单/元字符升 Ask，internal/permission/permission.go:1-7,58-99）， 但批准一次不写回规则，同一命令每次弹；无 plan/acceptEdits/bypass 档（permission.go:14-24,36）； headless 下 AskTimeout 默认 120s 超时按 deny（internal/runner/slot.go:220-267）。
为什么
CC 有 6 种权限模式 + Tool(specifier) 规则；Codex 有 4 档审批策略 + OS 级沙箱； Cursor 有 3 种 Run Modes + classifier。确认疲劳是 agent 产品头号体验杀手。
不做会怎样
交互用户被重复弹窗淹没，最终要么放弃要么设法绕开权限；headless 长任务在第 120s 静默死亡。

C5LLM 调用失败一律致命：恢复逻辑还是 loop 里的 TODO 大

事实
重试/退避/429 处理是 internal/agent/agent.go:223-246 内的明列 TODO； finish_reason=length 截断恢复同为 TODO（agent.go:273-279）。 TUI 侧 autoResumed 只覆盖 maxSteps 撞墙（internal/tui/model.go:554-564）。
为什么
429、断流、端点抖动在真实使用中必然出现。一次抖动杀死数小时的委派任务，是 headless 场景不可接受的失效率。
不做会怎样
runebot 的「无人值守长任务」定位不成立；此 TODO 同时是 P2 多副本扩展的前置。

C6会话无写锁：session_leases 建了表未接逻辑 中

事实
schema 已有 session_leases 表（internal/session/sqlite/sqlite.go:121-183）， 但两个 TUI 进程可对同一 session id 并发 Append，互不感知；唯一例外是 cron 的 workspace flock。
为什么
append-only 账本的前提是写者串行。并发写会让全局时序（自增 id）在逻辑上交错，resume 回放可能拼出非预期视图。
不做会怎样
多实例/多进程共库场景（runebot + TUI 同时开）会静默损坏账本；也是水平扩展的硬性前置。

C7压缩与持久化是长板，不应跟着竞品重做 无

事实
「offload 卸载 + 滚动摘要」双层、过期结果识别、压缩熔断、fork 水印零拷贝继承、append-only 可回放账本、 崩溃读侧自愈——这套设计比「到顶一刀切摘要」细一档；记忆侧双轨写入 + 全量流水 + tombstone 的结构完整度 接近 CC 的记忆体系。
为什么
差距报告不是全盘否定清单。把追赶资源压在 C1–C4 上回报更高；压缩维度的短板是召回侧（无检索）而非压缩本身。
不做会怎样
若误把长板重做，会消耗本应用于生态与分发的工时，且未必做得更好。

第 2 章 · 维度一

会话压缩 / 上下文管理 小

RuneHarness 现状

  • 三段式视图切分：发送形态 = system + 首部（前 3 条真实用户消息、8K 预算、第 1 条钉死）+ 最新摘要 + 尾部（最近 40 个用户轮、40K 预算），压缩只动中段（internal/compact/segment.go:6-12； internal/session/view.go:43-47）。
  • 三条阈值线：提醒线 W−56K、强制压缩线 W−33K、阻断线 W−20K，MinWindow=64K （internal/compact/compactor.go:21-52）。
  • 卸载层先行：压缩时先把中段 >1K 的工具结果落 blob 换索引；被较新同键调用取代的过期结果无论大小都卸载； tool_calls 参数里 >2K 的字符串字段换索引（internal/compact/offload.go:17-21,31-99,171-192）。
  • 写侧回填规范化：单条 >50K 字符或整批 >200K 字符落 blob 换 blob:// 指针； >400K 硬截断（internal/compact/backfill.go:17-22,39-94）。
  • 熔断与自愈：摘要失败连续 3 次断开自动通道（internal/compact/maintain.go:15-20,115-144）； 端点报错里的真实窗口经 NoteLimit 向下钳进配置并持久化 （internal/agent/agent.go:202-208；internal/compact/maintain.go:146-173）。
  • 子代理压缩：共享压缩器；normal 型 spawn 前对继承快照先卸载不摘要（Prime， internal/compact/maintain.go:66-81；internal/subagent/subagent.go:231-235）。

对标速览

竞品承重事实
Claude Code
  • 默认窗口 200k；auto-compact 近阈值自动触发，/autocompact 可调触发窗口。
  • 压缩后「存活物」语义明确：CLAUDE.md/path 规则重新注入，skill 只留实际调用过的，文件读取恢复一行占位。
  • /context 可视化占用；/rewind 可部分摘要回滚。
Codex CLI
  • /compact 手动压缩、/recap 立即总结；core 有 AutoCompact/CompactionTrigger 机制，压缩生成 checkpoint 替换历史。
  • PreCompact/PostCompact 钩子可拦截；触发阈值的具体 token 数未公开。
Cursor
  • CLI /summarize（别名 /compress）；hooks 体系含 preCompact。
  • 内置 Explore/Browser 子代理把高噪声输出隔离在子上下文；桌面端自动压缩阈值未公开。
OpenHands
  • Condenser 可编程：默认 LLMSummarizingCondenser，max_size/keep_first 参数化，可继承自定义策略。
  • Agent Server 暴露强制压缩端点；CLI/Cloud 默认参数未公开。

差距评级：小

压缩机制本身不落后：offload + 摘要双层、过期结果主动识别、压缩熔断、端点真实窗口反哺——这套组合的精细度超过 「单次摘要替换历史」的主流做法。真实差距在两点：token 估算是字符粗估（非锚点段，非 ASCII 口径 0.7 tok/字， internal/compact/estimate.go:19-56），阈值线实为「估算线」；以及卸载后只有 blob:// 指针，模型需主动 read_file 取回，无自动召回。

建议动作

应借鉴 CC 的「压缩后存活物」清单：把项目规则（AGENTS.md/CLAUDE.md 类）、已声明 skill 摘要列入压缩后重注入集合； 应逐步提高真实 usage 锚点覆盖率，把估算段收窄。

为什么：压缩后规则丢失会让 agent 在长会话后半段「忘记项目约定」；估算偏激进会导致早压（丢信息）或晚压（撞限）。

不做会怎样：长任务后半段行为漂移；极端场景 ErrContextFull 拒发整轮的问题仍在。

第 3 章 · 维度二

子 agent / 并行 大

RuneHarness 现状

  • task 工具 spawn 子代理：独立 agent.Agent + 独立 Registry + maxSteps=40 + 兜底 10min 超时 （internal/subagent/subagent.go:44-51,148-258）。
  • 两型：general_purpose（全新上下文）与 normal（继承委派时刻的历史快照， internal/subagent/subagent.go:28-35,120-146,269-280）。
  • fork 水印零拷贝：子会话只写 fork 控制行（父会话 + 水印行 id），读侧拼父视图 + 子行 （internal/subagent/subagent.go:209-229；internal/session/view.go:28-32）。
  • 纯串行：task 是普通工具，Run 同步阻塞；同批多个 task 按序执行，无 fan-out （internal/subagent/subagent.go:149-258；internal/agent/agent.go:294-355）。
  • 嵌套 depth 上限 2（RUNE_SUBAGENT_NEST 开启时）否则 1（internal/subagent/subagent.go:110-118,282-290）； 子代理复用同一权限三道闸（main.go:158-165,234-240）。
  • 上下文隔离：只有最后一条 assistant 文本回传（internal/subagent/subagent.go:322-331）； 子会话完整落库可审计（internal/subagent/subagent.go:198-207）。

对标速览

竞品承重事实
Claude Code
  • 内置 Explore/Plan/general-purpose 子代理，独立上下文与工具集；自定义 subagent 五种来源（项目/用户/托管/CLI/插件）。
  • /batch 把大改动拆成 5–30 个独立 worktree 并行执行；/background、/fork 后台会话；agent teams 跨会话互发消息。
Codex CLI
  • /agents command center、/subagents 切换；代理间经 agent-message-board 交换消息。
  • MultiAgentMode 两档 + agent-roles 角色定义；Codex Web/codex cloud 云任务并行。
Cursor
  • Task 工具委派；一条消息内多个 Task 调用即并行；前台阻塞/后台（is_background）两模式。
  • swarm 隔离（各自 worktree 或云 VM）；/in-cloud 云子代理；Projects coordinator 规划并委派。
OpenHands
  • TaskToolSet 委派 sub-agent，同步阻塞，官方明示「designed for sequential blocking tasks」；任务可凭 task_id 续跑。
  • Parallel Tool Execution 只并行单回合内多工具调用；无代理间消息；Agent Canvas 的并行在应用层而非进程内。

差距评级：大

继承机制（fork 水印）与权限复用是干净的自洽设计，但执行模型停留在「一次一个阻塞式委派」。对 CC/Codex/Cursor 而言并行 fan-out、后台 agent、代理间消息已是标配；RuneHarness 只与 OpenHands 同档。差距不在 spawn 能力，在并发与编排。

建议动作

应先实现同批多个 task 调用的并发执行 + 结果按序汇聚（工具批处理从顺序 for 循环改为 errgroup 式 fan-out）；worktree 隔离、代理间消息可后置。宜给子代理结果加结构化 schema 选项而非仅回传末条文本。

为什么：多任务委派是旗舰场景的高频用法；并发化只动工具批调度，不触碰隔离与权限模型。

不做会怎样：N 个任务耗时 ×N；在「探索-委托」工作流上与三家旗舰无可比性，该维度差距会随竞品继续演进而扩大。

第 4 章 · 维度三

持久记忆 小

RuneHarness 现状

  • 独立库 ~/.rune/memory.db（internal/config/config.go:153-161），三表： memories（当前信念视图）+ memory_log（upsert/supersede/delete/merge-into 全量流水）+ memory_meta（游标/锁/熔断）（internal/memory/store.go:1-5）。
  • 空间模型三档（workspace/subject/tenant）+ 画像驱动（coding/companion/generic 内置）， Profile 决定空间维度、类型辞典、写工具开关、注入配额、dream 节奏 （internal/memory/store.go:16-23,107-122；internal/memory/profile.go:26-39,47-50,166-174）。
  • 读路径：UserPromptSubmit hook 把索引 + 常驻正文注入本进程该会话第一条 user 消息； 记忆变更标脏，下一条 user 消息带新索引（internal/memory/memory.go:73-96,98-104）。
  • 写路径双轨：模型 memory 工具五操作（internal/memory/tool.go:14-80,82-177）+ dream 后台消化（锁/熔断/冷却/物料四门 + ops 校验 + 事务落库，internal/memory/dream.go:33-101,152-211）。
  • 凭据两道闸：提示词 DoNot 清单 + LooksLikeSecret 扫描（internal/memory/secrets.go:20-21； internal/memory/dream.go:304-306）。
  • 短板：无检索——读路径只有「索引注入 + 按名取/按实体查」，GET /svc/search 直接 501 （internal/gateway/handlers.go:298-300）；注入只进首条 user 消息，颗粒度为轮。

对标速览

竞品承重事实
Claude Code
  • CLAUDE.md 四级层级（企业/用户/项目/本地）逐级加载，@path 导入最深 4 跳；原生识别 AGENTS.md。
  • Auto memory 自动写 MEMORY.md，每会话注入前 200 行或 25KB；.claude/rules/ 支持 glob 触发。
Codex CLI
  • AGENTS.md 一等支持（解析注入 + /init 生成）。
  • Memories 两阶段流水线：Phase 1 从历史并行提取结构化记忆（secret 脱敏），Phase 2 由 consolidation sub-agent 合并进 ~/.codex/memories/（git 基线）。
Cursor
  • Rules 四类（.mdc frontmatter alwaysApply/description/globs，Always/智能/glob/手动四种应用方式）+ User/Team Rules + AGENTS.md。
  • 自动记忆（Memories/跨会话自动学习）在当前官方文档索引中未见——未公开。
OpenHands
  • Persistent Memory opt-in（默认关）：用户层 + 项目层两层 MEMORY.md 索引注入 <MEMORY_CONTEXT>，索引上限约 6000 字符。
  • 注入内容标记 <UNTRUSTED_CONTENT> 防注入；未开记忆时以 AGENTS.md 为唯一指引。

差距评级：小

写入侧结构完整度已接近甚至局部超前：全量变更流水、tombstone 防复活、ops 校验挡幻觉写入、空间/画像二维模型—— Codex 的 consolidation 流水线是相近思路。真实缺口在召回侧：没有任何检索机制（全文或向量），记忆只能「整体索引注入 + 按名精确取」，且注入锚定在会话首条 user 消息。

建议动作

应先用 SQLite FTS5 落地 /svc/search 与 memory 工具的 search 操作（库内已有表，无新依赖）， 再议向量索引；宜把「相关度触发的条目注入」作为第二步，而非一步到位改注入模型。

为什么：记忆只写不查等于成本沉没；FTS5 在现有存储层上即可补齐 80% 召回需求。

不做会怎样：记忆库增长反而稀释索引注入的信号；companion 画像（默认不暴露写工具）下用户即时纠正只能等 dream 消化。

第 5 章 · 维度四

RuneHarness 现状

第 9 章 · 路线图

补齐顺序：先堵风险，再追生态，后扩规模

排序准则：P0 = 阻断真实使用或风险随时间放大的缺口；P1 = 决定体验上限与分发可达性的缺口； P2 = 规模化与远程化的缺口。工作量为粗估人日，仅供相对排序。

项目对应维度/差距预计工作量依赖价值一句话
