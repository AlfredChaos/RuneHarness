RuneHarness 系统架构总览

一个 append-only 账本驱动的 agent 内核，加上一层可插拔的装配层与前端轨。 本文覆盖：分层模型、功能模块、核心流程（时序与状态迁移）、事件目录、 以及 SOUL.md 身份槽位——它与既有的压缩、记忆、后台任务、调度四份设计文档配套。

版本 v1.0 范围：现状 + 网关规划（docs/runeharness-gateway-plan.html） 基线：go 1.2x · OpenAI 兼容端点 · SQLite · Bubble Tea
怎么读
  1. 建立整体认知 → 第 1、2 章（分层 + 模块）。
  2. 改某条流程 → 第 3 章时序图 + 第 5 章状态机。
  3. 接前端 / 排障 → 第 4 章事件目录。
  4. 理解人格设计 → 第 6 章 SOUL.md。
第 1 章 · 分层模型

五层，每层只对下一层说一种话

系统分五层。层与层之间只靠 Go 接口和 ctx 传递的 scope.Scope 说话——没有跨层共享的可变状态，没有绕过接口的直连。 下面的图里，箭头方向是"依赖谁"，不是"谁调用谁"。

接入层 把外部输入翻译成"提交一条消息到某会话"
internal/tui cmd/runebot · WS/SSE rail（规划） 未来：Telegram / Slack / webhooks
编排层 会话路由、轮次调度、事件分发
SessionRunner（规划） EventLedger（规划） internal/subagent internal/bgtask internal/cron
内核层 agent loop 与 hook 体系——系统不可缺少的部分
internal/agent internal/compact internal/breaker internal/permission internal/todo
能力层 模型可调用的工具与外部适配
internal/tools internal/llm internal/skill internal/prompt
持久层 append-only 账本与衍生状态
internal/session + sqlite internal/memory internal/scope internal/config
依赖方向约束

下层不应引用上层。agent 不认识存储与 UI， tools 不认识 agent——跨层需要协作时走接口 （Recorder/Compactor/BGSpawner） 或 hook 回调，由装配方在 main.go 接好。

场景 为什么是"装配层"而不是"框架层"

Hermes 有 gateway/agent/tools 三层；为什么 RuneHarness 把编排层独立出来？

因为"会话归谁、轮次怎么串行、事件发给谁"这件事在 CLI 里是隐含的 （一进程一会话，UI 直接驱动 Run），在 bot 里是显式的 （N 个 chat → N 个槽位 → 串行轮次）。把编排层显式化以后， TUI 和 gateway 都只是"编排层的一个消费方"——coding agent 是 bot 的一个 profile 这句话才成立。

第 3 章 · 核心业务逻辑

两条主流程：同步轮次与异步通知

系统只跑两种事：用户提交消息触发一轮 agent loop，或后台件（bg/cron/dream） 到点把一条通知注入某会话。其他一切都是这两条主线的变奏。

3.1 同步轮次：用户消息 → agent.Run

一条用户消息从提交到回复的完整路径。每一步都有落库动作——历史是逐行追加的， 不存在"内存里的会话"。

一条用户消息的完整时序：斜杠是"跨层消息"，虚线是回调

3.2 异步交付：bg / cron 通知进入会话

后台任务与定时任务产出的事件不直接进对话——它们先进队列， 等"该会话空闲"这个条件成立才注入成一条 user 消息跑一轮。

三路异步源汇入每会话 inbox；只有"空闲"才消费——运行中轮次由 PreChat 自取

3.3 压缩：不占主线的旁路

压缩在两条路径上都存在：自动通道在每个 step 的 Chat 前检查阈值； 主动通道（/compact、模型 compact 工具）按需触发。 两者都落到同一个 Compactor 上，写回的都是 append-only 控制行—— 所以压缩**不改变时序图的形状**，只是往 store 多写几行。

详细设计见 docs/runeharness-compaction-plan.html §4。

第 4 章 · 事件目录

系统里流动的全部事实，分四类

事件不是新概念——是"值得被别处知道的状态变化"的统称。 按流动方向分四类：上行（前端→内核）、下行（内核→前端）、横向（内核↔内核）、 出站（内核→外部）。

4.1 上行事件（前端 → 内核）

事件来源载荷语义

cancelTUI Esc / WS cancel / POST actions —Interrupt 当前轮
answerTUI 权限弹窗 / POST actions ask_id + allow应答权限询问
attachWS attach / GET /events chat_id + since订阅会话事件流
slashTUI /xxx 命令名 + 参数本地查询或注入（不进模型）

4.2 下行事件（内核 → 前端）= EventLedger 的七种

delta / tool_call / tool_result / inject / ask / turn_end / reset ——完整定义与游标语义见 runeharness-gateway-plan.html §3.1。 TUI 侧对应 PartialMsg / ToolCallMsg / ToolResultMsg / InjectMsg / PermRequestMsg / turnDoneMsg，命名不同语义相同。

第 5 章 · 状态迁移

三个状态机：轮次、槽位、后台任务

持久层没有状态机（append-only 即终态）。运行层有三个， 分别管"一轮到哪了"、"一个会话归谁管"、"一个后台任务活着没"。

5.1 轮次状态机（每轮 Run 内部）

轮次内部：CALLING 与 TOOLING/STREAMING 交替；DEAD 含 error/interrupt/maxsteps 三种死因

关键不变量：每个 tool_call 都有结果。中断时 loop 给未执行的调用补占位 （agent.go:295-309），崩溃时由 Fold 在视图侧合成占位——两条路径都保证 "读出来的形态"满足 OpenAI 协议要求。

5.2 槽位状态机（SessionRunner，规划）

完整图与迁移规则见 runeharness-gateway-plan.html §5。摘要： COLD → LOADING → IDLE ⇄ TURN → (evict)；崩溃接管从 COLD 直接补记 turn_end(crashed) 回 IDLE。

5.3 后台任务 / cron 生命周期

bgtask
spawned → running → done / killed / timeout
         ↘ stalled（看门狗提醒一次）
cron
scheduled → fired → rescheduled（周期）
            → fired → burnt → deleted（一次性）
            → missed → delivered-once → deleted（停机漏跑）

5.4 记忆 dream 心跳

不属于槽位，是独立的旁路状态：cooldown → due → dreaming → done/failed。 触发三选一：定时器（每画像冷却分钟数）、手动 /dream、退出收尾。 失败计入 memory_meta 熔断计数。

第 6 章 · 身份槽位：SOUL.md

人格是配置，不是代码——把 Hermes 的 SOUL.md 移植过来

现状的"人格"只有一处：prompt.Identity 常量（一段写死的 coding agent 工程原则）。bot 形态需要把"我是谁、我说话什么调调、我边界在哪" 从代码里挪到一个用户可编辑的文件——这就是 SOUL.md 的角色。

场景 两个 agent 共用一套内核，但声音不一样

本地 CLI 的 coding agent 应该讲工程行话、先结论后证据；bigbigbear 的陪伴 bot 应该慢一点、软一点、记得你昨天说过什么。这两者的"不同"应该写在哪？

不能写进 prompt.Identity——那是代码，改人格要改二进制。 也不能写进 memory——那是"关于用户的事实"，不是"我是谁"。 SOUL.md 是第三层：per-profile 的人格契约，启动时读一次、 冻结进该进程所有会话的 system prompt。

6.1 身份的三层分离

层载体回答的问题改动频率归属
工程准则prompt.Identity（代码常量） "我怎么干活"——先读后写、修根因、不下假设 随版本发RuneHarness
人格SOUL.md（新增，可选文件） "我是谁、怎么说话、边界在哪" 随部署 / 随 profile部署方
项目规则AGENTS.md（未来按 workspace 注入） "在这个仓库里要守什么规矩" 随仓库代码库
用户事实memory 注入 "这个用户是谁、偏好什么、我们经历过什么" 随交互累积记忆层

6.2 加载与冻结规则

1
启动时读一次，会话内冻结
新会话把 SOUL.md 内容拼进 prompt.Env.Soul， Build 输出固定在 identity 段之后、tools 段之前——保持前缀缓存稳定。 已运行会话不换 SOUL.md（同 Hermes 的"tools 改动要 /reset"同一条理由）。
2
查找顺序
RUNE_SOUL 显式路径 > ~/.rune/profiles/<profile>/SOUL.md > ~/.rune/SOUL.md。文件不存在跳过，不算错误。
3
agent 可以改，但应说一声
SOUL.md 是普通文件，模型经 run_command 就能改。 OpenClaw 的约定值得保留：改动后应告知用户——人格变更不该是静默的。
4
大小与洁净约束
读取时过 LooksLikeSecret 同款扫描（不把 API key 写进 SOUL.md）， 上限 8KB，读超时 5s——对齐 Hermes 的 context-file 读取闸。

6.3 与 profile 的关系

没有 SOUL.md 时
Profile = {
  Tools, PermCfg,
  MemoryProfile,
  SkillsDir,
  WorkspacePolicy
}
# 人格 = prompt.Identity 全局一份
有了 SOUL.md 后
Profile = {
  Tools, PermCfg,
  MemoryProfile,
  SkillsDir,
  WorkspacePolicy,
  SoulPath  # → ~/.rune/profiles/<name>/SOUL.md
}
# coding agent：工程准则 + 可选人格
# companion bot：工程准则 + 陪伴人格
# 同内核，不同灵魂

6.4 推荐的 SOUL.md 模板（对齐 OpenClaw 四段式）

# SOUL.md — Who You Are

## Core Truths          # 本质：不是聊天机器人，是一个在做事的实体
## Personality & Vibe   # 说话方式、详略偏好、有没有脾气
## Boundaries           # 不做什么：外部动作先问、隐私不出口、群聊不替用户发言
## Continuity           # 记忆观：每次醒来重读这个文件；改了它要告诉用户
为什么这个设计值得抄

SOUL.md 解决的是"prompt 里哪一段归谁管"的问题。把人格从代码里拿出来， coding agent 和陪伴 bot 共用同一个 prompt.Build 管线、 同一个冻结规则、同一个缓存前缀策略——profile 化的最后一块拼图。
