数据层 · RuneHarness Storage

数据库设计

覆盖三块持久化面：会话库（sqlite，已实现 schema v2）、记忆库（sqlite，v1）、 以及散落的文件型状态（cron_tasks.json / tasks/ / soul / skill 目录）。 文末给出网关落地需要新增的 v3 schema。

版本 v1.0 基线：schema v2 已落地 · memory v1 已落地 · 网关 v3 规划 主库：~/.rune/sessions.db · 记忆库：~/.rune/memory.db
怎么读
  1. 查字段 → 第 2、3 章的表结构。

第 1 章 · 设计原则

四条贯穿所有表的红线

1
append-only，不改写历史
消息行只 INSERT 不 UPDATE。压缩、卸载、中断留下的都是新行； "现在发给 API 的形态"由读侧 Fold 组装，不是物理行本身。
2
租户隔离在函数侧强制
所有读写在事务内校验 scope.TenantID—— 参数里没有 tenant 字段，模型不可能越租户写。
3
schema 用 PRAGMA user_version 演进
不引入迁移框架；版本号单调递增，Open 时自动跑到最新。 破坏性变更（删列、改语义）不在此列，需另开文档。
4
文件型状态只在两类场合
要么是不属于任何会话的进程级配置（cron_tasks.json、SOUL.md、skills/）， 要么是体积大到不该进库的产物（tasks/ 输出文件）。会话内事实一律进 sqlite。
第 2 章 · 会话库 sessions.db（schema v2，已落地）

一个库装五张表：会话、消息、blob、状态、请求留痕

2.1 sessions — 会话元数据

列类型说明
idTEXT PKUUIDv7（时间有序）
tenant_idTEXT租户隔离边界；本地恒 "local"
parent_idTEXT子代理会话指回父会话；主会话为空
kindTEXTmain / subagent
titleTEXT首条 user 消息回填，截 40 rune
modelTEXT建会话时快照的模型名
workspaceTEXT会话绑定的根目录
depthINTEGER0=主代理，子代理递增
created_at / updated_atINTEGERunix；Append 时刷新 updated_at

v3 规划 增列 subject_id TEXT—— 记忆层按 subject 空间寻址用（memory/dream.go:144 已留 TODO）。 另增索引 idx_sessions_subject。

2.2 messages — append-only 消息行

列类型说明
idINTEGER PK AUTOINCREMENT全局时序，也是行 id
session_idTEXT FK→sessions所属会话
kindTEXTmsg / inject / compact_summary / compact_boundary / view_clear / fork
roleTEXTsystem / user / assistant / tool
contentTEXT正文或控制行 meta JSON
thinkingTEXT推理模型思考链（仅展示，不回传 API）
tool_callsTEXTassistant 行的调用 JSON 数组
tool_call_idTEXTtool 行回指的 call id
is_errorINTEGER该结果是否为失败（含被阻止/中断占位）
usage_jsonTEXT该请求的真实 token 用量（token 估算锚点）
created_atINTEGERunix

控制行（kind 非 msg）不进发送形态，只记录决策： compact_boundary 记一次压缩的切点与摘要指针、view_clear 记一批卸载替换、fork 记子会话继承水印。Fold 读侧组装时消费它们。

v3 规划 新增 kind='turn_end' 控制行： 记录轮次终态（status + 起止行 id 水印），账本补记用；以及 channel TEXT 列——多渠道会话（QQ+APP 共享 unified session）时 标记消息来源渠道，回复按渠道路由。

2.3 blobs — 卸载出的原文

列类型说明
idINTEGER PK—
session_idTEXT FK归属会话；祖先链可查
refTEXTblob:// 引用的 ref
contentTEXT被削减的原始工具结果全文
byte_sizeINTEGER字节数
UNIQUE(session_id, ref)；LoadBlob 沿 parent_id 向上查祖先会话

2.4 session_state — 每会话小状态

单行 JSON，放"非投影"的运行态：压缩熔断计数、钳过的窗口上限等。 参与发送形态组装的决策不走这里——那类状态是控制行。

2.5 requests — 请求留痕

列类型说明
upto_msg_id / upto_blob_idINTEGER写入时刻的水位（连控制行一起覆盖）
view_hashTEXT发送形态的 sha256，重放校验用
payload_jsonTEXT失败时的完整发送形态（现场证据）
errorTEXT失败原文（成功为空）

用途：任何一次 Chat 都能用 LoadView(upto_msg_id) 确定性重放， 与 view_hash 比对可发现视图组装逻辑漂移。

第 3 章 · 记忆库 memory.db（schema v1，已落地）

独立库文件，画像决定空间维度

记忆层与会话库分文件——schema 各自演进、记忆可独立备份带走。 库由 internal/memory/sqlite.go 管理，接口对调用方隐藏 tenant/space。

3.1 memories — 当前视图

列类型说明
tenant_id · space · nameTEXT PK 三元主键：租户 · 画像空间（subject/workspace/project）· 条目名
type · descr · bodyTEXT 类型辞典字段 + 简述 + 正文
entities · relatedTEXT JSON 实体列表与关联条目名
source_sessTEXT来源会话 id（溯源用）

3.2 memory_log — 变更流水

全量留痕：upsert / supersede / delete / merge-into 都记一行，含 old_body / new_body / reason / sess。审计与回溯用，不参与读路径。

3.3 memory_meta — 游标与锁

kv 表：dream_cursor（消化水位）、dream_lock（互斥）、 熔断计数。key 值由画像决定，不暴露给调用方。

第 4 章 · 文件型状态（不进库）

三类文件，三种归属

路径形态归属说明
~/.rune/cron_tasks.jsonJSON 数组 durable cron 任务 tmp+rename 原子写；flock 串行化跨进程读写
~/.rune/cron_sched_*.lockflock workspace 调度属主锁 每 workspace 一把；持锁者才点火 durable 任务
~/.rune/tasks/<sess>/bgN.output文本文件 后台任务输出 stdout+stderr 合并落盘；模型用 read_file 读
~/.rune/SOUL.mdMarkdown 人格契约（规划） 见 architecture 第 6 章
~/.agents/skills/*/SKILL.mdMarkdown 技能清单 启动扫描进 prompt 目录，正文按需读
~/.rune/rune.log文本 运行日志 TUI 占终端，日志写文件不写 stderr

为什么这些是文件而不是表：cron_tasks.json 是"跨进程共享的任务定义"， 文件 + flock 比 sqlite 多写者简单；tasks/ 输出是"可能上 MB 的原始字节"， 进库会让 WAL 膨胀；SOUL.md 与 SKILL.md 是"人直接编辑的制品"， 文件形态让编辑、git 管理、diff 都自然。

第 5 章 · v3 增量（网关落地需要）

为 bot 形态补的三张表

网关需要的不是新库，是现有会话库加三块能力： 外部对话映射、轮次终态、多副本占位。全部走 user_version 迁移，向后兼容。

5.1 chat_bindings — 外部对话 → 会话（新增）

列类型说明
tenant_id · channel · chat_idTEXT PK 三元主键：谁、在哪个渠道、哪个外部对话
session_idTEXT FK映射到的内部会话
subject_idTEXT对话另一端的主体（bot 场景下的"用户"）
created_at · last_activeINTEGER—

为什么独立成表而不是 sessions 加列：同一个 chat_id 可以在多个渠道 （QQ / APP / 未来的 web）——绑定关系是"渠道 × 对话"不是"会话的属性"。 会话归一（unified session）时多行 binding 指向同一 session_id。

5.2 turns — 轮次终态（新增，可选）

列类型说明
idTEXT PKturn_id（事件帧里那个）
session_idTEXT FK—
statusTEXTcompleted / interrupted / error / crashed / maxsteps
from_msg_id · to_msg_idINTEGER本轮覆盖的行 id 区间
reasonTEXT失败/中断原因
created_at · ended_atINTEGER—

可选的理由：轮次终态也能用 kind='turn_end' 控制行落 messages——append-only 一致性更好，但查询"该会话最后一轮状态" 要扫行。网关需要频繁回答"上一轮算完没完"，独立 turns 表是这个查询的索引。 两者可以并存：控制行是事实源，turns 是查询加速。

5.3 session_leases — 多副本占位（新增，v3 起建）

列类型说明
session_idTEXT PK—
ownerTEXT持锁实例 id（hostname:pid）
expires_atINTEGER租约到期；续约每 30s 一次

v1 单副本可以不启用；表先建出来是为了让 schema v3 一次性把网关需求收齐， 免得 v4 再迁移。多副本部署时持锁实例才有权给该会话跑轮次——与 cron 的 属主锁同一思路，但锁对象是 sqlite 行而不是文件。

第 6 章 · 数据流全景

一次"用户发消息"写了几张表

写入面：messages 是主线，requests/blobs/state 是支线，memory 是异步旁路

读取面只有一个入口：Fold。它把物理行组装成发送形态， 消费 compact_boundary / view_clear / fork 三类控制行， 修补悬空 tool_call（v3 起），不回写任何表。

附录 · 未实现与边界

规划项清单

  • v3 全部新表/新列：chat_bindings、turns、 session_leases、sessions.subject_id、messages.channel、 kind='turn_end'。落地随 cmd/runebot 一起做，不提前迁移。
  • Fold 悬空修补：读侧合成占位 tool 结果——设计已在 gateway-plan §5.2， 实现挂 v3。
  • 多副本：session_leases 先建表不启用；sqlite 单写者限制下， 多副本意味着共享存储换 PG 或同机多进程——那是另一个文档的事。
  • 不在库里的：EventLedger 的瞬态事件（delta 等）不落库，只走内存环； turn_end 落 turns 或控制行——二选一留到实现期定。
